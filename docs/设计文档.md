## 1. 设计目标与非目标

### 1.1 目标

| 目标 | 具体含义 | 验收方式 |
|---|---|---|
| **可玩闭环** | 从第 1 周能一路玩到某个结局，中间没有死路 | 有单元测试保证「一局必定走到结局」 |
| **可扩展** | 加内容（事件/结局）不需要改引擎一行代码 | 48 个事件全部只写在数据文件里 |
| **可测试** | 核心逻辑不依赖浏览器，能像 JUnit 一样单测 | 34 个测试，1 秒多跑完 |
| **可复现** | 给定种子，整局结果完全确定 | 有测试断言 `play(seed) === play(seed)`（种子 1/2/3/100/2025） |
| **可平衡** | 改数值后能量化验证是否失衡 | `pnpm simulate -- --games 500`（6 风格 × 500 = 3000 局） |
| **反馈真实** | 玩家看到的属性变化必须等于实际变化 | 有测试断言「报告的变化量之和 == 真实变化」 |
| **双人可协作** | 两个人能真并行，而不是互相等 | 引擎与内容之间只有一个类型文件作为接口 |

### 1.2 非目标（**明确不做**，这不是待办而是边界）

| 不做 | 为什么 |
|---|---|
| 美术 / 立绘 / 音效 | 零素材是本项目能在几周内出成品的**前提**。一旦要美术，进度会被资源拖死 |
| 3D / 实时战斗 | 与「文字养成」的核心体验无关，纯粹是技术炫技 |
| 多人 / 联机 | 会把项目从「单机状态机」变成「分布式系统」，复杂度上升一个数量级 |
| 后端服务 | 单机游戏不需要。加后端只会引入部署、鉴权、并发等无关复杂度 |
| 商业级内容量（几百个事件） | 学生的可支配时间不够。**用系统深度换内容广度**才是正确策略 |
| 引擎内做渲染 / 存档 IO | 引擎只做纯逻辑。渲染归 UI，IO 归调用方（见 §8） |

> **边界意识**：一个学生项目失败的最常见原因不是技术不够，而是**范围失控**。
> 上面每一条「不做」都对应一个真实会导致项目烂尾的诱惑。

### 1.3 成功标准

阶段 0 的完成标准（已达成）：

1. `pnpm play` 能从第 1 周玩到结局，且过程中没有卡死或非法状态
2. `pnpm test` 全绿
3. `pnpm simulate` 显示全部 10 个结局都可达
4. 换一套内容（改 `src/data/`）不需要改 `src/engine/` 任何一行

## 2. 核心体验：一局游戏应该发生什么

### 2.1 玩家幻想

> 「我是一个普通的大三学生。这学期只有 16 周，每周我只能认真做 3 件事。
> 学业、身体、心情、钱、技能、朋友——我全都想要，但**我知道我拿不到全部**。」

核心情绪是**稀缺感下的取舍**，而不是「打怪升级」。

### 2.2 情绪曲线设计

```
心情高点                                    ★ 期末爆发（结局揭晓）
   ▲                    ╱╲                  ╱
   │   开学新鲜感 ╱╲    ╱  ╲            ╱╲╱
   │  ╱╲        ╱  ╲  ╱    ╲        ╱╲╱
   │ ╱  ╲      ╱    ╲╱      ╲    ╱╲╱
   │╱    ╲____╱              ╲╱╲╱
   └────────────────────────────────────────▶ 周
    1    4    7(期中)  10  12(抢座)  16(期末)
```

- **第 1–3 周**：新鲜感。社团招新等一次性事件集中在这里（`week <= 3` 条件），给玩家建立初始身份
- **第 7–9 周**：期中考试压力峰值（`ev_midterm` 只在这个区间触发）
- **第 9 周起**：解锁「投简历」行动（需 `skill >= 50`）
- **第 10 周后**：实习面试机会出现（需 `week >= 10` **且** `skill >= 60`）
- **第 12 周后**：期末冲刺（图书馆抢座事件）
- **第 16 周**：结局结算

**设计含义**：条件里的周数限制不是随手写的，它们**共同构成一条时间轴**，让 16 周有节奏而不是平铺直叙。以后加事件时必须先问：「这件事在大三上学期**什么时候**会真实发生？」

> **阶段 1 已兑现**：此前这条只在文档里成立、代码里只有 4 个事件带周数门槛。现在 48 个事件里，开学典礼（≤2 周）、实验室进组（5–8 周）、期中成绩（8–10 周）、双十一（10–12 周）、体测（13–14 周）、抢票回家（≥14 周）等各自落在真实的时间窗里，可用池随周次**累积增长**，而不是从第 1 周到第 16 周都只有 7–8 个。

### 2.3 单局时长

| 形态 | 时长 | 说明 |
|---|---|---|
| 命令行版 | 8–15 分钟 | 48 次行动选择 + 约 11 次事件抉择 |
| 未来 Web 版目标 | 10–20 分钟 | 加上动效和阅读时间 |

这个量级是刻意的：**足够短，让人愿意重开一局试另一种活法**。养成游戏的重玩价值来自「换一条路看看」，而不是单局长度。

## 3. 系统设计

### 3.1 时间系统

| 概念 | 值 | 设计理由 |
|---|---|---|
| 学期长度 | 16 周 | 对应真实大学一个学期，玩家有直觉 |
| 每周行动力 | 3 点 | 少于 3 则每项都做不了，多于 3 则取舍感消失 |
| 总行动机会 | 48 次 | 这是**唯一的核心资源**，所有张力都来自它 |
| 每次行动消耗 | 1 点 | 保持简单。多档消耗（1/2/3 点）留给以后扩展 |

**相位（phase）**：没有显式的 `phase` 字段，相位由 `pending` 和 `endingId` 推导。**外部可观察到的只有三个**（`RESOLVING` 是方法调用内部的瞬时过程，外部看不到——因为那时 `pending=null && endingId=null`，与「玩家行动中」无法区分）：

```
   玩家行动中 ──(行动力归零)──▶ 结算本周 ──(抽中带选项的事件)──▶ 等待玩家选择
        ▲                                                              │
        │                                                              │
        └──────────(进入下一周，行动力重置)◀───────────────────────────┘
                                            (选择完毕)
```

关键规则：**事件未处理完，时间就冻结**（`week` 不增加）。这条规则由 `maybeAdvance()` 单点保证，是引擎最重要的不变量。

**每周结算会单独输出一条回执**（日志文案是「每周固定衰减」，刻意**不叫**「第 N 周结算」）。
这个措辞是被一次误读逼出来的：叫「结算」时玩家会把它读成「本周总结」，
但那条只报告固定衰减，本周的行动效果在自己的行上 —— 两者对不上，玩家就会以为数字错了。

这是**文案歧义被当成数值 bug** 的典型案例，详见 [§4.5](#45-反馈设计回执--预告)。

### 3.2 属性系统

| 属性 | 代号 | 初值 | 每周衰减 | 上下限 | 象征 |
|---|---|---|---|---|---|
| 学业 | `academic` | 60 | −1 | 0–100 | 绩点、保研资格 |
| 社交 | `social` | 50 | −1 | 0–100 | 人脉、朋友 |
| 健康 | `health` | 70 | −1 | 0–100 | 体能、睡眠 |
| 心情 | `mood` | 70 | −1 | 0–100 | 情绪状态 |
| 金钱 | `money` | 800 | −100 | 0–999999 | 生活费余额 |
| 技能 | `skill` | 40 | −1 | 0–100 | 编程、英语等硬实力 |

**为什么是 6 个而不是 3 个或 10 个？**

- 3 个（学业/身体/心情）：太容易同时满足，「取舍」消失
- 10 个：超出玩家的心智带宽，会变成「查表格做题」而不是「做选择」
- 6 个：恰好让「全都要」变成不可能，但每个维度又都能记住

**刻度选择 0–100 的理由**：人对百分制有直觉。代价是单项每次只能加 3–7，看起来数字小、不够「爽」——这是刻意的，见 §4.1。

### 3.3 行动系统

7 个行动，**几乎每个都有代价**（唯一的例外是「去操场跑步」，见下表）：

| 行动 | 收益 | 代价 | 角色 |
|---|---|---|---|
| 去图书馆自习 | 学业 +4 | 心情 −2、健康 −1 | 学业主线 |
| 和朋友聚餐 | 社交 +4、心情 +4 | 金钱 −40 | 社交/心情，需要钱 |
| 去操场跑步 | 健康 +7、心情 +2 | — | 健康**唯一**的有效补给；也是 7 个行动里唯一的纯收益选项 |
| 宿舍躺平休息 | 心情 +7、健康 +1 | 学业 −1 | 心情补给，但浪费时间 |
| 去做兼职 | 金钱 +280 | 健康 −2、心情 −2 | 经济压力出口 |
| 写项目/刷题 | 技能 +4、学业 +1 | 心情 −2、健康 −1 | 技能主线 |
| 投简历（技能≥50 且第 9 周起） | 技能 +3 | 心情 −3 | 求职线，后期解锁 |

**设计要点**：

1. **每个行动都要有代价**。纯收益行动会让最优解变得显然，游戏就退化成「点击收集」
2. **健康只有「跑步」能有效补**（+7），这是刻意的瓶颈。健康是那个「平时不觉得、崩了才知道」的属性
3. **金钱压力是硬约束**：每周固定支出 100，16 周共 1600，而初值只有 800。**不兼职必然破产**，破产会累计「穷困周数」并持续扣心情
4. **解锁条件制造时间感**：投简历要 `week >= 9`（第 9 周起就可以），让前 8 周必须专注积累

### 3.4 事件系统

48 个事件，约半数带选项（其余为直接结算的效果）。

**事件的三层过滤**（按顺序）：

```
1. 类别匹配      category === 'random'
2. 未触发过      !repeatable && !seenEvents.includes(id)
3. 条件满足      evaluate(requires, ctx)
        │
        ▼
   按 weight 加权随机抽一个（默认权重 1）
```

**设计要点**：

1. **`repeatable` 默认 `false`**：绝大多数事件一局只该发生一次。「室友通宵打游戏」可以重复（它是生活常态），「社团招新」绝不能重复（它只发生一次）
2. **权重和 `repeatable` 一起表达「常见程度」**：`ev_roommate_late` 权重 3 且 `repeatable: true`（宿舍日常，一局会反复发生）；`ev_midterm` 权重 5 但只在第 7–9 周出现。`ev_club_recruit` 权重 8 但只在第 1–3 周——**高权重 + 短时间窗口 = 「错过了就没了」的紧迫感**
3. **选项要有真实取舍**，不能有明显的「正确答案」：

```ts
// ev_borrow_money：好设计 —— 三个选项都损失点什么
{ label: '直接借给他',    effects: [钱 −500, 社交 +10] },
{ label: '借三百，说自己也紧', effects: [钱 −300, 社交 +5] },
{ label: '委婉拒绝',      effects: [社交 −6, 心情 −4] },
```

4. **选项可以条件不足而灰显**：`ev_laptop_broken` 的「咬牙换了」要求 `money >= 1200`。穷的时候你连选择的资格都没有——**这是叙事的一部分**

### 3.5 结局系统

10 个结局，按 `priority` 升序判定，取**第一个命中**的。

**最重要的设计原则：一个坏结局只对应一个核心失败维度。**

| 结局 | priority | 条件 | 失败维度 |
|---|---|---|---|
| 学业崩塌 | 10 | `academic < 25` | 学业 |
| 住院休学 | 20 | `health < 15` | 身体 |
| 情绪崩溃 | 30 | `mood < 15` | 心情 |
| 为钱所困 | 40 | `穷困周数 ≥ 4 && skill < 55` | 经济 |
| 拿到大厂 Offer | 50 | `拿到实习Offer && skill ≥ 75` | （好） |
| 保研上岸 | 60 | `academic ≥ 85 && 拿过奖学金` | （好） |
| 技术宅的胜利 | 70 | `skill ≥ 80 && social < 60` | （好） |
| 社交达人 | 80 | `social ≥ 85 && academic < 70` | （好） |
| 全面发展 | 90 | 四项都达标 | （好，最难） |
| 平凡的期末 | 999 | `all: []`（恒真） | 兜底 |

**为什么必须单维度？** 我第一版把 `mood < 10` 也放进了「学业崩塌」的 `any` 里。结果是：因为 `学业崩塌` 优先级更高，它把所有「心情崩了」的情况都抢走了，**「情绪崩溃」在 3000 局模拟里一次都没触发**——一段死代码。

**兜底结局的技巧**：最后一条用 `{ type: 'all', conditions: [] }`。空集合上的 `every()` 恒为真（这是数学上良定义的 vacuous truth），所以不需要为了「恒真」硬凑一个 `academic >= 0` 这样的假条件。有单元测试守着这条不变量。

### 3.6 flag 与暗线

`flag` 用来记录「发生过什么」，让后续事件据此判断走向。**阶段 1 之前**这里其实是个缺口——11 个 flag 只有 3 个被读取（还全是被结局读），所谓「三条暗线」是文档里的自我美化，代码里一条都不存在。

**阶段 1 已补齐**。现在每条暗线都是「前置事件设 flag → 后续事件读 flag」的闭环：

| 暗线 | 前置（写 flag） | 后续（读 flag） |
|---|---|---|
| 社团·集训队 | `ev_club_recruit` → `加入集训队` | `ev_training_team` 选拔 → `社团贡献 +1` |
| 社团·街舞社 | `ev_club_recruit` → `加入街舞社` | `ev_dance_performance` 演出 → `社团贡献 +1` |
| 社团·骨干 | 上两条攒 `社团贡献` | `ev_club_elite` 用 `flagEq 贡献==2` 竞选骨干 |
| 情感 | `ev_crush` → `纸条成功` | `ev_first_date` 第一次约会 |
| 人际 | `ev_roll_call` → `替答到过` | `ev_teacher_remembers` 被老师记住 |
| 经济 | `ev_borrow_money` → `借出去过钱` | `ev_debt_collect` 催债 |
| 学业 | `ev_academic_warning` → `被预警` | `ev_makeup_exam` 补考 |
| 学业 | `ev_scholarship` → `拿过奖学金` | `ev_baoyan_consult` 保研咨询会 |
| 求职 | `ev_internship` → `拿到实习Offer` | `ev_first_day_intern` 实习第一天 |
| 求职 | 「投简历」行动 → `投递次数` | `ev_written_test` 用 `flagAtLeast 投递次数>=3` 笔试通知 |
| 健康 | `ev_body_warning` → `身体预警` | `ev_health_checkup` 体检复查 |
| 心理 | `ev_counselor` → `谈过心` | `ev_psych_counseling` 心理咨询 |
| 财务 | `ev_laptop_broken` → `电脑坏了` | `ev_save_for_laptop` 攒钱买电脑 |

**当前状态**：写入 12 个 flag、被读取 14 个（`投递次数` 由行动写、`穷困周数` 由每周结算写，故写入侧不在此表），**死 flag = 0**。

> 一个诚实的边界说明：这些暗线**不是独立的抽取池**（`EventCategory` 仍只有 `'random'`），
> 后续事件和普通事件混在同一个随机池里、靠 `flag` 条件触发。
> 「行动专属事件」（给行动加 `eventPool` 之类）仍是未做的扩展点，见 §7。

## 4. 数值设计哲学

### 4.1 折旧机制（本项目最重要的一次平衡修正）

**问题**：第一版每个行动给 +6~+8。48 次行动对 0–100 刻度是碾压，模拟结果是平均学业 95、社交 99，保研率 36%。

**修法**：引入**每周衰减**（学业/技能/社交/健康 −1，心情 −1）。于是：

> 你光是为了「不往下掉」就得持续投入。行动力立刻从「富余」变成「稀缺」，取舍才有意义。

这符合现实直觉：不复习会忘，不联系会疏远，不运动体能会退化。

**调平衡后的量化标准**（实测口径——用真实引擎跑一遍，不是估算）：

| 阶段 | 成本 | 说明 |
|---|---|---|
| 前期突击 | 第 1–3 周投入 **7 次**自习 | 学业 60 → 85 |
| 后期维持 | 之后每 **~4 周**补 1 次（共 4 次） | 每次 +4，足以抵消 4 周的 −1 衰减 |
| **合计** | **11 次行动 = 48 次的 22.9%** | 第 16 周末学业 = 88 |

关键是**「一次性达标」和「保持到达标」是两笔账**：突击只要 7 次（约 15%），
但每周 −1 的衰减逼你必须不断回来补，全程下来要多花 4 次（合计 ~23%）。
所以想同时拿到两个好结局就要花掉近一半行动力，剩下的还要维持健康、心情和现金流
——**这才是张力的真正来源，而不是单次行动的成本**。

### 4.2 坏结局不能把好结局堵死

**问题**：心情每周 −2 加上学习/写代码的 −2，导致「学霸」风格 47% 情绪崩溃。因为坏结局优先级更高，**一旦心情崩了，所有好结局都不可能达成**，「技术宅的胜利」常年 0%。

**修法**：
- 心情衰减减半到 −1
- 崩溃阈值从 `< 25` 下调到 `< 15`（真正的灾难级别）
- 移除「投简历」白送的社交 +2（它让「孤僻技术宅」这个设定根本走不通）

**教训**：坏结局的**触发门槛必须足够极端**，否则它会变成一个「否决其他所有结局的守门人」，而不是一个「你玩砸了」的反馈。

### 4.3 健康为什么最紧

健康是唯一「**多个行动都在扣、只有运动在补**」的属性：

```
被扣：每周衰减 −1、自习 −1、写代码 −1、兼职 −2
被补：跑步 +7、休息 +1
```

第一版跑步只给 +5，结果是「均衡派」终局健康均值只有 48，连「全面发展」（要求 ≥70）都拿不到——**平衡模拟器发现这个问题后，把跑步提到 +7、兼职扣血从 −3 减到 −2。**

### 4.4 平衡的量化验收标准

`pnpm simulate` 的期望形状：**每种决策风格都应有清晰且不同的「签名」**。

```
结局                  均衡派      学霸    技术宅  社交达人      躺平      随机
学业崩塌                0.0%      0.0%      0.0%      0.0%     16.8%      0.0%
```

判断标准：
- **每种风格至少有一个「招牌结局」**（学霸→保研 48%，技术宅→崩溃 44%/技术宅 11%，社交达人→社交 39%）
- **均衡派应该低风险**（坏结局合计 < 5%）但**拿不到极致结局**
- **极端风格应该高风险高回报**（技术宅：44% 崩溃 vs 11% 大厂 Offer）
- **每个结局都必须至少可达一次**（已固化成单元测试，跑 720 局）

### 4.5 反馈设计：回执 ≠ 预告

**这是本项目吃过一次亏才总结出来的原则。**

养成游戏的核心循环是「选择 → 观察后果 → 调整策略」。**中间那一环断了，游戏就退化成盲选。**
所以玩家看到的属性变化必须等于实际变化，而且要**分得清两件事**：

| | 预告（preview） | 回执（receipt） |
|---|---|---|
| 玩家看到的 | 行动菜单里灰色的「学业 +4」 | 结算里彩色的「学业 +2（已满）」 |
| 含义 | 「这个选项**说**它会做什么」 | 「**实际**发生了什么」 |
| 数据来源 | 效果数组（声明值） | `applyEffects` 的返回值（实际值） |

**三条规则**：

1. **回执必须报告实际值，哪怕不好看。**
   学业 98 时选「自习」，预告说 +4、实际只 +2，回执就要显示 +2 并注明「已满」。
   如果显示 +4 让玩家高兴，他会一直做无效投入，**永远学不会该换方向了**。

2. **反馈失败比反馈缺失更糟。**
   加上回执之前，每周的 6 项衰减完全不可见，玩家只是「感觉有点难」；
   但如果显示的成本/收益是错的，玩家会基于错误信息做决策，这比没有信息更糟。

3. **预告和回执要从不同的数据算，不要图省事共用一个。**
   共用只能在简单情形下凑合；一旦有属性上限、`if` 条件、`branch` 概率分支，
   两者必然分叉 —— 这时「用一个」就意味着其中一个必然是错的。

**这个原则是被一次反馈逼出来的**：有玩家说「每周衰减与实际不符」。
量化核对后是 **839 个项次 0 处不一致** —— 数值完全正确，
真正的问题是那一行叫「第 N 周结算」，被读成了「本周总结」。
**教训是双向的**：
- 显示的数字必须是真的（所以有 I9 那条不变量）
- 显示的**语义**必须无歧义（所以后来改名叫「每周固定衰减」，并在开场主动解释）

**文案歧义和数值错误，在玩家眼里是一回事。** 两者都要当成缺陷来修。

## 5. 内容模型（策划视角）

### 5.1 一条事件的解剖

```ts
{
  id: 'ev_internship',              // 唯一，用 ev_ 前缀
  title: '实习面试机会',             // 卡片标题，尽量短
  text: '学长内推你到一家公司面后端开发实习。HR 说这周内安排面试。',  // 1–3 句，写「场景」不写「结果」
  category: 'random',
  weight: 6,                        // 数字越大越常出现
  repeatable: false,                // 省略即 false（只触发一次）
  requires: {                       // 什么时候可能出现
    type: 'all',
    conditions: [
      { type: 'week', op: '>=', value: 10 },
      { type: 'stat', key: 'skill', op: '>=', value: 60 },
    ],
  },
  choices: [                        // 有 choices → 等玩家选；没有 → 直接结算 effects
    {
      label: '全力准备，刷八股和算法',
      effects: [
        { type: 'stat', key: 'skill', delta: 6 },
        { type: 'stat', key: 'mood', delta: -6 },
        {
          type: 'branch',           // 概率分支：必定且只命中一个
          options: [
            { weight: 6, effects: [拿到 Offer, 心情 +15, 写日志] },
            { weight: 4, effects: [心情 −10, 写日志] },
          ],
        },
      ],
    },
    { label: '算了，先顾学业', effects: [学业 +4] },
  ],
}
```

### 5.2 写作规范

1. **`text` 写场景，不写结果**。「HR 说这周内安排面试」而不是「你可能会拿到 Offer」
2. **选项标签要短且有画面感**。「全力准备，刷八股和算法」比「努力准备面试（技能+6，60% 成功）」好得多
3. **不要在 `text` 里写数值**。数值由 UI 从 `effects` 自动生成
4. **每个选项都要有代价**。如果一个选项严格优于其他，那这个事件就没有存在意义
5. **条件要能自圆其说**。「第 10 周后才有实习机会」是合理的，「第 5 周才能进图书馆」不合理
6. **一次性事件要有「不可错过」的性格**。用高权重 + 窄时间窗口，而不是低权重 + 全程可见

### 5.3 现实感优先于数值效率

一个容易犯的错误是：为了数值平衡而写出**不像大学生活**的事件。正确顺序是**先保证场景真实，再调数值**。例如「室友通宵打游戏」这个事件的价值不在于它加多少属性，而在于**任何一个住过宿舍的人都能立刻代入**。

## 6. 决策记录（ADR）

记录关键决策及其**当时的理由**，避免未来的自己（或协作者）好心地把它们改回去。

### ADR-001：引擎用纯 TypeScript，零浏览器依赖

- **决定**：`src/engine/` 不 import 任何 DOM / 框架 / Node API
- **理由**：① 可以用 Vitest 像 JUnit 一样单测；② 命令行就能验证玩法，不用等 UI 做好；③ UI 层可以随时替换（React/Vue/终端/小程序）
- **代价**：需要自己写一个 CLI 来驱动游戏
- **如果被推翻会怎样**：一旦引擎里出现 `document`，单元测试就必须跑 jsdom，测试速度从 1 秒内变成数秒，且不能再在 Node 里跑平衡模拟

### ADR-002：随机数发生器从外部注入

- **决定**：`new GameEngine(data, { seed })`，**游戏内的随机全部来自 `mulberry32(seed)`**（`Math.random()` 只在调用方没传种子时被 `randomSeed()` 用一次，用来生成种子本身）
- **理由**：可复现是三个功能的地基——单元测试断言随机行为、玩家复现某一局、批量数值模拟
- **代价**：**随机调用次数和顺序会影响结果**，所以改动引擎代码会让旧种子失效（见技术文档 §5.4）
- **如果被推翻会怎样**：`simulate` 的结论会被随机噪声淹没，无法判断数值改动是否真的有效

### ADR-003：逻辑写成数据（条件 DSL + 效果 DSL）

- **决定**：条件与效果都是判别联合类型，可以序列化、可以嵌套
- **理由**：① 策划/内容作者改数值不用碰代码；② TS 的穷尽性检查让「加了 DSL 分支忘了处理」直接编译报错；③ 递归结构让 20 行引擎代码表达无限嵌套的玩法
- **代价**：DSL 的表达力有边界，遇到 DSL 写不出的逻辑就得扩展引擎
- **如果被推翻会怎样**：事件逻辑变成硬编码函数，`src/data/events.ts` 就无法保持"纯数据"，双人并行协作立刻失效

### ADR-004：坏结局单维度

- **决定**：每个坏结局只看一个属性的失败
- **理由**：多维度 `any` 会让高优先级结局**饿死**低优先级结局（实测「情绪崩溃」3000 局 0 触发）
- **代价**：坏结局的叙事变得单一（不能写「学业和身体同时崩」这种复合悲剧）
- **替代方案**：若真需要复合结局，应给它独立的更高优先级，而不是塞进已有结局的 `any` 里

### ADR-005：先做命令行，不做界面

- **决定**：阶段 0 只交付 CLI
- **理由**：把「玩法是否成立」和「界面是否好看」解耦。玩法靠 CLI + 模拟器就能验证完，UI 只是表现层
- **代价**：CLI 版无法作为作品集展示（所以阶段 3 必须补 UI）
- **如果被推翻会怎样**：如果先做 React，会在「玩法还没定型」时就把大量精力投进 UI 重构
- **事后验证**：这个决定的收益在阶段 3a 兑现了 ——
  做 Web 界面时**引擎零逻辑改动**，因为引擎从来就不知道界面的存在。
  如果当初把渲染逻辑混进引擎，加 Web 界面就得边重构边加功能

### ADR-006：属性衰减与上限锁定

- **决定**：每周固定衰减 + 属性硬夹取到 `[min, max]`
- **理由**：衰减提供「必须持续投入」的张力；夹取保证数值不会失控（有单元测试守住）
- **代价**：玩家在后期会撞到 100 的天花板，感觉「白加了」。可能的改进是加入**递减收益**（越高越难加）
- **后续**：见 ADR-007 —— 触顶必须**被玩家看见**（回执报告实际值而不是声明值），否则「白加了」会变成看不见的浪费

### ADR-007：玩法反馈必须由引擎产出「实际变化量」

- **决定**：`applyEffects` 返回**实际**造成的属性变化（含 `capped` 触顶标记），
  挂到对应的 `LogEntry.changes` 上；UI 只负责渲染，不自己推算
- **理由**：见 [§4.5](#45-反馈设计回执--预告)。养成游戏靠「选择 → 观察后果 → 调整策略」成立，
  这一环断了游戏就退化成盲选。而**只有引擎知道**三件 UI 算不出来的事：
  属性被 clamp 截断了多少、`if` 走了哪条分支、`branch` 命中了哪个结果
- **代价**：`LogEntry` 增加了字段（见技术文档 §2.3，属「可加不可减」）；
  `applyEffects` 的返回值从 `void` 变成数组；`pushLog` 必须返回条目以便「先写日志后补回执」
- **如果被推翻会怎样**：UI 只能拿效果数组去猜数字，
  于是触顶时显示虚假的 `+4`、`branch` 显示所有分支的并集 ——
  **提示错误比没有提示更糟，玩家会基于错误信息做决策**
- **配套约束**：有一条不变量守着他（技术文档 I9「报告之和 == 真实变化」）。
  这条不变量在排查「每周衰减与实际不符」时直接定案，避免去改一份本来正确的代码

## 8. 边界：引擎不做什么

这条边界必须守住，否则项目会慢慢烂成一个"什么都在里面"的大泥球。

| 引擎**不做** | 应该由谁做 |
|---|---|
| 渲染 / 显示 / 格式化 | UI 层（`src/cli/`、未来的 `src/web/`） |
| 读文件 / 写文件 / localStorage | 调用方（引擎只接收和返回纯对象） |
| 计时器 / 动画 / 帧循环 | UI 层 |
| 音频 / 图片加载 | UI 层 |
| 输入解析（键盘、鼠标、点击） | UI 层 |
| 网络请求 / 排行榜 | 未来的独立服务，绝不进引擎 |
| 存档格式与迁移 | 独立的存档层（`src/save/`），引擎只提供 `getState()` / 未来的 `loadState()` |

**引擎只做一件事**：给定一个 `GameState` 和一个输入，返回新的 `GameState` 和「发生了什么」。这是纯函数式的核心，也是它能被无限复用的原因。

## 9. 路线图与验收标准

每个阶段都必须**独立可交付且能跑**，不允许「做到一半不能运行」的状态。

### ✅ 阶段 0：引擎核心 + 命令行（已完成）

**验收**：CLI 能从第 1 周玩到结局；测试全绿（交付时 27 个，当前 33 个）；10 个结局全部可达。

### 阶段 1：内容扩充

**目标**：消除重复感。

- 事件 17 → **48**（✅ 已完成）
- 增加 `week` 分区覆盖：目前第 13–16 周事件偏少（✅ 已完成）
- 给未使用的 DSL 分支写出真实内容：`any`、`not`、`chance`、`flagEq`、`end`（✅ 已完成）
- 把只写不读的 flag 接成暗线（✅ 已完成，13 条）

**验收标准**：
- 连续玩 3 局，**重复遇到的事件不超过 30%**（⚠️ 当前 37%，接近但未达标，见技术文档 §9.5）
- `pnpm simulate` 中死结局列表为空（✅）
- 每种决策风格仍保持清晰签名（不能因为加内容而让分布糊掉）（✅）
- **新增**：死事件列表为空（✅，见 `simulate` 内容健康度）

### 阶段 2：存档 / 读档

**目标**：让一局可以中断和继续。

- JSON 存档 + `version` 字段 + 迁移机制
- **必须先解决 RNG 状态序列化问题**（见技术文档 §10）
- 存档版本与引擎版本解耦

**验收标准**：
- 存档 → 读档 → 继续玩到结局，结果与不中断完全一致
- 旧版本存档能被新版本引擎正确迁移
- 损坏的存档不会让游戏崩溃，而是给出明确错误

### 阶段 3：Web 界面

**目标**：变成能发链接给朋友玩的东西。

**分两截做**（这是刻意的顺序决定，理由见 §4.5 —— UI 会改变节奏感受和对单次互动的
信息密度要求，所以在写 40 个事件之前先打通界面，能避免内容写完才发现要重写）：

**3a · 最小可用版（✅ 已完成）**

- React + Vite
- 属性面板（进度条）、可滚动日志流、行动面板、事件卡、结算回执、结局页
- 移动端单列布局；`?seed=N` 可分享复现链接
- **不做**：动效、图表、路由、存档、美术

**验收（三条全中）**：
- ✅ **引擎代码一行都没改** ← 对分层架构的第一次真实验证。
  实际只加了 16 行（`STAT_ORDER` 常量 + 注释），**零逻辑改动**
- ✅ 手机上能完整玩一局走到结局
- ✅ 构建产物 245 KB / gzip 78 KB

**3b · 打磨（待做）**

- 动效：属性变化的高亮/飘字、事件卡入场、周推进过渡
- 属性可视化图表（雷达图 / 时间序列）

- 部署到 Vercel / GitHub Pages，URL 进简历

### 阶段 4：打磨与作品集化

## 10. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| **范围失控**（想同时做 UI + 内容 + 联机） | 项目烂尾 | 严格执行 §1.2 的非目标清单；每个阶段独立可交付 |
| **内容量不足导致重复感** | 玩两局就腻 | 阶段 1 优先解决；用「连续 3 局重复率 < 30%」量化 |
| **数值失衡** | 某条路明显最优，游戏失去意义 | 每次改数值都跑 `pnpm simulate`；有测试守着「所有结局可达」 |
| **网络不稳定**（本机 HTTPS 到 GitHub 间歇阻断） | 开发节奏被打断 | 已改用 SSH（实测 5/5 vs 0/5）；`pnpm preflight` 一键区分「网络问题」和「代码问题」 |
| **编码问题**（PS 5.1 把 UTF-8 当 GBK） | 静默数据损坏 | 见技术文档 §8.1 的 BOM 规则与自检命令 |
| **架构腐化**（引擎里混入 UI / IO 代码） | 失去可测试性和可移植性 | 守住 §8 的边界；代码评审时先看 engine 层的 import 列表 |
| **RNG 状态不可序列化** | 存档无法忠实恢复 | 阶段 2 必须先决策（技术文档 §10.2 已给出三个方案） |
| **单人维护疲劳** | 项目停滞 | 每个阶段都有可见产出；用 `pnpm simulate` 的分布图获得正反馈 |
