## 1. 架构总览

### 1.1 分层与依赖方向

依赖是**严格单向**的，不允许反向引用：

```
│    play.ts         交互式试玩                        │

│    endings.ts      结局表                            │

└──────────────────────┬──────────────────────────────┘

┌──────────────────────▼──────────────────────────────┐
│  src/engine/       引擎层（纯 TypeScript，零 DOM）    │
│    types.ts        全部类型定义（唯一协作契约）        │

│    conditions.ts   条件求值                          │

└─────────────────────────────────────────────────────┘
```

**关键约束**（已自动化，见 [§6.3](#63-pnpm-preflight推送前自检)）：

```powershell
pnpm preflight -- -SkipTests
# 其中「架构边界」一节会检查：engine 层无 DOM/框架/Node IO 依赖 + 依赖方向单向 + BOM 合规
```

引擎的 import 只允许来自 `./xxx`（自己的同级模块）。这是 ADR-001 的落地检查方式，

## 2. 模块职责与公开 API

### 2.1 各模块职责速查

| 文件 | 职责 | 依赖谁 | 导出 |
|---|---|---|---|
| `types.ts` | 只有类型定义，**运行时零代码** | 无 | 全部类型 |
| `rng.ts` | 种子随机数、加权抽取 | `types` | `mulberry32` `randomSeed` `pickWeighted` `pickOne` |
| `conditions.ts` | 条件树求值 | `types` | `evaluate` |
| `state.ts` | 建初始状态、写日志、深拷贝 | `types` | `createInitialState` `pushLog` `cloneState` |
| `effects.ts` | 效果树应用、生成数值摘要、**产出结算回执** | `conditions` `rng` `state` `types` | `applyEffects` `describeEffects` `STAT_LABELS` |
| `engine.ts` | 流程编排 | 以上全部 | `GameEngine` `NewGameOptions` `ChoiceView` |
| `index.ts` | 统一出口 | 以上全部 | re-export 全部 |
| `../cli/text.ts` | 终端排版（唯一在 cli 层但不依赖引擎的工具） | `node:process` | `displayWidth` `padEndWidth` `padStartWidth` `detectColorSupport` `createColors` |

**两处容易忽略的签名**（改代码前注意）：

```ts
// state.ts —— 返回刚写入的日志条目，让调用方能补挂 changes
export function pushLog(state, kind, text): LogEntry

// effects.ts —— 返回实际造成的属性变化（不是 void）
export function applyEffects(ctx, effects): StatChange[]
```

`applyEffects` 从 `void` 改成返回数组是**向后兼容**的：现有调用方忽略返回值即可，
所以这个改动没有波及 `engine.ts` 以外的任何调用点（`cli` / 测试 / 模拟器都不直接调它）。

`types.ts` 零运行时依赖这一点很重要：它保证 `import type` 之后不会产生任何 JS 代码，所以内容层可以自由地只依赖类型。

### 2.2 `GameEngine` 完整 API

#### 构造

```ts
new GameEngine(data: GameData, options?: NewGameOptions): GameEngine
```

| 参数 | 类型 | 说明 |
|---|---|---|
| `data` | `GameData` | 一整套内容，通常传 `GAME_DATA` |
| `options.seed` | `number?` | 不传则用 `randomSeed()` 随机。传了就完全可复现 |

#### 只读查询（**稳定契约**，UI 只应使用这些）

| 方法 | 返回 | 说明 |
|---|---|---|
| `getSeed()` | `number` | 本局种子，应该显示给玩家（可复现的前提） |
| `getState()` | `GameState` | **深拷贝**的状态快照。外部改它不影响引擎 |
| `getConfig()` | `GameConfig` | 数值配置 |
| `getPending()` | `GameEvent \| null` | 正在等待玩家选择的事件 |
| `getPendingChoices()` | `ChoiceView[]` | 待选事件的选项 + 每个选项**是否可用** |
| `isEnded()` | `boolean` | 是否已结算结局 |
| `getEnding()` | `Ending \| null` | 结局对象（含 `title` / `text`） |
| `availableActions()` | `ActionDef[]` | 当前可执行的行动（已按行动力和条件过滤） |

`ChoiceView` 的定义：

```ts
interface ChoiceView {
  choice: Choice      // 选项数据（label、effects）
  enabled: boolean    // false → UI 应该把按钮灰掉
}
```

> **设计意图**：`getPendingChoices()` 把「判断」留在了引擎里。UI **不需要** import `evaluate`、不需要构造 `EvalContext`、不需要知道条件 DSL。条件系统改版时，UI 一行都不用动。

#### 推进游戏（**稳定契约**）

| 方法 | 返回 | 会抛错的时机 |
|---|---|---|
| `takeAction(actionId: string)` | `TurnResult` | 已结束 / 有待处理事件 / 未知行动 / 行动力不足 / 条件不满足 |
| `choose(choiceIndex: number)` | `TurnResult` | 没有待处理事件 / 序号无效 / 该选项条件不满足 |

**抛异常是刻意的设计**（fail fast）：调用方本就应该先用 `availableActions()` 和 `getPendingChoices()` 过滤掉非法操作。抛错代表**调用方写错了**，而不是「可预期的失败」。

> 这个约定在写测试时咬过我一次：测试里图省事写 `engine.choose(0)`，结果 0 号选项是「换主板（需要 1200 元）」条件不满足 → 直接抛错。**这个抛错是正确的**，它暴露了测试没按 `enabled` 过滤，而不是引擎有问题。

`TurnResult` 的定义：

```ts
interface TurnResult {
  logs: LogEntry[]          // 只包含本次操作新产生的日志（增量，不是全量）
  pending: GameEvent | null // 需要玩家做选择的事件
  ended: boolean
}
```

#### 内部实现（**非契约**，可自由重构）

`private` 成员：`createContext` `endWeek` `rollWeeklyEvent` `triggerEvent` `maybeAdvance` `settleEnding` `buildResult`

这四个字段是 `private readonly`：`data` `state` `rng` `seed`，另有可变的 `pending`。

> ⚠️ **TS 的 `private` 编译后完全消失**，运行时照样能访问。想真正私有得用 `#field`。这里用编译期 `private` 足够了。

### 2.3 什么算「稳定契约」

改动前请对照：

| 层级 | 内容 | 变更自由度 |
|---|---|---|
| **稳定契约** | `GameEngine` 的公开方法签名、`GameState` 字段、`LogEntry` 字段、`GameData` 结构、DSL 分支语义 | 改动 = **破坏性变更**，必须同步更新文档、测试、所有调用方 |
| **可加不可减** | 给已有接口**新增可选字段**（如 `LogEntry.changes?`） | 非破坏性，但需同步文档 |
| **内部实现** | `private` 方法、模块内部辅助函数 | 自由重构 |
| **内容** | `src/data/` 里的每一条数据 | 随时可加可改，不影响任何代码 |

> 本项目的两次实际变更可以对照上面这张表：
> `LogEntry` 新增可选字段 `changes` → 「可加不可减」；`applyEffects` 返回值从 `void` 变成数组
> → 因为原有调用方都忽略返回值，也算非破坏性。两者都**需要同步文档**，但都不需要改调用方。

## 3. 数据模型

### 3.1 `GameState` 字段表与不变量

```ts
interface GameState {
  week: number                 // 1..config.totalWeeks
  actionPoints: number         // 0..config.actionPointsPerWeek
  stats: Stats                  // 6 项属性，各自被夹在 statRanges 内
  flags: Flags                  // 事件留下的痕迹
  seenEvents: string[]          // 已触发过的非重复事件 id
  log: LogEntry[]               // 完整历史，只追加
  endingId: string | null       // null = 未结束
}

/** 一条日志。这是 UI 唯一的信息来源 */
interface LogEntry {
  week: number
  kind: 'action' | 'event' | 'system' | 'ending'
  text: string
  changes?: StatChange[]        // 这条日志造成的**实际**属性变化；无变化时该字段不存在
}

/** 一次结算里某项属性的实际变化量 */
interface StatChange {
  key: StatKey
  delta: number
  capped?: 'min' | 'max'        // 撞到上限/下限被截断了
}
```

**`changes` 是「回执」，不是「预告」** —— 这是本项目最容易搞错的一个语义：

| | 预告（preview） | 回执（receipt） |
|---|---|---|
| 数据来源 | `describeEffects(effects)` | `applyEffects()` 的返回值 |
| 含义 | 这个效果**声明**它会做什么 | 实际**发生了什么** |
| 触顶时 | 显示 `学业 +4` | 显示 `学业 +2`（并标 `capped: 'max'`） |
| `if` / `branch` | 列出所有分支的并集（不准确） | 只算真正走到的分支 |
| 用在哪 | 行动菜单（灰色） | 结算显示（彩色） |

**两者不一致是正常的、也是必要的**：玩家必须能从回执里看出「我这次白费了」，
否则他没法调整策略。所以不要让 UI 拿 `effects` 数组去推算回执。

**必须守住的不变量**：

| # | 不变量 | 由谁保证 | 有测试吗 |
|---|---|---|---|
| I1 | 每项属性都在 `statRanges` 的 `[min, max]` 内 | `effects.ts` 里的 `clamp` 是**唯一**改属性的入口 | ✅ |
| I2 | `week` 单调不减，且 `≤ totalWeeks` | `maybeAdvance()` 是**唯一**改 `week` 的地方 | ✅ |
| I3 | `actionPoints` 归零后必然进入 `endWeek()` | `takeAction()` 里的判断 | ✅ |
| I4 | 有 `pending` 时 `week` 不增加 | `maybeAdvance()` 首行检查 | ✅ |
| I5 | `endingId !== null` 后不能再 `takeAction` | `takeAction()` 首行守卫 | ✅ |
| I6 | 一局游戏必定走到某个结局 | 兜底结局（空 `all` 恒真） | ✅ |
| I7 | `log` 只追加，不修改历史条目 | 只有 `pushLog` 写它 | — |
| I8 | `state` 可被 `structuredClone` / `JSON.stringify` 无损处理 | 只用 JSON 可表达的类型 | — |
| **I9** | **报告的 `changes` 之和 == 属性的真实变化** | `applyEffects` 按同一入口记录 | ✅ |

> **I9 是「回执可信」的根本保证**，也是这个项目里最有价值的一条不变量。
> 它不关心引擎内部怎么算，只要求「你说变了多少」和「实际变了多少」永远一致。
>
> 实战价值：有玩家反馈「每周衰减与实际不符」，先跑 I9 的检查得到 **839 个项次 0 处不一致**，
> 于是立刻定位到「不是引擎算错，而是文案有歧义」——
> 如果没有这条检查，很可能会去「修」一份本来正确的 `weeklyEffects`。

**I8 的实践含义**（写新字段时必须遵守）：

- 用 `null` 而不是 `undefined`。`JSON.stringify` 会**直接丢掉** `undefined` 字段，导致存档读回来少一个 key。`endingId: string | null` 就是为此
- 不要放函数、`Map`、`Set`、类实例、循环引用
- 需要新的复合结构时，用普通对象和数组

### 3.2 `GameConfig`

```ts
interface GameConfig {
  totalWeeks: number              // 16
  actionPointsPerWeek: number     // 3
  initialStats: Stats
  statRanges: StatRange           // Record<StatKey, {min, max}>，必须覆盖全部属性
  weeklyEffects: Effect[]         // 每周结束时的固定衰减（日志文案是「每周固定衰减」）
  weeklyEventChance: number       // 0.7
}
```

`statRanges` 是 `Record<StatKey, ...>`，所以**加了属性却忘了加范围会直接编译报错**。这是刻意的类型设计（见 §4.1）。

## 4. DSL 完整参考

### 4.1 类型派生关系（单一真相源）

```ts
interface Stats { academic; social; health; mood; money; skill }  // ← 唯一真相源
type StatKey = keyof Stats                                        // → 'academic' | ...
type StatRange = Record<StatKey, { min; max }>                    // 必须覆盖全部键
```

**实测过**：往 `Stats` 加一个 `stress` 字段，`pnpm typecheck` 准确报出 3 处需要同步的地方：

```
src/data/config.ts(7,14):     Property 'stress' is missing in type 'StatRange'      ← STAT_RANGES
src/data/config.ts(16,14):    Property 'stress' is missing in type 'Stats'          ← INITIAL_STATS
src/engine/effects.ts(88,14): Property 'stress' is missing in type 'Record<keyof Stats, string>'  ← STAT_LABELS
```

（上表为可读性做了简化：真实输出是 `error TS2741: Property 'stress' is missing in type '{...}' but required in type 'StatRange'` 这种形式，**行号列号与原输出完全一致**。）

`types.ts` 自己不报错——因为 `StatKey` 和 `StatRange` 是**派生**的，自动跟着变。这就是「改一处，编译器列出所有同步点」。

### 4.2 `Condition` 参考（9 种分支）

| `type` | 字段 | 语义 | 示例 |
|---|---|---|---|
| `stat` | `key: StatKey` `op: CompareOp` `value: number` | 属性比较 | `{ type:'stat', key:'academic', op:'>=', value:85 }` |
| `flag` | `key: string` | flag 为真（`true` 或**非 0 数字**） | `{ type:'flag', key:'加入集训队' }` |
| `flagEq` | `key: string` `value: FlagValue` | flag 精确等于某值 | `{ type:'flagEq', key:'结局分支', value:1 }` |
| `flagAtLeast` | `key: string` `value: number` | 数值 flag ≥ 某值 | `{ type:'flagAtLeast', key:'穷困周数', value:4 }` |
| `week` | `op: CompareOp` `value: number` | 周数比较 | `{ type:'week', op:'>=', value:10 }` |
| `not` | `condition: Condition` | 取反 | `{ type:'not', condition:{...} }` |
| `all` | `conditions: Condition[]` | 全部满足。**空数组 = 恒真** | 兜底结局用它 |
| `any` | `conditions: Condition[]` | 任一满足。**空数组 = 恒假** | |
| `chance` | `probability: number` | 概率命中，**消耗一次随机数** | `{ type:'chance', probability:0.3 }` |

`CompareOp` = `'>=' | '<=' | '>' | '<' | '==' | '!='`

**求值语义细则**：

1. `condition === undefined` → **返回 `true`**。所以「不写 `requires`」=「总是触发」。这让所有调用方省掉了判空
2. `flag` 把**非 0 数字**也算作真。所以 `穷困周数: 3` 既可以用 `flag` 判断「至少穷困过一次」，也可以用 `flagAtLeast` 判断「≥4 次」
3. `flagAtLeast` 对不存在的 key 返回 `false`（不是 0），因为它要求 `typeof === 'number'`
4. `chance` **会消耗一次随机数**，所以它在条件树里的位置会影响后续所有随机结果（见 §5.4）

**内容中的实际使用情况**（诚实记录）：

| 已使用（5） | 从未使用（4） |
|---|---|
| `stat` `flag` `flagAtLeast` `week` `all` | `any` `not` `chance` `flagEq` |

未使用的 4 种**有单测覆盖**（`not`/`any`/`chance` 都测了），只是没有真实内容用它们。这是我们自己造的一笔技术债——见 [§9](#9-已知限制与技术债)。

### 4.3 `Effect` 参考（7 种分支）

| `type` | 字段 | 语义 |
|---|---|---|
| `stat` | `key: StatKey` `delta: number` | 属性增减，**自动 clamp 到 statRanges** |
| `setFlag` | `key: string` `value: FlagValue` | 设置 flag |
| `addFlag` | `key: string` `delta: number` | 数值 flag 累加（不存在则视为 0） |
| `log` | `text: string` | 往日志写一条 `system` 消息 |
| `if` | `requires: Condition` `effects: Effect[]` | 条件效果，**可嵌套** |
| `branch` | `options: { weight: number; effects: Effect[] }[]` | 概率分支，**必定且只命中一个** |
| `end` | `endingId: string` | 直接结束游戏并指定结局 |

**`branch` 的存在理由（重要）**：

❌ **错误写法**：
```ts
effects: [
  { type:'if', requires:{ type:'chance', probability:0.5 }, effects:[好结果] },
  { type:'if', requires:{ type:'not', condition:{ type:'chance', probability:0.5 } }, effects:[坏结果] },
]
```
这是**两次独立的 50% 抽取**！会有 25% 概率两个都不中（什么都不发生），25% 概率两个都中（好坏结果同时生效）。

✅ **正确写法**：
```ts
effects: [
  { type:'branch', options: [
    { weight: 5, effects: [好结果] },   // 5/(5+5) = 50%
    { weight: 5, effects: [坏结果] },
  ]},
]
```
一次加权抽取决定落在哪个区间，**必定且只命中一个**。

**内容中的实际使用情况**：

| 已使用（6） | 从未使用（1） |
|---|---|
| `stat` `setFlag` `addFlag` `log` `if`（在 `config.weeklyEffects`）`branch` | **`end`** |

`end` 是完整实现且类型安全的功能，但没有任何内容用它——意味着这条路径**没有被真实内容验证过**。

### 4.4 `describeEffects` 与「回执」的分工

```ts
describeEffects(action.effects)   // → "学业 +4 / 心情 -2 / 健康 -1"   ← 预告（声明值）
applyEffects(ctx, effects)        // → [{key:'academic',delta:4,capped:undefined}, ...]  ← 回执（实际值）
```

两者**故意不共用同一套逻辑**，因为它们回答的是不同问题：

| | `describeEffects` | `applyEffects` 的返回值 |
|---|---|---|
| 回答 | 「这个选项**说**它要做什么」 | 「**实际**发生了什么」 |
| 触顶时 | `学业 +4` | `学业 +2` + `capped:'max'` |
| `if` / `branch` | **所有**分支的并集（不准确） | 只算真正走到的分支 |
| 是否消耗随机数 | 否（纯读数据） | 是（`chance` / `branch` 会消耗） |
| 用途 | 行动菜单的灰色预告 | 结算彩色回执 |

**⚠️ 不要拿 `effects` 数组去推算回执。** 那会漏掉两件只有 `applyEffects` 才知道的事：
属性被 clamp 截断了多少、`if`/`branch` 里哪条分支真的走了。

**`describeEffects` 的已知局限**：对带 `branch` 的效果，它列出所有分支的属性**并集**，
语义上不准确（实际只会发生一个分支）。对行动够用（行动一般没有 `branch`），
但对带概率的事件选项会误导。

**改进方向**：让它接受一个「策略」——比如只列 `if` 里非概率的部分，
或对 `branch` 显示为「随机结果」而不是罗列全部。

## 5. 执行流程

### 5.1 相位状态机

引擎没有显式的 `phase` 字段，相位由 `pending` 和 `endingId` **推导**出来：

```
                    ┌─────────────────────────────┐
                    │  PLANNING（玩家选行动）       │
                    │  pending=null, endingId=null │
                    └──────────────┬──────────────┘
                       takeAction()│ 行动力 -1
                                   ▼
                    ┌─────────────────────────────┐
               no   │  行动力归零？                 │
                    └──────────────┬──────────────┘
                              yes  ▼
                    ┌─────────────────────────────┐
                    │  RESOLVING（结算本周）        │
                    │  weeklyEffects → 掷随机事件   │
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
             有选项 │  事件有 choices？             │
                    └──────┬───────────────┬──────┘
                      yes  │               │ no
                           ▼               ▼
              ┌────────────────────┐   ┌──────────────────┐
              │  AWAITING_CHOICE   │   │  maybeAdvance()  │
              │  pending=事件       │   └────────┬─────────┘
              └─────────┬──────────┘            │
                 choose()│                      │
                        └──────────────────────┤
                                               ▼
                              ┌─────────────────────────────┐
                              │  maybeAdvance()              │
                              │  pending? → 停               │
                              │  week≥16? → settleEnding()   │
                              │  否则 week+1, AP 重置         │
                              └─────────────────────────────┘
```

### 5.2 `takeAction` 时序

```ts
takeAction(actionId) {
  const from = this.state.log.length          // ① 记日志起点
  // ② 两道状态守卫（顺序重要：先检查最严重的情况）
  if (endingId !== null) throw '游戏已经结束了'
  if (pending !== null)  throw '还有未处理的事件，请先做出选择'
  // ③ 查表 + 校验
  action = data.actions.find(a => a.id === actionId)
  if (!action)                throw '未知行动'
  if (action.cost > AP)       throw '行动力不足'
  if (!evaluate(requires))    throw '行动条件不满足'
  // ④ 开始改状态（一旦开始就不再回滚，所以校验必须全部前置）
  AP -= action.cost
  entry = pushLog('action', ...)               // ★ 日志先写
  changes = applyEffects(action.effects)       // ★ 结算后才知道实际变化
  if (changes.length > 0) entry.changes = changes   // ★ 补挂回执
  // ⑤ 行动力耗尽则结算本周
  if (AP <= 0) endWeek()
  return buildResult(from)                    // ⑥ 只返回增量日志
}
```

**为什么是「先写日志、后补变化量」**：日志里的 `log` 效果（`{type:'log'}`）必须排在
行动这一行**之后**，叙事顺序才对。但变化量要等 `applyEffects` 跑完才知道。
所以 `pushLog` 被改成**返回刚写入的条目**，让调用方随后补上 `entry.changes`。
这是「先写后改」的典型取舍 —— 换来了正确的叙事顺序和正确的回执。

**为什么用 `slice(fromLogIndex)` 返回增量而不是全量日志**：UI 只想显示「刚刚发生了什么」。让它自己去 diff 上一份 `log` 很别扭，重印全程又很吵。

### 5.3 `maybeAdvance()` —— 时间推进的唯一闸门

```ts
private maybeAdvance(): void {
  if (this.pending !== null) return          // ① 有事件没处理 → 冻结时间
  if (this.state.endingId !== null) return   // ② 已结束 → 冻结时间
  if (this.state.week >= config.totalWeeks) {
    this.settleEnding()                      // ③ 学期结束 → 结算结局
    return
  }
  this.state.week += 1                       // ④ 正常推进
  this.state.actionPoints = config.actionPointsPerWeek
  pushLog('system', `—— 第 N 周开始 ——`)
}
```

**只有两个调用点**：`endWeek()` 末尾、`choose()` 末尾。

**为什么这样设计**：考虑「第 5 周行动力用完 → 触发一个 3 选项事件」的场景。

1. `endWeek()` 结算完本周、抽到事件、设好 `pending`，然后调 `maybeAdvance()`
2. `maybeAdvance()` 看到 `pending !== null`，**什么都不做就返回**
3. 所以 `week` 还是 5，玩家必须先处理事件
4. 玩家 `choose(1)` → `pending = null` → 再次 `maybeAdvance()` → 这次才 `week = 6`

**时间推进的逻辑只写了一遍，而且它自己知道什么时候不该推进。UI 完全不需要判断「现在能不能进下一周」。**

对比常见烂写法：把推进逻辑散在三四个地方、每处各加一句 `if (hasPending) return`。漏一处就会出现「事件没选完就跳周」的 bug，而且极难复现。

**注意第 ③ 分支的顺序**：结算结局在「推进周数」之前，所以第 16 周用完行动力时不会出现「第 17 周」。

### 5.4 ⚠️ 随机数调用顺序（**改引擎代码前必读**）

`rng` 是一个**有状态的随机流**。同一个 seed，只要**调用次数或顺序**变了，整局结果就全变。

当前一局游戏的随机数消耗序列（`weeklyEventChance = 0.7`）：

```
每周结束时（共 16 次）：
  ① rng()                          ← 判定本周有没有事件（0.7 概率）
  ② 若命中：条件求值中每个 chance 各消耗 1 次
  ③ 若命中：pickWeighted 里的 rng()  ← 抽取抽中哪个事件

事件选项结算中（可能）：
  ④ branch 效果里的 pickWeighted 的 rng()
  ⑤ if/chance 条件里的 rng()
```

**实践后果**：

| 操作 | 是否影响同种子复现 |
|---|---|
| 改 `src/data/` 里的内容（加事件、改权重） | ✅ **会影响**（事件池变了，`pickWeighted` 结果变） |
| 改引擎里 `rng()` 的调用位置/次数 | ✅ **会影响** |
| 改 UI / CLI 代码 | ❌ 不影响（UI 不碰 rng） |
| 改属性数值但不动随机调用 | ⚠️ 影响最终状态，但随机序列不变 |

**所以「用种子复现某一局」的前提是代码没改过。** 这不是 bug，是种子确定性系统的固有特性。要做真正的跨版本回放，需要事件溯源（记录每一步的输入）而不是只记种子。

> **一个正面案例**：加「结算回执」时，`endWeek` 里插入了 `pushLog('每周固定衰减')`
> 和一次返回值接收，但**没有插入任何 `rng()` 调用**，所以随机序列完全没变 ——
> 老种子的对局仍然可复现。改引擎时**刻意避开 rng 调用**是有意为之，
> 这和「随手加一行 `rng()` 就让所有老种子失效」是完全不同的代价。

## 6. 质量保障

### 6.1 测试策略

只有一个测试文件（`tests/engine.test.ts`，**27 个测试**），刻意如此。按目的分六组：

| 组 | 目的 | 例子 |
|---|---|---|
| **条件求值** | DSL 语义正确 | 「空 `all` 恒真、空 `any` 恒假」（兜底结局的基础） |
| **属性边界** | 不变量 I1 | 「连写 30 次代码，技能顶到 100 而不是无限增长」 |
| **引擎流程** | 不变量 I2–I6 | 「有待处理事件时不能继续行动」；「同种子必得同结局」 |
| **结算回执** | 不变量 I9 + 回执语义 | 「触顶时报告实际值并标 capped」；「报告值之和 == 真实变化」 |
| **防卡死** | 「有选项就一定有得选」 | 「每个带选项的事件至少有一个无条件选项」 |
| **内容数据合法性** | 防低级错误 + 守设计不变量 | 「id 唯一」「存在兜底结局」「**所有结局都能被玩出来**」 |

**最有价值的一条**是最后一个：

```ts
it('所有结局都能被玩出来（没有死结局）', () => {
  const report = simulate(120)   // 6 种风格 × 120 局 = 720 局
  expect(report.deadEndings.map(e => `${e.title}(${e.id})`)).toEqual([])
})
```

它把「每个结局都必须可达」这个**设计不变量**固化成了自动化测试。因为整个模拟是种子确定的，这条测试**不会 flaky**；反过来，一旦调数值导致某个结局变得不可达，它会立刻报警——这个项目就真的踩过一次（「情绪崩溃」3000 局 0 触发）。

### 6.2 为什么不为每个内容条目写「快照测试」

内容条目会频繁改动（调数值、改文案、加选项）。如果为每个事件写断言其具体效应的测试，**每次调平衡都要改一堆测试**，测试就从资产变成了负担。

正确的分工是：
- **结构性不变量**（id 唯一、必备字段非空）→ 单元测试
- **数值正确性** → `pnpm simulate` 的统计分布，靠人判断形状
- **可达性** → 那条 720 局的测试

### 6.3 `pnpm preflight`：推送前自检

```powershell
pnpm preflight                  # 全量
pnpm preflight -- -SkipTests    # 只想查网络
```

检查 **12 项**，分五组：

| 组 | 检查项 |
|---|---|
| 工具链 | node / pnpm / git 版本 |
| 代码健康 | typecheck、单元测试 |
| **架构边界** | ① engine 层无 DOM / 框架 / Node IO 依赖（ADR-001）② 依赖方向单向（engine 不认识 data / cli）③ BOM 合规 |
| GitHub 连接 | remote 协议、SSH 认证（计时） |
| 工作区状态 | 未提交改动、未推送提交 |

**加它的实际原因**：这台机器到 `github.com:443` 是**间歇性阻断**的。以前推一次代码可能失败好几次才发现是网络问题。先跑一次自检就能立刻区分「网络不通」和「代码有问题」。

**「架构边界」那一组的意义**：把文档里的规则变成机器执行的检查。只写在文档里的架构约束迟早会被人忘掉（或「就这一次」地破坏），跑一次 `preflight` 就能拦下。

**实现注意**（改这个脚本时别踩）：

1. `ssh -T git@github.com` 认证**成功时退出码是 1**（GitHub 的约定），所以只能靠输出文字里的 `Hi <user>!` 判断，**不能看 exit code**
2. 脚本里有中文，**必须存成带 BOM 的 UTF-8**，否则 Windows PowerShell 5.1 按 GBK 解码 → 全乱码（见 [§8.1](#81-编码--bom-规则最重要的一条)）。**注意 `edit` 工具会去掉 BOM，改完必须补回**
3. npm script 名不能叫 `doctor`——**会被 pnpm 内置的 `doctor` 命令遮蔽**，`pnpm doctor` 跑的不是你的脚本
4. ⚠️ **检查架构边界时不要直接搜单词**。第一版用 `'node:|document|window|react'` 正则扫 `src/engine/*.ts`，结果把 `state.ts` 里一句中文注释「等以后接 React 时」误判成了违规。正确做法是只匹配**模块说明符**（`from 'node:...'`）和 **DOM 属性访问**（`document.` / `window.`）。
   这类检查**必须做反向验证**：故意注入一个 `import ... from 'node:fs'`，确认它真的能被抓到，否则你只是在检查一个永远返回 OK 的脚本

### 6.4 目前**没有**的东西

| 缺失 | 影响 | 何时补 |
|---|---|---|
| CI（GitHub Actions） | 推送不会自动跑测试 | 阶段 4 |
| 覆盖率统计 | 不知道哪块没测到 | 可选 |
| E2E 测试 | CLI 的交互流程靠人工冒烟 | 阶段 3 引入 UItest 时 |
| 存档兼容性测试 | 存档还没做 | 阶段 2 |
| 性能测试 | 当前规模完全不需要 | 规模上来再说 |

### 配方 1：加一个事件 ⭐ 最常用

**改动文件**：`src/data/events.ts`（只需这一个）

```ts
{
  id: 'ev_your_event',                 // 必须唯一，用 ev_ 前缀
```

**检查清单**：
- [ ] 每个选项都有代价？（如果一个选项严格优于其他，这个事件没有存在意义）

### 配方 3：加一个结局

### 配方 6：加一个效果类型

**改动文件**：`src/engine/types.ts` + `src/engine/effects.ts`

1. 往 `Effect` 联合加分支
2. 往 `applyEffect` 的 `switch` 加 case

⚠️ **`applyEffect` 的 `switch` 是 `void` 返回**，所以 TS **不会**帮你检查漏了 case！
这是与 `evaluate` 不同的地方。保护措施：

```ts
// 在 applyEffect 的 switch 之后加一个穷尽性断言
default: {
  const never: never = effect
  throw new Error(`未处理的 effect 类型: ${JSON.stringify(never)}`)
}
```

这样加了新分支而忘了处理时，`const never: never = effect` 会编译报错。

3. 如果新效果会**产生属性变化**，有两个地方要一起考虑：
   - `describeEffects`（**预告**：菜单里显示「这个选项说它做什么」）
   - `applyEffects` 里的 `recordChange`（**回执**：结算时显示「实际发生了什么」）

   ⚠️ **只做前者会漏掉回执**。最典型的是 `stat` 之外的隐含属性效果，
   或者需要按分支/条件决定数值的效果 —— 它们必须走 `recordChange` 记录，
   否则 I9（报告之和 == 真实变化）会失败。**跑 `pnpm test` 会立刻抓到。**

4. 如果新效果会**消耗随机数**，一定要在 [§5.4](#54-️-随机数调用顺序改引擎代码前必读) 里更新记录，并接受「旧种子失效」

### 配方 6b：新增一条「结算回执」日志

**改动文件**：`src/engine/engine.ts`（通常不用改 `effects.ts`）

当你要在某个流程节点显示「这一步改了什么」时：

```ts
// ① 先写日志（这样效果里的 log 效果会排在它后面，叙事顺序才对）
const entry = pushLog(this.state, 'system', '这一步的说明文字')

// ② 结算，拿到**实际**变化量
const changes = applyEffects(this.createContext(), someEffects)

// ③ 补挂回执（无变化时不挂，保持字段可选）
if (changes.length > 0) entry.changes = changes
```

**三条硬要求**：

1. **顺序不能反**。先 `pushLog` 再 `applyEffects`，否则 `{type:'log'}` 效果的文本会跑到这行前面
2. **不要新增 `rng()` 调用**。这会让所有老种子失效（见 §5.4）
3. **写测试**。至少断言这条日志存在且 `changes` 非空；更强的是让 I9 覆盖它

现有的四个挂载点可以直接抄：`takeAction`（行动）、`choose`（玩家选项）、
`triggerEvent`（无选项事件的自动效果）、`endWeek`（每周固定衰减）。

### 配方 7：实现存档 / 读档

**这是阶段 2 的任务，有一个前置难题必须先解决。** 完整设计见 [§10](#10-存档格式设计rfc)。简要步骤：

1. 先决定 RNG 策略（三种方案见 §10.2），推荐**方案 B：暴露 RNG 状态**
2. 新建 `src/save/`，与引擎平级（**不要放进 engine**，引擎不做 IO）
3. 定义 `SaveFile` 接口（含 `version`）
4. 写迁移注册表 `MIGRATIONS: Record<number, (data) => data>`
5. 写 `tests/save.test.ts`，重点测：**存档 → 读档 → 继续玩，结果必须与不中断完全一致**
6. CLI 加 `--save` / `--load` 参数验证

### 配方 8：加 Web 界面（React）

**新增目录**：`src/web/`

**工作方式**：

```tsx
// 伪代码：UI 只是一个状态机渲染器
const engineRef = useRef(new GameEngine(GAME_DATA))
const [state, setState] = useState(engineRef.current.getState())

function handleAction(id: string) {
  engineRef.current.takeAction(id)         // 引擎内部状态已更新
  setState(engineRef.current.getState())   // 拉一份快照触发重渲染
}
```

**关键点**：

1. **永远不要修改 `engine.getState()` 返回的对象**。它每次都是新的深拷贝，但 React 的渲染语义要求「状态不变就不重渲染」——所以正确做法是**每次操作后重新 `getState()`**，靠新对象引用触发渲染
2. **不要 import `evaluate` / `applyEffects`**。UI 只用 §2.2 里列出的稳定 API
3. `getPendingChoices()` 给的 `enabled` 直接用来控制按钮 disabled 状态
4. **引擎代码一行都不要改**——如果需要改引擎才能做 UI，说明分层设计出了问题

**顺带**：Vite 的 `lib`/`app` 配置、路由、部署，都不影响 `src/engine/`。

## 8. 约定与规约

### 8.1 编码 & BOM 规则（**最重要的一条**）

这是本项目踩过最严重的坑——**静默数据损坏**，而且已经推到过 GitHub 一次。

**规则**：

| 文件类型 | BOM | 字符集 | 原因 |
|---|---|---|---|
| `.ps1`（含中文） | **必须有 BOM** | UTF-8 | Windows PowerShell 5.1 读无 BOM 的 UTF-8 会按 GBK 解码 → 乱码 |
| `.ts` `.json` `.md` `.npmrc` `.gitignore` `.yaml` | **必须无 BOM** | UTF-8，配置文件尽量纯 ASCII | `JSON.parse` / pnpm 遇到 BOM 直接报错 |

**⚠️ 绝对不要用 PowerShell 的 `Get-Content` / `Set-Content` 往返处理 UTF-8 文件**：

```powershell
# ☠️ 危险！这一行会同时造成两种不可逆损坏
(Get-Content package.json -Raw) -replace 'a','b' | Set-Content package.json -Encoding UTF8
```

- `Get-Content` 在 PS 5.1 里**默认按系统 ANSI 码页读取**（简中是 GBK）→ UTF-8 中文被误解码成乱码
- `Set-Content -Encoding UTF8` 把乱码以 UTF-8 写回 → **损坏不可逆**
- 而且 `-Encoding UTF8` 会**额外写入 BOM** → `JSON.parse` 抛 `Unexpected token ''`，pnpm 报 `control character found while parsing`

**正确做法**：

```powershell
# A. 需要精确控制字节/BOM 时，用 .NET（$false = 不写 BOM）
$t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding $false))

# B. 只改文本内容时，用编辑器，别让 shell 参与
```

**全仓库 BOM 自检**（正常输出应该**只有 `preflight.ps1`**）：

```powershell
Get-ChildItem -Recurse -File | Where-Object { $_.FullName -notmatch 'node_modules|\\\.git\\' } | ForEach-Object {
  $b = [System.IO.File]::ReadAllBytes($_.FullName)
  if ($b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF) { $_.Name }
}
```

## 9. 已知限制与技术债

诚实记录，避免以后重复踩或误以为是 bug。

### 9.1 ⚠️ RNG 状态不可序列化（**阻塞存档功能**）

```ts
export function mulberry32(seed: number): RNG {
  let a = seed >>> 0            // ← 闭包私有变量
  return function next() {
    a = (a + 0x6d2b79f5) >>> 0  // ← 只在这里被读写
    ...
  }
}
```

**问题**：`a` 是闭包内部状态，**外部既读不到也写不回**。所以：

```
存档 → 读档 → 用同一个 seed 重建引擎
                              ↓
              随机流会从「序列开头」重新开始
              而不是从「存档那一刻的位置」继续
                              ↓
              继续玩下去的结果 ≠ 不中断的结果
```

**唯一能存的东西是 `seed`，不是「当前随机流位置」。** 这直接影响阶段 2 的「存档 → 读档 → 继续玩结果一致」这条验收标准。三个解决方案见 [§10.2](#102-核心难题rng-状态不可序列化)。

### 9.2 `describeEffects` 对 `branch` 显示不准确

罗列了所有分支的属性并集，但实际只会命中一个。对行动无影响（行动没有 `branch`），
对带概率的事件选项会误导玩家。

**注意这个局限只影响「预告」，不影响「回执」** —— 回执走的是 `applyEffects` 的返回值，
只算真正走到的分支（见 [§4.4](#44-describeeffects-与回执的分工)）。
所以最坏情况是菜单里的预告偏乐观，但结算数字永远是真的。

### 9.3 `compare` 的 `default` 削弱了穷尽性检查

```ts
function compare(a, op, b) {
  switch (op) {
    // ...6 个 case
    default: return false       // ← 这里
  }
}
```

如果以后往 `CompareOp` 加了 `'startsWith'`，编译器**不会报错**，新算子会静默地永远返回 `false`。严格做法是删掉 `default` 并声明返回类型，让 TS 保证穷尽。

### 9.4 有 4 种条件 + 1 种效果从未被内容使用

| DSL | 已实现 | 内容中使用 | 未被使用 |
|---|---|---|---|
| Condition | 9 种 | 5 种 | `any` `not` `chance` `flagEq` |
| Effect | 7 种 | 6 种 | **`end`** |

其中 `not` / `any` / `chance` 有单测覆盖，`flagEq` 和 `end` 连测试都没有。**这意味着这些代码路径没有被真实内容验证过**——`simulate` 跑 3000 局也覆盖不到。

**好消息**：这些分支都是**完备且类型安全**的，只是没被用过。稳妥的做法是删掉没人用的分支；但考虑到它们都合理且以后大概率会用，暂时保留，**阶段 1 用真实内容把它们跑起来**。

### 9.5 事件量不足导致重复感

17 个事件，而一局要经历约 11 次事件触发。在 `repeatable` 只有 4 个的情况下，**连玩两局会明显重复**。这是当前可玩性最大的短板。

### 9.6 `getState()` 每次深拷贝

`getState()` 用 `structuredClone` 深拷贝整个状态。当前状态只有几十个字段，**完全无所谓**（720 局模拟含大量 `getState` 调用，加起来也才几百毫秒）。

如果状态涨到几千个字段（比如记录完整历史事件流），需要改成不可变数据结构 + 结构共享。**原则：先正确，再快。**

### 9.7 没有 CI

推送不会自动跑测试。目前靠 `pnpm preflight` 手动执行。阶段 4 补 GitHub Actions。

### 9.8 「主线」只是 flag 暗线，不是系统

`EventCategory` 只有 `'random'` 一个值。所谓社团/求职/学业三条线，实际是靠 flag 隐式串联，**没有独立的抽取池和推进节奏**。真做主线需要给 `EventCategory` 加值 + 引擎按类别独立抽取。

### 9.9 有两个 flag 是「只写不读」的死 flag

| flag | 谁写 | 谁读 | 状态 |
|---|---|---|---|
| `投递次数` | 「投简历」行动累加（`actions.ts`） | **无人读取** | 死 flag |
| `被预警` | `ev_academic_warning` 设置（`events.ts`） | **无人读取** | 死 flag |

它们目前纯粹是"记了个账"——既不参与结局判定，也不影响任何事件触发。这不影响正确性，但意味着**玩家永远看不到这两个 flag 的存在**。

两个选择：
- **用起来**：让结局或事件读它们（例如「被预警」且最终学业仍不达标 → 一个专门的劝退结局）
- **删掉**：如果确定不需要，就删掉，避免留下「看起来有意义其实没有」的数据

> 这类问题很难靠人肉发现——建议在阶段 1 加一条自检：**扫描 `src/data/` 里所有出现的 flag 名（写入侧）与所有 `flag`/`flagEq`/`flagAtLeast` 的 key（读取侧），报告只写不读的差集。** 这和「死结局」检查是同一个思路。

## 10. 存档格式设计（RFC）

阶段 2 的设计草案，**写代码前先定这个**。

### 10.1 存档结构

```ts
interface SaveFile {
  /** 存档格式版本，与游戏内容版本解耦。迁移逻辑的唯一依据 */
  formatVersion: number
  /** 生成这个存档时的游戏版本，只用于诊断 */
  gameVersion: string
  /** ISO 8601 时间戳 */
  savedAt: string
  /** 玩家看到的存档名 */
  label?: string
  /** 随机种子（用于「重开同一局」和 UI 显示） */
  seed: number
  /** RNG 的当前状态 —— 见 10.2 */
  rngState: number
  /** 引擎状态 */
  state: GameState
  /** 已解锁的结局 id，用于「还有几个结局没解锁」提示 */
  unlockedEndings?: string[]
}
```

**为什么 `formatVersion` 与 `gameVersion` 分开**：游戏加内容（新事件/结局）不需要改存档格式，此时 `gameVersion` 变而 `formatVersion` 不变——**旧存档必须能直接读**。只有 `GameState` 的结构本身变了才升 `formatVersion`。

### 10.2 核心难题：RNG 状态不可序列化

| 方案 | 做法 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|---|
| **A. 只存 seed** | 读档后用 seed 重建 RNG | 零改动 | 读档后随机流从**开头**重放 → 结果与不中断**不一致**；且会重复触发已经历过的事件分支 | ❌ 不满足验收标准 |
| **B. 暴露 RNG 状态** | 让 `mulberry32` 支持导出/导入内部 `a` | 忠实恢复；改动很小；结果完全一致 | 需要改 `rng.ts` 的 API | ✅ **推荐** |
| **C. 事件溯源** | 存档只记 seed + 玩家的每一步输入，读档时从头重放 | 天然支持回放/录制；不需要序列化 RNG | 读档要重放全部历史（当前规模 48 步 + ~11 事件，微不足道）；存档含完整操作日志 | ✅ 也很好，且额外获得回放能力 |

**方案 B 的具体做法**：

```ts
// 改造后：RNG 是一个带显式状态的对象，而不是纯闭包
export interface Rng {
  next(): number
  getState(): number      // 导出内部 a
  setState(s: number): void  // 导入内部 a
}

export function createRng(seed: number, state?: number): Rng {
  let a = (state ?? seed) >>> 0
  return {
    next() { /* ...原逻辑... */ },
    getState: () => a,
    setState(s) { a = s >>> 0 },
  }
}
```

**注意这个改动会触及 ADR-002**：`RNG` 类型从 `() => number` 变成带方法的对象，所有传 `rng` 的地方（`conditions.ts` 的 `chance`、`effects.ts` 的 `branch`、`engine.ts`）都要从 `ctx.rng()` 改成 `ctx.rng.next()`。改动面不大但很分散——**所以要在阶段 2 一开始就做，不要等到写了别的功能再回头改**。

**推荐组合**：**方案 B 为主**（满足验收标准）+ 把「玩家操作序列」也存进 `SaveFile` 作为可选字段（这样以后能顺便做「回放这一局」，即方案 C 的能力）。

### 10.3 迁移机制

```ts
/** key = 从哪个版本升级；value = 把该版本的数据升到下一版 */
const MIGRATIONS: Record<number, (data: any) => any> = {
  // 例：v1 → v2 时 stats 里新增了 stress 字段
  1: (d) => ({ ...d, formatVersion: 2, state: { ...d.state, stats: { ...d.state.stats, stress: 50 } } }),
}

function migrate(save: any): SaveFile {
  let data = save
  while (data.formatVersion < CURRENT_FORMAT_VERSION) {
    const step = MIGRATIONS[data.formatVersion]
    if (!step) throw new Error(`缺少 v${data.formatVersion} 的迁移逻辑，无法读取此存档`)
    data = step(data)
  }
  return data as SaveFile
}
```

**要求**：
- 迁移函数必须是**纯函数**（不改入参）
- 每一次 `formatVersion` 递增都**必须**配一个迁移函数，否则旧存档永久丢失
- 迁移失败要给**明确错误**（告诉玩家存档太旧），不允许静默损坏

### 10.4 数据校验

读档时必须校验，不能直接信任文件内容（用户可能手改过、文件可能损坏）：

```ts
function validate(save: unknown): save is SaveFile {
  // 用 zod 之类的库，或者手写检查
  // 关键：检查 stats 的每个字段都是有限数字、week 在范围内、flags 只含 FlagValue
}
```

**要求**：校验失败的存档**不能导致游戏崩溃**，而是给出可读的错误并让玩家选择「开新档」。

## 11. 变更影响矩阵

「我想改 X，会连带影响什么？」

| 改动 | 需同步修改 | 会破坏同种子复现吗 | 必须跑的验证 |
|---|---|---|---|
| 加/改一个事件 | 无 | ✅ 会影响 | `pnpm simulate`（看死结局 & 分布） |
| 改事件权重 | 无 | ✅ 会影响 | `pnpm simulate` |
| 加/改行动 | `simulate.ts` 的 `STRATEGIES` | ✅ 会影响 | `pnpm simulate -- --games 500`（看平衡是否被稀释） |
| 加/改结局 | 无 | ❌ 不影响 | `pnpm test`（可达性测试会检验新结局） |
| 改 `priority` | 无 | ❌ | `pnpm test` + `simulate`（检查是否饿死了别的结局） |
| 加属性 | `types.ts` → 编译器指引 3 处 + `STAT_ORDER` ×2 + 配套行动/事件 + 可选衰减 | ⚠️ 若动了随机调用则影响 | `pnpm typecheck` `pnpm test` `pnpm simulate` |
| 改属性衰减 | 无 | ❌ | `pnpm simulate`（分布形状会大变） |
| 加条件类型 | `types.ts` + `conditions.ts` + 测试 + 真实内容 | ⚠️ 若内容里用 `chance` 则影响 | `pnpm typecheck`（TS 会抓漏掉的 case） |
| 加效果类型 | `types.ts` + `effects.ts` + **手动加穷尽断言** + 测试 | ⚠️ 若消耗随机数则影响 | `pnpm typecheck`（注意：`applyEffect` 是 `void` 返回，TS **不会**自动检查漏 case） |
| 改 `rng.ts` 调用位置 | 更新 §5.4 的记录 | ✅ **必然破坏** | `pnpm test`（可复现性测试会失败——这是**预期**的） |

## 12. 性能与规模

当前规模与实测数据：

| 指标 | 数值 |
|---|---|
| 单局行动数 | 48 |
| 单局事件触发数 | ~11 |
| 27 个单元测试 + 720 局可达性模拟 | **~450ms** |
| 1800 局平衡模拟（6 风格 × 300） | 1 秒内 |
| `pnpm test` 总耗时 | ~0.9s |

**结论：当前规模下性能完全不是问题，不要提前优化。**

需要开始关注性能的信号（按优先级）：

1. 单局超过 500 次行动
2. `GameState` 里开始存完整历史事件流（而不是只存 `log`）
3. Web 界面里 `getState()` 每帧调用
4. 事件池超过 1000 条（`filter` 是 O(n)。注意次数：`rollWeeklyEvent` 每局调 **16 次**，但 `filter` 在 0.7 的判定命中后才执行，实际约 **11 次/局**）

`rollWeeklyEvent` 的 `filter` 是当前唯一的 O(n) 热路径。如果事件涨到几千条，可以预建「按 `week` 分桶」的索引。**在那之前不要动它。**
