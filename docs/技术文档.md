## 1. 架构总览

### 1.1 分层与依赖方向

依赖是**严格单向**的，不允许反向引用。**界面是两个平行的层**，都只依赖 `data/`：

```
┌──────────────────────────────┐  ┌──────────────────────────────┐
│  src/cli/   界面层 A（命令行）│  │  src/web/  界面层 B（浏览器） │
│    play.ts      交互式试玩    │  │    main.tsx    React 入口     │
│    simulate.ts  数值平衡模拟  │  │    useEngine   引擎适配层      │
│    audit.ts     静态内容审计  │  │    App.tsx     页面骨架        │
│    text.ts      终端排版      │  │    styles.css  样式            │
│                              │  │    components/ 8 个组件        │
└──────────────┬───────────────┘  └───────────────┬──────────────┘
               │ 依赖                             │ 依赖
┌──────────────▼──────────────────────────────────▼──────────────┐
│  src/data/         内容层（纯数据，无逻辑）                      │
│    config.ts       数值配置（含基准属性）                        │
│    majors.ts       专业表（身份文案 + 属性偏移）                 │
│    actions.ts      行动表（共享 + 计算机专属）                   │
│    events.ts       事件库  ← 90% 的内容工作在这里                │
│    literature.ts   汉语言文学专业的完整内容包                    │
│    projects.ts     计算机专业的项目 / 作品                       │
│    endings.ts      结局表                                      │
│    index.ts        汇总成 GAME_DATA 注入给引擎                   │
└──────────────────────┬─────────────────────────────────────────┘
                       │ 依赖
┌──────────────────────▼─────────────────────────────────────────┐
│  src/engine/       引擎层（纯 TypeScript，零 DOM）              │
│    types.ts        全部类型定义（唯一协作契约）                  │
│    rng.ts          种子随机数                                  │
│    conditions.ts   条件求值                                    │
│    effects.ts      效果应用                                    │
│    state.ts        状态创建 / 日志 / 深拷贝                     │
│    majors.ts       专业维度的通用处理（引擎不认识具体专业）      │
│    engine.ts       流程编排（GameEngine 类）                    │
│    index.ts        统一出口（re-export）                       │
└────────────────────────────────────────────────────────────────┘
```

**两个界面层谁都不认识谁**，但共用同一个引擎。这不是设计意图层面的漂亮话，
而是被真实检验过的：加 Web 界面时，`src/engine/` 的改动是 **0 行逻辑**
（只加了一个 `STAT_ORDER` 常量，那是消除「三处各写一份属性顺序」的重构）。

**关键约束**（已自动化，见 [§6.3](#63-pnpm-preflight推送前自检)）：

```powershell
pnpm preflight -- -SkipTests
# 其中「架构边界」一节会检查：engine 层无 DOM/框架/Node IO 依赖
# + 依赖方向单向（engine 不得引用 data / cli / web）+ BOM 合规
```

引擎的 import 只允许来自 `./xxx`（自己的同级模块）。这是 ADR-001 的落地检查方式，
而且**规则已经被写进 `preflight` 自动执行**——只写在文档里的规则迟早会失效。

## 2. 模块职责与公开 API

### 2.1 各模块职责速查

| 文件 | 职责 | 依赖谁 | 导出 |
|---|---|---|---|
| `types.ts` | 只有类型定义，**运行时零代码** | 无 | 全部类型 |
| `rng.ts` | 种子随机数、加权抽取 | `types` | `mulberry32` `randomSeed` `pickWeighted` `pickOne` |
| `conditions.ts` | 条件树求值 | `types` | `evaluate` |
| `state.ts` | 建初始状态、写日志、深拷贝 | `types` | `createInitialState` `pushLog` `cloneState` |
| `majors.ts` | **专业维度**：内容归属判断、专业解析、基准属性 + 偏移并夹进合法区间 | `types` | `matchesMajor` `resolveMajor` `applyStatBonus` |
| `effects.ts` | 效果树应用、生成数值摘要、**产出结算回执** | `conditions` `rng` `state` `types` | `applyEffects` `describeEffects` `STAT_LABELS` |
| `engine.ts` | 流程编排 | 以上全部 | `GameEngine` `NewGameOptions` `ChoiceView` |
| `index.ts` | 统一出口 | 以上全部 | re-export 全部 |
| `../cli/text.ts` | 终端排版（cli 层唯一不依赖引擎的工具） | `node:process` | `displayWidth` `padEndWidth` `padStartWidth` `detectColorSupport` `createColors` |
| `../cli/audit.ts` | **静态内容审计**：死 flag（写了没人读 / 读了没人写），按专业作用域 | `data` `simulate`（只取内容切片） | `auditFlags` `auditFlagsOf` `flagUsageOf` |
| `../web/useEngine.ts` | **引擎与 React 的适配层**（Web 层唯一认识引擎的地方） | `react` `data` `engine` | `useEngine` |
| `../web/components/*.tsx` | 展示组件（纯函数，无状态） | `react` `engine`（`describeEffects` / `STAT_LABELS`） | 各组件 |

**Web 层的四条约定**（照配方 8 做的时候别违反）：

1. **`useEngine.ts` 是唯一允许 import `GameEngine` 的前端文件**。组件只能拿到数据，不能碰引擎实例
2. 组件**不自己判断规则**：选项能不能点是引擎给的（`getPendingChoices().enabled`），
   行动可不可用是引擎过滤好的（`availableActions()`）
3. 组件**不自己推算数值**：回执直接读 `LogEntry.changes`，绝不读 `effects` 数组去算
4. 每次操作后**重新取快照**（`engine.getState()` 返回深拷贝），靠新对象引用触发渲染 ——
   所以**不需要任何状态管理库**

**两处容易忽略的签名**（改代码前注意）：

```ts
// state.ts —— 返回刚写入的日志条目，让调用方能补挂 changes
export function pushLog(state, kind, text): LogEntry

// effects.ts —— 返回实际造成的属性变化（不是 void）
export function applyEffects(ctx, effects): StatChange[]
```

`applyEffects` 从 `void` 改成返回数组是**向后兼容**的：现有调用方忽略返回值即可，
所以这个改动没有波及 `engine.ts` 以外的任何调用点（`cli` / 测试 / 模拟器都不直接调它）。

`types.ts` 零运行时依赖这一点很重要：它保证 `import type` 之后不会产生任何 JS 代码，所以内容层可以自由地只依赖类型。

### 2.2 `GameEngine` 完整 API

#### 构造

```ts
new GameEngine(data: GameData, options?: NewGameOptions): GameEngine
```

| 参数 | 类型 | 说明 |
|---|---|---|
| `data` | `GameData` | 一整套内容，通常传 `GAME_DATA` |
| `options.seed` | `number?` | 不传则用 `randomSeed()` 随机。传了就完全可复现 |
| `options.majorId` | `string?` | 专业 id。不传 = `data.majors` 里的第一个。传了未知 id 会**抛错**（不静默回退） |

#### 只读查询（**稳定契约**，UI 只应使用这些）

| 方法 | 返回 | 说明 |
|---|---|---|
| `getSeed()` | `number` | 本局种子，应该显示给玩家（可复现的前提） |
| `getState()` | `GameState` | **深拷贝**的状态快照。外部改它不影响引擎 |
| `getConfig()` | `GameConfig` | 数值配置 |
| `getMajor()` | `MajorDef` | 本局专业定义（含 `name` / `identity`），供界面显示 |
| `getPending()` | `GameEvent \| null` | 正在等待玩家选择的事件 |
| `getPendingChoices()` | `ChoiceView[]` | 待选事件的选项 + 每个选项**是否可用** |
| `isEnded()` | `boolean` | 是否已结算结局 |
| `getEnding()` | `Ending \| null` | 结局对象（含 `title` / `text`） |
| `getSummary()` | `RunSummary` | **学期结算回顾**：把这一局做过的事翻译成叙述（见 §2.4） |
| `availableActions()` | `ActionDef[]` | 当前可执行的行动（已按**专业 / 行动力 / 条件**过滤） |
| `getProjects()` | `ProjectView[]` | 本专业可见的项目（**含未解锁与已完成的**），带进度 |

`getProjects()` 刻意不把未解锁 / 已完成的过滤掉：界面需要显示「未解锁」和「进度 2/3」
这类信息，直接滤掉就什么都展示不了。能不能投入由 `investProject` 负责挡。

`ChoiceView` 的定义：

```ts
interface ChoiceView {
  choice: Choice      // 选项数据（label、effects）
  enabled: boolean    // false → UI 应该把按钮灰掉
}
```

`ProjectView` 的定义：

```ts
interface ProjectView {
  project: ProjectDef   // 项目定义（名称、描述、每次投入的效果……）
  progress: number      // 已投入次数
  required: number      // 需要投入几次
  completed: boolean
  unlocked: boolean     // 解锁条件是否满足；false → UI 应该置灰
}
```

> **设计意图**：`getPendingChoices()` 把「判断」留在了引擎里。UI **不需要** import `evaluate`、不需要构造 `EvalContext`、不需要知道条件 DSL。条件系统改版时，UI 一行都不用动。`getProjects()` 同理 —— UI 拿到的已经是算好的进度与解锁状态。

#### 推进游戏（**稳定契约**）

| 方法 | 返回 | 会抛错的时机 |
|---|---|---|
| `takeAction(actionId: string)` | `TurnResult` | 已结束 / 有待处理事件 / 未知行动 / **行动不属于本专业** / 行动力不足 / 条件不满足 |
| `investProject(projectId: string)` | `TurnResult` | 已结束 / 有待处理事件 / 未知项目 / **项目不属于本专业** / 行动力不足 / **项目已完成** / 条件不满足 |
| `choose(choiceIndex: number)` | `TurnResult` | 没有待处理事件 / 序号无效 / 该选项条件不满足 |

`investProject` 的语义刻意与 `takeAction` 对齐：同样的守卫顺序、同样「先写日志、后补变化量」、
同样在行动力归零时结算本周。所以「做项目」和「做行动」在引擎里是同一种东西。

**抛异常是刻意的设计**（fail fast）：调用方本就应该先用 `availableActions()`、
`getProjects()` 和 `getPendingChoices()` 过滤掉非法操作。抛错代表**调用方写错了**，
而不是「可预期的失败」。

> 这个约定在写测试时咬过我一次：测试里图省事写 `engine.choose(0)`，结果 0 号选项是「换主板（需要 1200 元）」条件不满足 → 直接抛错。**这个抛错是正确的**，它暴露了测试没按 `enabled` 过滤，而不是引擎有问题。

`TurnResult` 的定义：

```ts
interface TurnResult {
  logs: LogEntry[]          // 只包含本次操作新产生的日志（增量，不是全量）
  pending: GameEvent | null // 需要玩家做选择的事件
  ended: boolean
}
```

#### 内部实现（**非契约**，可自由重构）

`private` 成员：`createContext` `endWeek` `rollWeeklyEvent` `triggerEvent` `maybeAdvance` `settleEnding` `buildResult` `projectProgress`

这五个字段是 `private readonly`：`data` `state` `rng` `seed` `major`，另有可变的 `pending`。

> ⚠️ **TS 的 `private` 编译后完全消失**，运行时照样能访问。想真正私有得用 `#field`。这里用编译期 `private` 足够了。

### 2.3 什么算「稳定契约」

改动前请对照：

| 层级 | 内容 | 变更自由度 |
|---|---|---|
| **稳定契约** | `GameEngine` 的公开方法签名、`GameState` 字段、`LogEntry` 字段、`GameData` 结构、DSL 分支语义 | 改动 = **破坏性变更**，必须同步更新文档、测试、所有调用方 |
| **可加不可减** | 给已有接口**新增可选字段**（如 `LogEntry.changes?`、`ActionDef.majors?`） | 非破坏性，但需同步文档 |
| **内部实现** | `private` 方法、模块内部辅助函数 | 自由重构 |
| **内容** | `src/data/` 里的每一条数据 | 随时可加可改，不影响任何代码 |

> 本项目的几次实际变更可以对照上面这张表：
> `LogEntry` 新增可选字段 `changes` → 「可加不可减」；`applyEffects` 返回值从 `void` 变成数组
> → 因为原有调用方都忽略返回值，也算非破坏性。
> 两者都**需要同步文档**，但都不需要改调用方。
>
> 而给 `GameData` 加**必填**的 `summary` 字段（结算回顾）是**破坏性变更**。
> 之所以敢这么改：`GameData` 全项目只有一个实现（`GAME_DATA`），
> 而必填能保证「忘了写回顾规则」在编译期就暴露，而不是上线后玩家看到一页空白。
>
> 阶段 2 的几处改动同样按这张表走：
> - `GameState` 新增 `majorId`、`ActionDef` / `GameEvent` / `Ending` / `SummaryRule`
>   各加可选的 `majors?` → **破坏性/可加**，已同步文档与测试
> - `NewGameOptions` 新增可选 `majorId`、新增公开方法 `getMajor` / `getProjects` / `investProject`
>   → **可加不可减**（不传 `majorId` 就是第一个专业，老调用方行为完全不变）
> - `GameData` 新增**必填**的 `projects` → 破坏性，理由与 `summary` 相同：
>   唯一实现是 `GAME_DATA`，必填能让「忘了写项目」在编译期暴露

### 2.4 结算回顾（`getSummary()`）

学期结束时给玩家的「这学期你做了什么」——而不是只丢一个结局标题过去。

```ts
interface RunSummary {
  identity: string       // 「计算机专业大三学生」/「汉语言文学专业大三学生」
  lines: SummaryLine[]   // 叙述要点，已按 order 排好序
  stats: Stats           // 终局属性
  endingTitle: string
  verdict: string        // 一句话总评
  seed: number
}
```

**`identity` 现在来自专业数据**（`MajorDef.identity`），不在回顾内容里。
`SummaryContent` 特意**没有** `identity` 字段：如果身份留在这里，改专业就会出现
「专业换了、结算页还写着旧身份」的二源问题。

**规则是纯数据**（`src/data/summary.ts`），形态就是一条条「条件满足 → 产出一句话」：

```ts
{
  requires: { type: 'flag', key: '加入集训队' },
  kind: 'club',
  order: 10,
  text: '加入了 ACM 集训队，把自己泡在算法题里',
}
```

引擎的职责只有三件事：求值条件、替换 `{n}` 占位、按 `order` 排序。

**为什么由引擎产出，而不是 UI 自己算**：

| 理由 | 说明 |
|---|---|
| 语义在引擎侧 | 回顾要读 `flags` / `seenEvents` / `stats`，UI 拿不到全部语义 |
| 两个界面必须一致 | CLI 和 Web 渲染**同一份**回顾，不能各写一套 |
| 可测试 | 给一个状态就能断言「该出现哪几句」，于是有了「无死规则」测试 |

**两个容易写错的地方**：

1. **一句话总评按「归一化后」的属性算**。`money` 上限是 999999、其余是 100，
   直接比大小的话总评永远是「跟钱打交道」。所以比较的是 `值 / 该项上限`。
   （副作用正好合乎意图：钱多不构成「你是什么样的人」。）
2. **规则里不要用 `chance`**。回顾必须是确定的：同一局结算两次要给出同样的话，
   而且 `chance` 会消耗 RNG、破坏「同种子同结果」。

## 3. 数据模型

### 3.1 `GameState` 字段表与不变量

```ts
interface GameState {
  week: number                 // 1..config.totalWeeks
  actionPoints: number         // 0..config.actionPointsPerWeek
  stats: Stats                  // 6 项属性，各自被夹在 statRanges 内
  flags: Flags                  // 事件留下的痕迹（**项目进度与完成标志也存在这里**）
  seenEvents: string[]          // 已触发过的非重复事件 id
  log: LogEntry[]               // 完整历史，只追加
  endingId: string | null       // null = 未结束
  majorId: string               // 本局专业 id（决定哪些事件/行动/结局/回顾可见）
}

/** 一条日志。这是 UI 唯一的信息来源 */
interface LogEntry {
  week: number
  kind: 'action' | 'event' | 'system' | 'ending'
  text: string
  changes?: StatChange[]        // 这条日志造成的**实际**属性变化；无变化时该字段不存在
}

/** 一次结算里某项属性的实际变化量 */
interface StatChange {
  key: StatKey
  delta: number
  capped?: 'min' | 'max'        // 撞到上限/下限被截断了
}
```

**`changes` 是「回执」，不是「预告」** —— 这是本项目最容易搞错的一个语义：

| | 预告（preview） | 回执（receipt） |
|---|---|---|
| 数据来源 | `describeEffects(effects)` | `applyEffects()` 的返回值 |
| 含义 | 这个效果**声明**它会做什么 | 实际**发生了什么** |
| 触顶时 | 显示 `学业 +4` | 显示 `学业 +2`（并标 `capped: 'max'`） |
| `if` / `branch` | 列出所有分支的并集（不准确） | 只算真正走到的分支 |
| 用在哪 | 行动菜单（灰色） | 结算显示（彩色） |

**两者不一致是正常的、也是必要的**：玩家必须能从回执里看出「我这次白费了」，
否则他没法调整策略。所以不要让 UI 拿 `effects` 数组去推算回执。

**必须守住的不变量**：

| # | 不变量 | 由谁保证 | 有测试吗 |
|---|---|---|---|
| I1 | 每项属性都在 `statRanges` 的 `[min, max]` 内（**包括开局那一帧**） | `effects.ts` 的 `clamp` + `majors.ts` 的 `applyStatBonus` | ✅ |
| I2 | `week` 单调不减，且 `≤ totalWeeks` | `maybeAdvance()` 是**唯一**改 `week` 的地方 | ✅ |
| I3 | `actionPoints` 归零后必然进入 `endWeek()` | `takeAction()` / `investProject()` 里的判断 | ✅ |
| I4 | 有 `pending` 时 `week` 不增加 | `maybeAdvance()` 首行检查 | ✅ |
| I5 | `endingId !== null` 后不能再 `takeAction` / `investProject` | 两个方法的首行守卫 | ✅ |
| I6 | 一局游戏必定走到某个结局；**每个专业都有一份可见的恒真兜底结局** | 共享兜底结局（空 `all` 恒真） | ✅ |
| I7 | `log` 只追加，不修改历史条目 | 只有 `pushLog` 写它 | — |
| I8 | `state` 可被 `structuredClone` / `JSON.stringify` 无损处理 | 只用 JSON 可表达的类型 | — |
| **I9** | **报告的 `changes` 之和 == 属性的真实变化**（行动、事件选项、**项目投入**三条路径都算） | `applyEffects` 按同一入口记录 | ✅ |

> **I9 是「回执可信」的根本保证**，也是这个项目里最有价值的一条不变量。
> 它不关心引擎内部怎么算，只要求「你说变了多少」和「实际变了多少」永远一致。
>
> 实战价值：有玩家反馈「每周衰减与实际不符」，先跑 I9 的检查得到 **839 个项次 0 处不一致**，
> 于是立刻定位到「不是引擎算错，而是文案有歧义」——
> 如果没有这条检查，很可能会去「修」一份本来正确的 `weeklyEffects`。

**I8 的实践含义**（写新字段时必须遵守）：

- 用 `null` 而不是 `undefined`。`JSON.stringify` 会**直接丢掉** `undefined` 字段，导致存档读回来少一个 key。`endingId: string | null` 就是为此
- 不要放函数、`Map`、`Set`、类实例、循环引用
- 需要新的复合结构时，用普通对象和数组

### 3.2 `GameConfig`

```ts
interface GameConfig {
  totalWeeks: number              // 16
  actionPointsPerWeek: number     // 3
  initialStats: Stats             // **基准属性**（按计算机专业定）；各专业在此基础上做偏移
  statRanges: StatRange           // Record<StatKey, {min, max}>，必须覆盖全部属性
  weeklyEffects: Effect[]         // 每周结束时的固定衰减（日志文案是「每周固定衰减」）
  weeklyEventChance: number       // 0.7
}
```

`statRanges` 是 `Record<StatKey, ...>`，所以**加了属性却忘了加范围会直接编译报错**。这是刻意的类型设计（见 §4.1）。

> `weeklyEffects` 虽然写在 `config` 里，但它**也是内容**：它会写 flag
> （`穷困周数` 就是在这里 +1 的）。做静态 flag 审计时必须把它算进扫描范围，
> 否则会报出「读了却没人写」的假警报 —— 这个坑真的踩过一次（见 §6.1）。

### 3.3 存档约束（为阶段 2.5 铺路）

`GameState` 从设计之初就满足「纯 JSON」约束，目的就是让存档零成本。但**目前还不能正确存档**——不是状态的问题，而是 RNG 的问题。见 [§10 存档格式设计](#10-存档格式设计rfc)。

阶段 2 新增的 `majorId` 与项目进度都遵守同一套约束：
`majorId` 是字符串，项目进度是**数值 flag**（存在已有的 `flags` 里，没有新增复合结构）。

### 3.4 专业（`MajorDef`）

```ts
interface MajorDef {
  id: string                 // 'computer' | 'literature'
  name: string               // 「计算机」/「汉语言文学」
  identity: string           // 「计算机专业大三学生」—— 开局日志与结算回顾共用
  description: string        // 开局选择界面上的介绍
  statBonus?: Partial<Stats> // 相对 config.initialStats 的偏移
}
```

**专业不是引擎里的分支，而是内容上的一层可选标签。** 五个内容类型
（`ActionDef` / `GameEvent` / `Ending` / `SummaryRule` / `ProjectDef`）都有一个
`majors?: MajorTags` 字段：

```ts
type MajorTags = string[] | undefined   // undefined = 全专业共享
```

引擎只学会一句话（`majors.ts` 里的 `matchesMajor`）：
**打了标签的内容只有列出的专业看得见，没打标签的全专业共享。**
四个地方用它过滤：`availableActions()` / `rollWeeklyEvent()` / `settleEnding()` / `getSummary()`。

> **为什么默认是「共享」**：内容库里绝大多数条目（下雨、生病、宿舍矛盾）跟专业无关。
> 让它们默认可见，才能保证「加一个专业」的改动量正比于**新增内容**，
> 而不是正比于**全库内容**。
>
> **`statBonus` 为什么用偏移而不是完整属性**：基准值只留一处（`config.ts`），
> 调平衡时改基准就能同时作用于所有专业，而「两个专业差在哪」也压缩成一眼能看完的一小行。
>
> ⚠️ **偏移要写得克制**（文科最终只有 `skill −12、academic +2、health −2`）：
> 共享内容里的「低阈值」路线是按基准值设计的，起点抬高几点就可能让
> 「学业崩塌」「social ≤ 30」这类失败路线整片不可达 —— 这件事是被
> **按专业的死结局/死事件/死规则检查**当场抓出来的（见 §6.1）。

### 3.5 项目 / 作品（`ProjectDef` / `ProjectView`）

```ts
interface ProjectDef {
  id: string
  name: string
  description: string
  majors?: MajorTags
  requires?: Condition            // 解锁条件
  cost?: number                  // 每次投入的行动力，默认 1
  requiredInvestments: number    // 需要投入几次
  perInvest: Effect[]            // 每次投入的效果
  onComplete: Effect[]           // 完成时的一次性效果
  progressFlag: string           // 进度存放的数值 flag key（**引擎写**）
  completionFlag: string         // 完成标志 flag key（**引擎写**）
}
```

**进度存在 `flags` 里，没有新增 `GameState` 字段** —— 这是刻意的：
`flags` 本来就是「记录发生过什么」的纯 JSON 容器，进度就是一个数值 flag。
于是 I8（存档约束）零成本满足，而 flag 的 key 由数据声明，引擎不需要任何命名约定。

**这套机制没有新增任何 DSL 分支**：进度累计等价于 `addFlag`，完成判定用现成的
`flagAtLeast` / `if`。`investProject` 只做四件事：扣行动力、进度 +1、跑 `perInvest`、
攒满时置完成 flag 并跑 `onComplete`。

> ⚠️ `ProjectDef.requires` 里**不要用 `chance`**：界面每次渲染项目列表都会求值它，
> 用 `chance` 会让「打开面板」这件事消耗随机数，破坏同种子复现。

## 4. DSL 完整参考

### 4.1 类型派生关系（单一真相源）

```ts
interface Stats { academic; social; health; mood; money; skill }  // ← 唯一真相源
type StatKey = keyof Stats                                        // → 'academic' | ...
type StatRange = Record<StatKey, { min; max }>                    // 必须覆盖全部键
```

**实测过**：往 `Stats` 加一个 `stress` 字段，`pnpm typecheck` 准确报出 3 处需要同步的地方：

```
src/data/config.ts(7,14):     Property 'stress' is missing in type 'StatRange'      ← STAT_RANGES
src/data/config.ts(16,14):    Property 'stress' is missing in type 'Stats'          ← INITIAL_STATS
src/engine/effects.ts(88,14): Property 'stress' is missing in type 'Record<keyof Stats, string>'  ← STAT_LABELS
```

（上表为可读性做了简化：真实输出是 `error TS2741: Property 'stress' is missing in type '{...}' but required in type 'StatRange'` 这种形式，**行号列号与原输出完全一致**。）

`types.ts` 自己不报错——因为 `StatKey` 和 `StatRange` 是**派生**的，自动跟着变。这就是「改一处，编译器列出所有同步点」。

### 4.2 `Condition` 参考（10 种分支）

| `type` | 字段 | 语义 | 示例 |
|---|---|---|---|
| `stat` | `key: StatKey` `op: CompareOp` `value: number` | 属性比较 | `{ type:'stat', key:'academic', op:'>=', value:85 }` |
| `flag` | `key: string` | flag 为真（`true` 或**非 0 数字**） | `{ type:'flag', key:'加入集训队' }` |
| `flagEq` | `key: string` `value: FlagValue` | flag 精确等于某值 | `{ type:'flagEq', key:'结局分支', value:1 }` |
| `flagAtLeast` | `key: string` `value: number` | 数值 flag ≥ 某值 | `{ type:'flagAtLeast', key:'穷困周数', value:4 }` |
| `week` | `op: CompareOp` `value: number` | 周数比较 | `{ type:'week', op:'>=', value:10 }` |
| `not` | `condition: Condition` | 取反 | `{ type:'not', condition:{...} }` |
| `all` | `conditions: Condition[]` | 全部满足。**空数组 = 恒真** | 兜底结局用它 |
| `any` | `conditions: Condition[]` | 任一满足。**空数组 = 恒假** | |
| `chance` | `probability: number` | 概率命中，**消耗一次随机数** | `{ type:'chance', probability:0.3 }` |

`CompareOp` = `'>=' | '<=' | '>' | '<' | '==' | '!='`

**求值语义细则**：

1. `condition === undefined` → **返回 `true`**。所以「不写 `requires`」=「总是触发」。这让所有调用方省掉了判空
2. `flag` 把**非 0 数字**也算作真。所以 `穷困周数: 3` 既可以用 `flag` 判断「至少穷困过一次」，也可以用 `flagAtLeast` 判断「≥4 次」
3. `flagAtLeast` 对不存在的 key 返回 `false`（不是 0），因为它要求 `typeof === 'number'`
4. `chance` **会消耗一次随机数**，所以它在条件树里的位置会影响后续所有随机结果（见 §5.4）

**内容中的实际使用情况**（诚实记录）：

| 已使用（5） | 从未使用（4） |
|---|---|
| `stat` `flag` `flagAtLeast` `week` `all` | `any` `not` `chance` `flagEq` |

未使用的 4 种**有单测覆盖**（`not`/`any`/`chance` 都测了），只是没有真实内容用它们。这是我们自己造的一笔技术债——见 [§9](#9-已知限制与技术债)。

### 4.3 `Effect` 参考（7 种分支）

| `type` | 字段 | 语义 |
|---|---|---|
| `stat` | `key: StatKey` `delta: number` | 属性增减，**自动 clamp 到 statRanges** |
| `setFlag` | `key: string` `value: FlagValue` | 设置 flag |
| `addFlag` | `key: string` `delta: number` | 数值 flag 累加（不存在则视为 0） |
| `log` | `text: string` | 往日志写一条 `system` 消息 |
| `if` | `requires: Condition` `effects: Effect[]` | 条件效果，**可嵌套** |
| `branch` | `options: { weight: number; effects: Effect[] }[]` | 概率分支，**必定且只命中一个** |
| `end` | `endingId: string` | 直接结束游戏并指定结局 |

**`branch` 的存在理由（重要）**：

❌ **错误写法**：
```ts
effects: [
  { type:'if', requires:{ type:'chance', probability:0.5 }, effects:[好结果] },
  { type:'if', requires:{ type:'not', condition:{ type:'chance', probability:0.5 } }, effects:[坏结果] },
]
```
这是**两次独立的 50% 抽取**！会有 25% 概率两个都不中（什么都不发生），25% 概率两个都中（好坏结果同时生效）。

✅ **正确写法**：
```ts
effects: [
  { type:'branch', options: [
    { weight: 5, effects: [好结果] },   // 5/(5+5) = 50%
    { weight: 5, effects: [坏结果] },
  ]},
]
```
一次加权抽取决定落在哪个区间，**必定且只命中一个**。

**内容中的实际使用情况**：

| 已使用（6） | 从未使用（1） |
|---|---|
| `stat` `setFlag` `addFlag` `log` `if`（在 `config.weeklyEffects`）`branch` | **`end`** |

`end` 是完整实现且类型安全的功能，但没有任何内容用它——意味着这条路径**没有被真实内容验证过**。

### 4.4 `describeEffects` 与「回执」的分工

```ts
describeEffects(action.effects)   // → "学业 +4 / 心情 -2 / 健康 -1"   ← 预告（声明值）
applyEffects(ctx, effects)        // → [{key:'academic',delta:4,capped:undefined}, ...]  ← 回执（实际值）
```

两者**故意不共用同一套逻辑**，因为它们回答的是不同问题：

| | `describeEffects` | `applyEffects` 的返回值 |
|---|---|---|
| 回答 | 「这个选项**说**它要做什么」 | 「**实际**发生了什么」 |
| 触顶时 | `学业 +4` | `学业 +2` + `capped:'max'` |
| `if` / `branch` | **所有**分支的并集（不准确） | 只算真正走到的分支 |
| 是否消耗随机数 | 否（纯读数据） | 是（`chance` / `branch` 会消耗） |
| 用途 | 行动菜单的灰色预告 | 结算彩色回执 |

**⚠️ 不要拿 `effects` 数组去推算回执。** 那会漏掉两件只有 `applyEffects` 才知道的事：
属性被 clamp 截断了多少、`if`/`branch` 里哪条分支真的走了。

**`describeEffects` 的已知局限**：对带 `branch` 的效果，它列出所有分支的属性**并集**，
语义上不准确（实际只会发生一个分支）。对行动够用（行动一般没有 `branch`），
但对带概率的事件选项会误导。

**改进方向**：让它接受一个「策略」——比如只列 `if` 里非概率的部分，
或对 `branch` 显示为「随机结果」而不是罗列全部。

### 4.5 `majors` 标签**不是** DSL 的一部分

阶段 2 给内容加了一层「专业」维度，但**条件 DSL 与效果 DSL 一个分支都没加**：

| | 是什么 | 谁在用 |
|---|---|---|
| `Condition` / `Effect` | 「什么情况下触发 / 结果是什么」 | `conditions.ts` / `effects.ts` |
| `majors?: string[]` | 「这条内容属于哪个专业」 | `engine.ts` 的四处内容过滤（走 `matchesMajor`） |

两者刻意正交。好处是 `ProjectDef` 这种新内容类型可以**复用现成的 DSL 表达完整玩法**：
「多周投入 → 攒进度 → 完成 → 产出 flag」用 `addFlag` + `if` + `flagAtLeast` 就写完了，
不需要为项目发明 `{ type: 'progress', ... }` 之类的分支。

> **判据**：如果你发现要给 DSL 加一个新分支才能表达某个玩法，先问一句
> 「它是**新的判定语义**，还是只是**已有语义的新组合**？」
> 项目系统属于后者 —— 加了分支才是过度设计。

## 5. 执行流程

### 5.1 相位状态机

引擎没有显式的 `phase` 字段，相位由 `pending` 和 `endingId` **推导**出来：

```
                    ┌─────────────────────────────┐
                    │  PLANNING（玩家选行动）       │
                    │  pending=null, endingId=null │
                    └──────────────┬──────────────┘
                       takeAction()│ 行动力 -1
                                   ▼
                    ┌─────────────────────────────┐
               no   │  行动力归零？                 │
                    └──────────────┬──────────────┘
                              yes  ▼
                    ┌─────────────────────────────┐
                    │  RESOLVING（结算本周）        │
                    │  weeklyEffects → 掷随机事件   │
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
             有选项 │  事件有 choices？             │
                    └──────┬───────────────┬──────┘
                      yes  │               │ no
                           ▼               ▼
              ┌────────────────────┐   ┌──────────────────┐
              │  AWAITING_CHOICE   │   │  maybeAdvance()  │
              │  pending=事件       │   └────────┬─────────┘
              └─────────┬──────────┘            │
                 choose()│                      │
                        └──────────────────────┤
                                               ▼
                              ┌─────────────────────────────┐
                              │  maybeAdvance()              │
                              │  pending? → 停               │
                              │  week≥16? → settleEnding()   │
                              │  否则 week+1, AP 重置         │
                              └─────────────────────────────┘
```

### 5.2 `takeAction` 时序

```ts
takeAction(actionId) {
  const from = this.state.log.length          // ① 记日志起点
  // ② 两道状态守卫（顺序重要：先检查最严重的情况）
  if (endingId !== null) throw '游戏已经结束了'
  if (pending !== null)  throw '还有未处理的事件，请先做出选择'
  // ③ 查表 + 校验
  action = data.actions.find(a => a.id === actionId)
  if (!action)                throw '未知行动'
  if (action.cost > AP)       throw '行动力不足'
  if (!evaluate(requires))    throw '行动条件不满足'
  // ④ 开始改状态（一旦开始就不再回滚，所以校验必须全部前置）
  AP -= action.cost
  entry = pushLog('action', ...)               // ★ 日志先写
  changes = applyEffects(action.effects)       // ★ 结算后才知道实际变化
  if (changes.length > 0) entry.changes = changes   // ★ 补挂回执
  // ⑤ 行动力耗尽则结算本周
  if (AP <= 0) endWeek()
  return buildResult(from)                    // ⑥ 只返回增量日志
}
```

**为什么是「先写日志、后补变化量」**：日志里的 `log` 效果（`{type:'log'}`）必须排在
行动这一行**之后**，叙事顺序才对。但变化量要等 `applyEffects` 跑完才知道。
所以 `pushLog` 被改成**返回刚写入的条目**，让调用方随后补上 `entry.changes`。
这是「先写后改」的典型取舍 —— 换来了正确的叙事顺序和正确的回执。

**为什么用 `slice(fromLogIndex)` 返回增量而不是全量日志**：UI 只想显示「刚刚发生了什么」。让它自己去 diff 上一份 `log` 很别扭，重印全程又很吵。

### 5.3 `maybeAdvance()` —— 时间推进的唯一闸门

```ts
private maybeAdvance(): void {
  if (this.pending !== null) return          // ① 有事件没处理 → 冻结时间
  if (this.state.endingId !== null) return   // ② 已结束 → 冻结时间
  if (this.state.week >= config.totalWeeks) {
    this.settleEnding()                      // ③ 学期结束 → 结算结局
    return
  }
  this.state.week += 1                       // ④ 正常推进
  this.state.actionPoints = config.actionPointsPerWeek
  pushLog('system', `—— 第 N 周开始 ——`)
}
```

**只有两个调用点**：`endWeek()` 末尾、`choose()` 末尾。

**为什么这样设计**：考虑「第 5 周行动力用完 → 触发一个 3 选项事件」的场景。

1. `endWeek()` 结算完本周、抽到事件、设好 `pending`，然后调 `maybeAdvance()`
2. `maybeAdvance()` 看到 `pending !== null`，**什么都不做就返回**
3. 所以 `week` 还是 5，玩家必须先处理事件
4. 玩家 `choose(1)` → `pending = null` → 再次 `maybeAdvance()` → 这次才 `week = 6`

**时间推进的逻辑只写了一遍，而且它自己知道什么时候不该推进。UI 完全不需要判断「现在能不能进下一周」。**

对比常见烂写法：把推进逻辑散在三四个地方、每处各加一句 `if (hasPending) return`。漏一处就会出现「事件没选完就跳周」的 bug，而且极难复现。

**注意第 ③ 分支的顺序**：结算结局在「推进周数」之前，所以第 16 周用完行动力时不会出现「第 17 周」。

### 5.4 ⚠️ 随机数调用顺序（**改引擎代码前必读**）

`rng` 是一个**有状态的随机流**。同一个 seed，只要**调用次数或顺序**变了，整局结果就全变。

当前一局游戏的随机数消耗序列（`weeklyEventChance = 0.7`）：

```
每周结束时（共 16 次）：
  ① rng()                          ← 判定本周有没有事件（0.7 概率）
  ② 若命中：条件求值中每个 chance 各消耗 1 次
  ③ 若命中：pickWeighted 里的 rng()  ← 抽取抽中哪个事件

事件选项结算中（可能）：
  ④ branch 效果里的 pickWeighted 的 rng()
  ⑤ if/chance 条件里的 rng()
```

**实践后果**：

| 操作 | 是否影响同种子复现 |
|---|---|
| 改 `src/data/` 里的内容（加事件、改权重） | ✅ **会影响**（事件池变了，`pickWeighted` 结果变） |
| 改引擎里 `rng()` 的调用位置/次数 | ✅ **会影响** |
| 改 UI / CLI 代码 | ❌ 不影响（UI 不碰 rng） |
| 改属性数值但不动随机调用 | ⚠️ 影响最终状态，但随机序列不变 |
| **新增一个专业**（内容都带 `majors` 标签） | ❌ **不影响已有专业**（标签内容被过滤掉，进不了它的池子） |
| **给某个风格把项目权重设为 0** | ❌ 不影响（见下面的 opt-in 说明） |

**所以「用种子复现某一局」的前提是代码没改过。** 这不是 bug，是种子确定性系统的固有特性。要做真正的跨版本回放，需要事件溯源（记录每一步的输入）而不是只记种子。

> **一个正面案例**：加「结算回执」时，`endWeek` 里插入了 `pushLog('每周固定衰减')`
> 和一次返回值接收，但**没有插入任何 `rng()` 调用**，所以随机序列完全没变 ——
> 老种子的对局仍然可复现。改引擎时**刻意避开 rng 调用**是有意为之，
> 这和「随手加一行 `rng()` 就让所有老种子失效」是完全不同的代价。
>
> **第二个正面案例（阶段 2）**：`playOne` 的候选列表里多了一类「向项目投入一次」，
> 看起来必然会改变抽取结果。但它做成了 **opt-in**：
> `pickWeighted` 对 **0 权重项是惰性的**（不参与累加、总权重不变、`rng()` 仍然只调一次），
> 所以只要某个风格的 `__project` 是 0，它的抽取结果就逐位不变。
> 于是「6 个经典风格」的对局指纹在加了整套项目系统之后**依然完全一致** ——
> 这是「新机制没有扰动原有平衡」的**证据**，而不是一句自我评价。
> （项目本身由一个新增的「作品派」风格覆盖，否则它的可达性没人测。）

### 6.2 为什么不为每个内容条目写「快照测试」

内容条目会频繁改动（调数值、改文案、加选项）。如果为每个事件写断言其具体效应的测试，**每次调平衡都要改一堆测试**，测试就从资产变成了负担。

正确的分工是：
- **结构性不变量**（id 唯一、必备字段非空）→ 单元测试
- **数值正确性** → `pnpm simulate` 的统计分布，靠人判断形状
- **可达性 / 有没有被消费** → 那五条「死 XX」不变量
- **「加东西没有弄坏老东西」** → 两个方向：冻结的金标指纹（快）+ 差分不变量（不会过期）

### 6.3 `pnpm preflight`：推送前自检

```powershell
pnpm preflight                  # 全量
pnpm preflight -- -SkipTests    # 只想查网络
```

检查 **12 项**，分五组：

| 组 | 检查项 |
|---|---|
| 工具链 | node / pnpm / git 版本 |
| 代码健康 | typecheck、单元测试 |
| **架构边界** | ① engine 层无 DOM / 框架 / Node IO 依赖（ADR-001）② 依赖方向单向（engine 不认识 data / cli）③ BOM 合规 |
| GitHub 连接 | remote 协议、SSH 认证（计时） |
| 工作区状态 | 未提交改动、未推送提交 |

**加它的实际原因**：这台机器到 `github.com:443` 是**间歇性阻断**的。以前推一次代码可能失败好几次才发现是网络问题。先跑一次自检就能立刻区分「网络不通」和「代码有问题」。

**「架构边界」那一组的意义**：把文档里的规则变成机器执行的检查。只写在文档里的架构约束迟早会被人忘掉（或「就这一次」地破坏），跑一次 `preflight` 就能拦下。

**实现注意**（改这个脚本时别踩）：

1. `ssh -T git@github.com` 认证**成功时退出码是 1**（GitHub 的约定），所以只能靠输出文字里的 `Hi <user>!` 判断，**不能看 exit code**
2. 脚本里有中文，**必须存成带 BOM 的 UTF-8**，否则 Windows PowerShell 5.1 按 GBK 解码 → 全乱码（见 [§8.1](#81-编码--bom-规则最重要的一条)）。**注意 `edit` 工具会去掉 BOM，改完必须补回**
3. npm script 名不能叫 `doctor`——**会被 pnpm 内置的 `doctor` 命令遮蔽**，`pnpm doctor` 跑的不是你的脚本
4. ⚠️ **检查架构边界时不要直接搜单词**。第一版用 `'node:|document|window|react'` 正则扫 `src/engine/*.ts`，结果把 `state.ts` 里一句中文注释「等以后接 React 时」误判成了违规。正确做法是只匹配**模块说明符**（`from 'node:...'`）和 **DOM 属性访问**（`document.` / `window.`）。
   这类检查**必须做反向验证**：故意注入一个 `import ... from 'node:fs'`，确认它真的能被抓到，否则你只是在检查一个永远返回 OK 的脚本

### 6.4 `pnpm measure:layout`：布局回归检查

```bash
pnpm dev:web                            # 先把界面跑起来
pnpm measure:layout                     # 测量首屏（默认 http://localhost:5173/）
pnpm measure:layout -- --shots          # 顺便把截图写到 shots/
pnpm measure:layout -- --ending         # 在页面里玩到结局，再测**结算页**
pnpm measure:layout -- --ending --shots # 结算页 + 截图
```

阶段 2 又加了几种模式 —— 因为界面多了两屏，而首屏并不是最难的那一屏：

```bash
pnpm measure:layout -- --start                  # 测「开局选专业」那一屏
pnpm measure:layout -- --major literature       # 测指定专业（文科 7 个行动，比计算机更挤）
pnpm measure:layout -- --projects               # 展开作品面板之后再测
pnpm measure:layout -- --advance 30             # 先点 30 次，再测「游戏进行中」的界面
pnpm measure:layout -- --advance 30 --prefer 写稿   # 优先点某个标签，把技能顶上去
```

> **为什么要 `--major`**：界面里的行动数量取决于专业（计算机 7 个、文科 8 个），
> 而「选项被挤出屏幕」恰恰只在选项多的时候发生。只测默认专业等于没测到边界。
>
> **为什么要 `--advance`**：首屏永远只有 6–7 个行动（「投简历」要第 9 周且技能 ≥ 50
> 才解锁），**那根本不是最难的界面**。`--advance` 让脚本真的把游戏往前推，
> 逼出后面更挤的状态。
>
> **为什么固定 `?seed=12345`**：布局回归必须可复现。同一颗种子 → 同一串事件 →
> 同一个界面状态；否则每次跑到的「中间状态」都不一样，出的问题也没法复现。

用真实浏览器（CDP 驱动 Edge/Chrome）在 3 个视口下测量关键容器，**用数字判断而不是靠眼睛**：

| 视口 | 为什么选它 |
|---|---|
| 390×844 | iPhone 14 —— 主要目标平台 |
| 360×740 | 小屏 Android —— 垂直空间最紧 |
| 1280×900 | 桌面 —— 作品集里别人第一眼看的尺寸 |

首屏检查四条：① 页面无横向溢出 ② **行动面板不需要内部滚动**（否则玩家看不到全部选项）
③ **日志区不被压到 72px 以下**（引导文字放不下） ④ 最后一个选项在视口内。

**`--ending` 模式**（测结算页）检查另外三条：① 无横向溢出 ② 卡片不横向溢出
③ **滚到顶部时卡片顶部够得着**（专治 flex 居中 + overflow 的经典坑）。

**`--start` 模式**（测开局屏）检查：专业卡片没有横向溢出、最后一张卡片在视口内、
整屏不需要滚动。**`--projects` 模式**（展开作品面板）检查：标题行仍在屏幕上
（否则收不回去）、项目卡片没有横向溢出、内容够不着时面板必须可滚动。

> ⚠️ **第 ③ 条（日志区）在阶段 2 放宽过一次，这里要说清楚为什么。**
> 它原来是「初始状态一律不许溢出」。但阶段 2 底部多了一个作品入口，
> 而 360×740 上的账是算得死的：顶栏 49 + 属性 88 + 日志下限 72 + 底部留白 10
> ≈ 219px 是留给「面板 + 日志」的全部空间。
> 现在的判据是**日志区不得低于 72px 的下限**（低于它开场引导真的放不下），
> 日志内容超出则如实报出来但不算失败 —— 因为**日志本质上是可滚的历史**，
> 而行动选项和作品入口是**操作**，后者被藏起来才是真正不能接受的事。
> 这是有意的取舍，不是把检查调松好让它变绿。

> ⚠️ **`--ending` 用的是另一组「矮视口」**（含 360×560），这不是随手定的。
> 结算卡片的高度取决于这局触发了多少条回顾（实测 4–9 条 → 650–850px），
> 用 844px 的视口它**刚好装得下** —— 于是「内容超过一屏」这个真正危险的场景
> 根本压不到，全绿但什么都没测到。第一次跑就吃了这个亏。
> 矮视口能稳定逼出「卡片比屏幕高」，那条 `margin: auto` 的修复才被真正验证。

**为什么需要它**：布局问题**无法用单元测试覆盖** —— `renderToString` 只产出 HTML，没有排版。
而它很难靠眼睛发现：开发这个界面时，桌面上「6 个行动只显示 4 个，必须往面板里滚动」——
截图看着只是"有点挤"，但真实数字是 `clientHeight=386 / scrollHeight=590`，
**204px 的关键内容藏在折叠线下面**。

**两个坑（都踩过）**：

1. ⚠️ **不要用 `msedge --window-size=390,844 --screenshot` 做移动端验证**。
   Edge 在 Windows 上对窗口宽度有**最小值**，视口不会真的变成 390 ——
   截图会显示宽布局的左半边，看起来完全像「页面横向溢出了」。
   实测证明它没溢出：`innerWidth=390, docScrollWidth=390, offenderCount=0`。
   必须用 CDP 的 `Emulation.setDeviceMetricsOverride` 才能真正设定视口。
   （顺带说：`--screenshot` 产出的图看着像 bug，实际是工具骗人 —— 这类假警报已经出现 5 次了。）
2. 面板的 `max-height` **不要拍脑袋写百分比**。原来写 `62dvh`，在 740px 高的屏幕上
   就是 459px —— 而 6 个行动需要 465px，于是第 6 个被裁掉 8px。
   现在写成由固定部分推导的 `calc(100dvh - 220px)`
   （顶栏 49 + 属性面板 88 + 日志区下限 72 + 底部留白 10 ≈ 220）。

**CSS 布局的一条经验**：手机上**垂直空间是最稀缺的资源**。
这个界面里几个关键取舍都围绕它：属性面板在手机上保持两列（单列会多吃 57px、
直接把行动面板挤出屏幕）、选项压成 2 行（83px → 59px）、开局引导压成 1 行。

### 6.5 阶段 2 新增的不变量（专业维度 + 消费检查）

阶段 2 把内容切成了「共享 + 各专业专属」，于是原来的检查必须**降口径到专业**，
否则会两头出错：把专属内容误判成死内容，或者把跨专业泄漏放过去。

| 不变量 | 判据 | 在哪 |
|---|---|---|
| **死结局 / 死事件 / 死规则（按专业）** | 每个专业**自己看得见**的每一条，都必须在该专业下被触发过 | `engine.test.ts`（跑 `simulate`） |
| **无死项目** | 每个专业可见的每个项目都必须被真的**完成**过 | 同上 |
| **无死选项** | 每个**触发过**的事件的每个选项，都必须至少「可点」过一次 | 同上 |
| **无死行动** | 每个行动都必须至少上过一次菜单 | 同上 |
| **无死 flag（静态审计）** | 写了却没有任何条件读它 = 死数据；读了却没有任何地方写它 = 永远不成立的条件 | `src/cli/audit.ts` + `engine.test.ts` |
| **引擎无专业硬编码** | 引擎源码（去注释后）里不许出现任何专业 id 或专业名 | `engine.test.ts`（读文件扫描） |
| **专业隔离（差分）** | 把某专业的内容单独拎出来跑，结果必须与它在完整数据集里逐位相同 | `engine.test.ts` |
| **金标指纹** | 70 局对局的结局/属性/事件数/回顾数逐位不变 | `tests/golden-fingerprint.ts` |

**「死选项」和「死行动」为什么是后补的（阶段 2.6 加）**：

这两个判据都是「曾经**可点/可见**过」，不是「被选过」——
模拟器按权重随机选，「没被选中」可能只是运气；而「连出现都没出现过」
说明那个 `requires` 严到条件永远凑不齐，玩家一辈子看不到它。

它们是加「花钱换属性」时被逼出来的：那些选项靠 `money >= X` 把关，
**而钱在这个游戏里是紧的**（每周固定 −100，16 周就是 −1600，起始只有 800），
非常容易写出一个「永远付不起」的门槛。事实上第一版就真的抓到了 ——
`室友还钱了吗` 的两个选项从未被启用过（因为上游 `借出去过钱` 的链条被新花钱内容挤断了）。

> **「死选项」只查触发过的事件**：一个根本没出现过的事件，它的所有选项当然
> 都没被启用过 —— 但那是「死事件」的判据，混在一起只会让报告里多出一堆下游噪音
>（一个死事件带出 2–3 条假死选项）。

**两个「死 flag」方向都要查**，只查一个方向会漏掉另一种死法：

- **写了没人读**：`setFlag` 设了一个 flag，却没有任何条件读它 —— 玩家永远感知不到，
  维护者却以为它有意义
- **读了没人写**：某个条件读了 flag，却没有任何地方写它 —— 这是一个**永远不可能成立的分支**

**扫描范围必须覆盖所有能写 flag 的入口**，包括容易被忘掉的那些：
`config.weeklyEffects`（每周固定衰减里也有 `addFlag`）、项目的 `perInvest` / `onComplete`、
以及回顾规则的 `countFrom`（它也是**读**这个 flag 来渲染文案）。
漏掉任何一个写入点，就会得到一个「看起来很严重、其实只是自己漏扫」的假警报 ——
这个坑真的踩过一次：`穷困周数` 被误报成「读了却没人写」。

**项目的两个 flag 要豁免**：`progressFlag` / `completionFlag` 是**引擎**写的
（`investProject` 每次 +1 / 置 true），静态扫描看不到写入点，所以
`auditFlags` 通过 `consumedByEngine` 参数把它们算作「已写入」。

**差分不变量为什么比指纹更耐久**：

```ts
// 把 A 专业单独拎出来跑一局 → 必须和它在完整数据集里跑完全一样
const isolated = isolateMajor(major.id)
expect(playOne(seed, weights, major.id, isolated)).toEqual(playOne(seed, weights, major.id))
```

指纹是**冻结的历史**（内容一变就必须重新生成，否则它守的是过期事实）；
差分不变量每次现算，所以**永远不会过期**：只要引擎的过滤漏了一处，
B 专业的内容就会渗进 A 的池子，这条会直接指出来。
两者一起用：指纹抓「悄悄漂移」，差分抓「渗漏」。

**改动文件**：`src/engine/types.ts` + `src/engine/conditions.ts`

```ts
case 'flagBetween': {
```

### 配方 6：加一个效果类型

**改动文件**：`src/engine/types.ts` + `src/engine/effects.ts`

1. 往 `Effect` 联合加分支
2. 往 `applyEffect` 的 `switch` 加 case

⚠️ **`applyEffect` 的 `switch` 是 `void` 返回**，所以 TS **不会**帮你检查漏了 case！
这是与 `evaluate` 不同的地方。保护措施：

```ts
// 在 applyEffect 的 switch 之后加一个穷尽性断言
default: {
  const never: never = effect
  throw new Error(`未处理的 effect 类型: ${JSON.stringify(never)}`)
}
```

这样加了新分支而忘了处理时，`const never: never = effect` 会编译报错。

3. 如果新效果会**产生属性变化**，有两个地方要一起考虑：
   - `describeEffects`（**预告**：菜单里显示「这个选项说它做什么」）
   - `applyEffects` 里的 `recordChange`（**回执**：结算时显示「实际发生了什么」）

   ⚠️ **只做前者会漏掉回执**。最典型的是 `stat` 之外的隐含属性效果，
   或者需要按分支/条件决定数值的效果 —— 它们必须走 `recordChange` 记录，
   否则 I9（报告之和 == 真实变化）会失败。**跑 `pnpm test` 会立刻抓到。**

4. 如果新效果会**消耗随机数**，一定要在 [§5.4](#54-️-随机数调用顺序改引擎代码前必读) 里更新记录，并接受「旧种子失效」

### 配方 6b：新增一条「结算回执」日志

**改动文件**：`src/engine/engine.ts`（通常不用改 `effects.ts`）

当你要在某个流程节点显示「这一步改了什么」时：

```ts
// ① 先写日志（这样效果里的 log 效果会排在它后面，叙事顺序才对）
const entry = pushLog(this.state, 'system', '这一步的说明文字')

// ② 结算，拿到**实际**变化量
const changes = applyEffects(this.createContext(), someEffects)

// ③ 补挂回执（无变化时不挂，保持字段可选）
if (changes.length > 0) entry.changes = changes
```

**三条硬要求**：

1. **顺序不能反**。先 `pushLog` 再 `applyEffects`，否则 `{type:'log'}` 效果的文本会跑到这行前面
2. **不要新增 `rng()` 调用**。这会让所有老种子失效（见 §5.4）
3. **写测试**。至少断言这条日志存在且 `changes` 非空；更强的是让 I9 覆盖它

现有的四个挂载点可以直接抄：`takeAction`（行动）、`choose`（玩家选项）、
`triggerEvent`（无选项事件的自动效果）、`endWeek`（每周固定衰减）。

### 配方 8：加 Web 界面（React）—— ✅ 已实现，见 `src/web/`

**现状**：`src/web/` 已经是**可运行的参考实现**（最小可用版）。要加功能时照它改，
或者读 [§2.1 的「Web 层四条约定」](#21-各模块职责速查)。

**目录结构**：

```
src/web/
  useEngine.ts          引擎适配层（唯一 import GameEngine 的地方）
  App.tsx               页面骨架
  styles.css            样式（移动优先、零美术资源）
  components/
    StatsPanel.tsx        属性面板
    LogFeed.tsx           日志流（可滚动历史）
    ActionPanel.tsx       行动列表
    EventPanel.tsx        事件卡 + 选项
    ChangeList.tsx        结算回执
    EndingScreen.tsx      结局页
```

**核心工作方式**（`useEngine` 里的模式）：

```ts
// 引擎内部是**可变**的，但 getState() 返回**深拷贝** ——
// 所以「每次操作后重新取快照」就能直接用 useState 驱动渲染
const engineRef = useRef<GameEngine | null>(null)
const [snapshot, setSnapshot] = useState(() => takeSnapshot(engineRef.current!))
const [feed, setFeed] = useState<LogEntry[]>(() => engineRef.current!.getState().log)

function sync(logs: LogEntry[]) {
  setFeed((prev) => [...prev, ...logs])   // 引擎只返回增量，累积是 UI 的责任
  setSnapshot(takeSnapshot(engineRef.current!))
}
```

**四条硬约束**（违反任何一条都说明分层出了问题）：

1. **不修改 `getState()` 返回的对象**。它是深拷贝，直接改它引擎毫无反应
   （这是刻意的设计，见 [§3.1](#31-gamestate-字段表与不变量)）
2. **不 import `evaluate` / `applyEffects` / `GameEngine`**（除 `useEngine.ts`）。
   UI 只用 [§2.2](#22-gameengine-完整-api) 里列出的稳定 API
3. **不自己判断规则**：选项可不可点用 `getPendingChoices().enabled`，
   行动可不可用由 `availableActions()` 过滤好
4. **不自己推算数值**：回执直接读 `LogEntry.changes`，绝不去解析 `effects` 数组
   （见 [§4.4](#44-describeeffects-与回执的分工)）

**回调里要读 ref，不要捕获 engine 变量** —— 否则 `restart()` 之后回调还指着旧引擎：

```ts
// ❌ 捕获了 engine，restart 后失效
const engine = engineRef.current
const acting = useCallback((id) => sync(engine.takeAction(id).logs), [engine])

// ✅ 每次从 ref 取
const acting = useCallback((id) => sync(engineRef.current!.takeAction(id).logs), [])
```

**`?seed=N`**：`useEngine` 会读地址栏的 seed，所以「复现某一局」的链接可以直接分享
（对应 CLI 的 `pnpm play -- --seed N`，是 ADR-002 的直接收益）。

**关于构建配置的两个坑**：

- Vite 的 `base` 用 `'./'`（相对路径）而不是默认的 `'/'` ——
  否则部署到 GitHub Pages 的项目页（`https://user.github.io/repo/`）会 404
- `tsconfig.json` 需要 `"jsx": "react-jsx"`。注意**根目录下的临时 `.tsx` 文件
  拿不到这个配置**（不在 tsconfig 的 `include` 里），tsx/esbuild 会退回经典转换
  并报 `React is not defined`

| 检查 | 报什么 | 怎么修 |
|---|---|---|

- **顺序**：专属内容一律**追加在末尾**。`pickWeighted` 按数组顺序累加权重，

  追加则不影响（过滤掉专属内容后，已有专业的池子逐位不变）。
- **不要动共享内容**。改了共享事件的条件或权重，所有专业的老对局都会变
  （金标指纹会红，那是**正确**的报警，不是要你更新指纹，而是要想清楚是否值得）。

### 配方 10：加一个项目 / 作品

**改动文件**：对应专业的内容文件（如 `literature.ts`）里的 `*_PROJECTS`。

```ts
{
  id: 'proj_medicine_chart',          // 唯一
  name: '整理一份病程记录模板',
  description: '把见习时记的零散笔记，整理成能给别人复用的模板',
  majors: ['medicine'],
  requires: { type: 'stat', key: 'academic', op: '>=', value: 45 },  // 解锁条件
  requiredInvestments: 3,             // 投入几次完成
  perInvest: [                        // 每次投入的效果
    { type: 'stat', key: 'academic', delta: 2 },
    { type: 'stat', key: 'mood', delta: -1 },
  ],
  onComplete: [                       // 完成时的一次性奖励
    { type: 'stat', key: 'academic', delta: 4 },
    { type: 'log', text: '模板被带教老师拿去用了。' },
  ],
  progressFlag: '项目_病程模板_进度',   // 引擎写，不用自己维护
  completionFlag: '项目_病程模板_完成', // 引擎写
}
```

**然后务必做两件事**：

1. **让 `completionFlag` 被消费掉** —— 至少写一条回顾规则读它
   （或者接进某个结局的 `requires`）。否则静态审计会报「写了没人读」，
   而且玩家做完项目看不到任何叙事反馈，这笔投入等于白花。
2. **跑 `pnpm test`** 确认「无死项目」通过 —— 也就是确认**真的有某种玩法会把它做完**。
   `作品派` 风格会主动投项目（`__project: 6`），它是你的兜底验证者。

> ⚠️ `requires` 里**不要用 `chance`**：界面每次渲染项目列表都会求值它，
> 会在你打开面板时消耗随机数，破坏同种子复现。

## 8. 约定与规约

### 8.1 编码 & BOM 规则（**最重要的一条**）

这是本项目踩过最严重的坑——**静默数据损坏**，而且已经推到过 GitHub 一次。

**规则**：

| 文件类型 | BOM | 字符集 | 原因 |
|---|---|---|---|
| `.ps1`（含中文） | **必须有 BOM** | UTF-8 | Windows PowerShell 5.1 读无 BOM 的 UTF-8 会按 GBK 解码 → 乱码 |
| `.ts` `.json` `.md` `.npmrc` `.gitignore` `.yaml` | **必须无 BOM** | UTF-8，配置文件尽量纯 ASCII | `JSON.parse` / pnpm 遇到 BOM 直接报错 |

**⚠️ 绝对不要用 PowerShell 的 `Get-Content` / `Set-Content` 往返处理 UTF-8 文件**：

```powershell
# ☠️ 危险！这一行会同时造成两种不可逆损坏
(Get-Content package.json -Raw) -replace 'a','b' | Set-Content package.json -Encoding UTF8
```

- `Get-Content` 在 PS 5.1 里**默认按系统 ANSI 码页读取**（简中是 GBK）→ UTF-8 中文被误解码成乱码
- `Set-Content -Encoding UTF8` 把乱码以 UTF-8 写回 → **损坏不可逆**
- 而且 `-Encoding UTF8` 会**额外写入 BOM** → `JSON.parse` 抛 `Unexpected token ''`，pnpm 报 `control character found while parsing`

**正确做法**：

```powershell
# A. 需要精确控制字节/BOM 时，用 .NET（$false = 不写 BOM）
$t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding $false))

# B. 只改文本内容时，用编辑器，别让 shell 参与
```

**全仓库 BOM 自检**（正常输出应该**只有 `preflight.ps1`**）：

```powershell
Get-ChildItem -Recurse -File | Where-Object { $_.FullName -notmatch 'node_modules|\\\.git\\' } | ForEach-Object {
  $b = [System.IO.File]::ReadAllBytes($_.FullName)
  if ($b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF) { $_.Name }
}
```

|---|---|---|
| 事件 id | `ev_` + 蛇形 | `ev_club_recruit` |
| 结局 id | `ending_` + 蛇形 | `ending_dropout` |
| 行动 id | 动词/名词，蛇形，无前缀 | `study` `parttime` `job_hunt` |

## 9. 已知限制与技术债

诚实记录，避免以后重复踩或误以为是 bug。

### 9.1 ⚠️ RNG 状态不可序列化（**阻塞存档功能**）

```ts
export function mulberry32(seed: number): RNG {
  let a = seed >>> 0            // ← 闭包私有变量
  return function next() {
    a = (a + 0x6d2b79f5) >>> 0  // ← 只在这里被读写
    ...
  }
}
```

**问题**：`a` 是闭包内部状态，**外部既读不到也写不回**。所以：

```
存档 → 读档 → 用同一个 seed 重建引擎
                              ↓
              随机流会从「序列开头」重新开始
              而不是从「存档那一刻的位置」继续
                              ↓
              继续玩下去的结果 ≠ 不中断的结果
```

**唯一能存的东西是 `seed`，不是「当前随机流位置」。** 这直接影响阶段 2 的「存档 → 读档 → 继续玩结果一致」这条验收标准。三个解决方案见 [§10.2](#102-核心难题rng-状态不可序列化)。

### 9.2 `describeEffects` 对 `branch` 显示不准确

罗列了所有分支的属性并集，但实际只会命中一个。对行动无影响（行动没有 `branch`），
对带概率的事件选项会误导玩家。

**注意这个局限只影响「预告」，不影响「回执」** —— 回执走的是 `applyEffects` 的返回值，
只算真正走到的分支（见 [§4.4](#44-describeeffects-与回执的分工)）。
所以最坏情况是菜单里的预告偏乐观，但结算数字永远是真的。

### 9.3 `compare` 的 `default` 削弱了穷尽性检查

```ts
function compare(a, op, b) {
  switch (op) {
    // ...6 个 case
    default: return false       // ← 这里
  }
}
```

如果以后往 `CompareOp` 加了 `'startsWith'`，编译器**不会报错**，新算子会静默地永远返回 `false`。严格做法是删掉 `default` 并声明返回类型，让 TS 保证穷尽。

### 9.4 DSL 覆盖面（✅ 阶段 1 起全部分支都被真实内容使用）

| DSL | 已实现 | 内容中使用 | 未被使用 |
|---|---|---|---|
| Condition | 10 种 | **10 种** | （无） |
| Effect | 7 种 | **7 种** | （无） |

阶段 1 之前这里是 5/9 和 6/7：`any`/`not`/`chance`/`flagEq`/`end` 五个分支**没有被真实内容验证过**——`simulate` 跑几千局也覆盖不到。现在全部用真实内容跑起来，各自的落点：

| 分支 | 落点 |
|---|---|
| `flagEq` | 「社团骨干竞选」读 `社团贡献 == 2` |
| `not` | 「没社团的周末」`not(加入集训队 或 加入街舞社)` |
| `any` | 「感觉被掏空」`any(健康<40, 心情<40)` |
| `chance` | 「双十一秒杀」40% 概率回血 |
| `end` | 「考试作弊」30% 概率半途强制「学业崩塌」结局 |

> `seenEvent` 是加「结算回顾」时新增的第 10 个条件（见 §2.4）——
> 回顾想说「你这学期遇到过期中考试」，而这件事既没有也不该有 flag。
> 条件 DSL 的扩展成本很低：加一个 type + `conditions.ts` 里一个 `case`，
> 所有已有的内容自动获得这个能力。

### 9.5 事件量不足导致重复感

阶段 1 前 17 个事件、一局约 11 次触发，跨局重复度实测 **69%**。阶段 1 扩到 48 个后降到 37%，再加 14 个「全程可用 + weight 1」的日常琐事事件稀释池子后，降到 **28%（达标，目标 ≤30%）**。

关键洞察：**光加带门槛的事件不够**。48 个事件时结构池已经有 36，但有效池（考虑属性/flag 门槛后）偏小，重复度仍卡在 37%。真正管用的是那 14 个**无门槛、weight 1** 的琐事——它们不推进剧情，职责就是撑大有效池，让别的关键事件不再每局必见。

阶段 2 之后总数是 **72 条**（62 条共享/计算机 + 10 条文科专属），但**每个专业只看得到自己那份**：
计算机 62 条、文科 68 条，两个专业的重复度都仍是 28%（达标）。

> ⚠️ 专属事件会**稀释**共享内容的出现率：文科的池子里多了 10 个自己专属的高权重事件，
> 共享的稀有事件（比如「心理咨询预约」）就更难被抽中 —— 阶段 2 一度因此被
> 「死事件」检查拦住一次。加专属内容时要留意这件事。

### 9.6 `getState()` 每次深拷贝

`getState()` 用 `structuredClone` 深拷贝整个状态。当前状态只有几十个字段，**完全无所谓**（2800 局模拟含大量 `getState` 调用，加起来也只有几秒）。

如果状态涨到几千个字段（比如记录完整历史事件流），需要改成不可变数据结构 + 结构共享。**原则：先正确，再快。**

### 9.7 没有 CI

推送不会自动跑测试。目前靠 `pnpm preflight` 手动执行。阶段 4 补 GitHub Actions。

### 9.8 「主线」是 flag 暗线，不是独立抽取池

阶段 1 已把 13 条 flag 暗线做成闭环（前置设 flag → 后续读 flag，见设计文档 §3.6），死 flag 清零。但它们**仍不是独立的抽取池**：`EventCategory` 只有 `'random'`，后续事件和普通事件混在同一个随机池里、靠 `flag` 条件触发。真做「行动专属事件」需要给 `EventCategory` 加值 + 引擎按类别独立抽取，仍是后续的扩展点。

### 9.9 死 flag（✅ 阶段 1 清零，阶段 2 变成自动检查）

~~有两个 flag 是「只写不读」的死 flag~~ → 阶段 1 全部清零。

这一节原来的版本只列了「投递次数、被预警」两个，还错把 `投递次数` 当死 flag（它其实被「大厂 Offer」结局读取）。阶段 1 加了自动扫描后才发现真实缺口远不止两个——「替答到过」「加入集训队」「纸条成功」「借出去过钱」「身体预警」「谈过心」「电脑坏了」这些都是只写不读。现在全部接上了后续事件（见设计文档 §3.6 的暗线表）。

> 教训：**「看着只有两个」和「实际有八个」之间，只差一次自动扫描。**
> 这跟「死结局」检查是同一个思路——把「内容是否真的被消费」变成可自动验证的不变量，
> 而不是靠人肉去数。

**阶段 2 把这件事收进了代码**（当时这里写着「flag 侧目前还是一次性脚本」）：
现在是 `src/cli/audit.ts`，而且是**两个方向 + 按专业作用域**：

| 方向 | 含义 | 为什么会发生 |
|---|---|---|
| **写了没人读** | `setFlag` 设了 flag，没有任何条件读它 | 写的时候以为后面会用到，后来忘了 |
| **读了没人写** | 条件读了 flag，没有任何地方写它 | 抄条件时漏了写入点 → **永远不成立的分支** |

**为什么必须按专业作用域**：共享结局读了 flag「诗集完成」，而写它的只有文科的专属事件 ——
全局看「有写有读」，但**对计算机来说那个条件永远不成立**。

### 9.10 项目收益偏强（已知的平衡观察，未处理）

`作品派` 风格在文科身上 **85.5%** 走成「签约作者」。这不是 bug，但值得记下来：
项目每次投入的性价比略高于最好的行动（`write` 每点行动力 +4 技能 / −3 心情 / −1 健康，
而 `proj_longform` 每点 +4.5 技能、约 0 心情、0 健康），再加上完成奖励，
「做项目」在长期看是**严格更优**的选择。

目前没动它，原因有两个：
1. 经典 7 种风格的平衡**没有受影响**（项目是 opt-in，见 §5.4），
   所以它没有把某条路变成「唯一最优解」——只是让专门投项目的风格更集中
2. 「投项目 → 成为签约作者」本身就是要传达的因果关系（设计文档 §9 的耦合点 2）

**真要调的话**，方向是提高投入次数（3/4 → 4/5）或下调 `onComplete` 的数值，
而不是砍 `perInvest` —— 后者会让「投入过程」本身变成纯亏，玩家就不会开始了。

## 10. 存档格式设计（RFC）

阶段 2.5 的设计草案，**写代码前先定这个**。（阶段 2 是玩法扩充，不含存档。）

### 10.1 存档结构

```ts
interface SaveFile {
  /** 存档格式版本，与游戏内容版本解耦。迁移逻辑的唯一依据 */
  formatVersion: number
  /** 生成这个存档时的游戏版本，只用于诊断 */
  gameVersion: string
  /** ISO 8601 时间戳 */
  savedAt: string
  /** 玩家看到的存档名 */
  label?: string
  /** 随机种子（用于「重开同一局」和 UI 显示） */
  seed: number
  /** RNG 的当前状态 —— 见 10.2 */
  rngState: number
  /** 引擎状态 */
  state: GameState
  /** 已解锁的结局 id，用于「还有几个结局没解锁」提示 */
  unlockedEndings?: string[]
}
```

> **阶段 2 之后**：`state` 里已经有 `majorId`，所以「读档后还是那个专业」是自动满足的 ——
> 这也是当初把 `majorId` 放进 `GameState` 而不是存在 `SaveFile` 顶层的原因：
> 它本来就是**这一局的一部分**，不是存档的元信息。
> 项目进度也在 `state.flags` 里，同样不需要额外字段。

**为什么 `formatVersion` 与 `gameVersion` 分开**：游戏加内容（新事件/结局）不需要改存档格式，此时 `gameVersion` 变而 `formatVersion` 不变——**旧存档必须能直接读**。只有 `GameState` 的结构本身变了才升 `formatVersion`。

### 10.2 核心难题：RNG 状态不可序列化

| 方案 | 做法 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|---|
| **A. 只存 seed** | 读档后用 seed 重建 RNG | 零改动 | 读档后随机流从**开头**重放 → 结果与不中断**不一致**；且会重复触发已经历过的事件分支 | ❌ 不满足验收标准 |
| **B. 暴露 RNG 状态** | 让 `mulberry32` 支持导出/导入内部 `a` | 忠实恢复；改动很小；结果完全一致 | 需要改 `rng.ts` 的 API | ✅ **推荐** |
| **C. 事件溯源** | 存档只记 seed + 玩家的每一步输入，读档时从头重放 | 天然支持回放/录制；不需要序列化 RNG | 读档要重放全部历史（当前规模 48 步 + ~11 事件，微不足道）；存档含完整操作日志 | ✅ 也很好，且额外获得回放能力 |

**方案 B 的具体做法**：

```ts
// 改造后：RNG 是一个带显式状态的对象，而不是纯闭包
export interface Rng {
  next(): number
  getState(): number      // 导出内部 a
  setState(s: number): void  // 导入内部 a
}

export function createRng(seed: number, state?: number): Rng {
  let a = (state ?? seed) >>> 0
  return {
    next() { /* ...原逻辑... */ },
    getState: () => a,
    setState(s) { a = s >>> 0 },
  }
}
```

**注意这个改动会触及 ADR-002**：`RNG` 类型从 `() => number` 变成带方法的对象，所有传 `rng` 的地方（`conditions.ts` 的 `chance`、`effects.ts` 的 `branch`、`engine.ts`）都要从 `ctx.rng()` 改成 `ctx.rng.next()`。改动面不大但很分散——**所以要在阶段 2.5 一开始就做，不要等到写了别的功能再回头改**。

**推荐组合**：**方案 B 为主**（满足验收标准）+ 把「玩家操作序列」也存进 `SaveFile` 作为可选字段（这样以后能顺便做「回放这一局」，即方案 C 的能力）。

### 10.3 迁移机制

```ts
/** key = 从哪个版本升级；value = 把该版本的数据升到下一版 */
const MIGRATIONS: Record<number, (data: any) => any> = {
  // 例：v1 → v2 时 stats 里新增了 stress 字段
  1: (d) => ({ ...d, formatVersion: 2, state: { ...d.state, stats: { ...d.state.stats, stress: 50 } } }),
}

function migrate(save: any): SaveFile {
  let data = save
  while (data.formatVersion < CURRENT_FORMAT_VERSION) {
    const step = MIGRATIONS[data.formatVersion]
    if (!step) throw new Error(`缺少 v${data.formatVersion} 的迁移逻辑，无法读取此存档`)
    data = step(data)
  }
  return data as SaveFile
}
```

**要求**：
- 迁移函数必须是**纯函数**（不改入参）
- 每一次 `formatVersion` 递增都**必须**配一个迁移函数，否则旧存档永久丢失
- 迁移失败要给**明确错误**（告诉玩家存档太旧），不允许静默损坏

### 10.4 数据校验

读档时必须校验，不能直接信任文件内容（用户可能手改过、文件可能损坏）：

```ts
function validate(save: unknown): save is SaveFile {
```

## 11. 变更影响矩阵

「我想改 X，会连带影响什么？」

| 改动 | 需同步修改 | 会破坏同种子复现吗 | 必须跑的验证 |
|---|---|---|---|
| 加/改一个事件 | 无 | ✅ 会影响 | `pnpm simulate`（看死结局 & 分布） |
| 改事件权重 | 无 | ✅ 会影响 | `pnpm simulate` |
| **加一个专业** | `data/majors.ts` + 一个新内容文件 + `data/index.ts`（**追加**）+ `simulate.ts` 的 `STRATEGIES` | ❌ **不影响已有专业**（专属内容被过滤） | `pnpm test`（差分不变量 + 金标指纹 + 按专业的死内容）+ `pnpm simulate` |
| **把某条已有内容标成专属专业** | 无（加一个 `majors` 字段） | ❌ 对**标注的那个**专业不影响；对别的专业会让它消失 | `pnpm test`（如果被排掉的内容在别的专业里没人读了，死内容检查会报） |
| **加一个项目** | 对应专业内容文件里的 `*_PROJECTS` | ❌（只要不给经典风格加 `__project` 权重） | `pnpm test`（无死项目 + I9）+ `pnpm simulate` |
| **给某个风格打开项目权重** | `simulate.ts` 的 `STRATEGIES`（`__project`） | ✅ 会影响那一风格的全部对局 | `pnpm simulate`（这是**有意的**改动，金标指纹会红） |
| 加/改行动 | `simulate.ts` 的 `STRATEGIES` | ✅ 会影响 | `pnpm simulate -- --games 500`（看平衡是否被稀释） |
| 加/改结局 | 无 | ❌ 不影响 | `pnpm test`（可达性测试会检验新结局） |
| 改 `priority` | 无 | ❌ | `pnpm test` + `simulate`（检查是否饿死了别的结局） |
| 加属性 | `types.ts` → 编译器指引 3 处 + `STAT_ORDER` ×2 + 配套行动/事件 + 可选衰减 | ⚠️ 若动了随机调用则影响 | `pnpm typecheck` `pnpm test` `pnpm simulate` |
| 改属性衰减 | 无 | ❌ | `pnpm simulate`（分布形状会大变） |
| 加条件类型 | `types.ts` + `conditions.ts` + 测试 + 真实内容 | ⚠️ 若内容里用 `chance` 则影响 | `pnpm typecheck`（TS 会抓漏掉的 case） |
| 加效果类型 | `types.ts` + `effects.ts` + **手动加穷尽断言** + 测试 | ⚠️ 若消耗随机数则影响 | `pnpm typecheck`（注意：`applyEffect` 是 `void` 返回，TS **不会**自动检查漏 case） |
| 改 `rng.ts` 调用位置 | 更新 §5.4 的记录 | ✅ **必然破坏** | `pnpm test`（可复现性测试会失败——这是**预期**的） |
| 给 `LogEntry` / `StatChange` 加字段 | 本文档 §3.1 字段表 + §2.3 契约表 | ❌ | `pnpm test`（I9 会覆盖回执正确性） |
| 改 `applyEffects` 的返回值语义 | §2.1 签名表 + §4.4 + 本文档全部引用它的地方 | ❌ | `pnpm test`（I9 + 回执语义测试） |
| 新增一条「结算回执」日志 | 无（照配方 6b 做） | ⚠️ **只要不加 `rng()` 就不影响** | `pnpm test`（I9 会自动覆盖新流程） |
| 改 UI / CLI | 无 | ❌ | 手动冒烟 |
| 重构 `private` 方法 | 无 | ⚠️ 若动了随机调用 | `pnpm test` |
| 改 `GameState` 结构 | 文档 + 存档迁移 | ❌ | 需要加存档兼容性测试 |
| 加存档 | 新增 `src/save/`，**先解决 RNG 状态** | ❌ | 新增 `tests/save.test.ts` |

## 12. 性能与规模

当前规模与实测数据：

| 指标 | 数值 |
|---|---|
| 单局行动数 | 48 |
| 单局事件触发数 | ~11 |
| 75 个单元测试 + 1680 局可达性模拟 | **~5 秒** |
| 2800 局平衡模拟（2 专业 × 7 风格 × 200） | 约 20 秒 |
| Web 产物（含 React + 引擎 + 全部内容） | 292 KB / gzip **91 KB** |
| CSS 产物 | 9.8 KB / gzip 2.6 KB |
| `pnpm test` 总耗时 | ~5s |

**结论：当前规模下性能完全不是问题，不要提前优化。**

需要开始关注性能的信号（按优先级）：

1. 单局超过 500 次行动
2. `GameState` 里开始存完整历史事件流（而不是只存 `log`）
3. Web 界面里 `getState()` 每帧调用
4. 事件池超过 1000 条（`filter` 是 O(n)。注意次数：`rollWeeklyEvent` 每局调 **16 次**，但 `filter` 在 0.7 的判定命中后才执行，实际约 **11 次/局**）

`rollWeeklyEvent` 的 `filter` 是当前唯一的 O(n) 热路径。如果事件涨到几千条，可以预建「按 `week` 分桶」的索引。**在那之前不要动它。**
