
阶段 2 新增的 `majors.ts`，以及专业 / 项目相关的引擎改动，集中在**第 8 节**。

## 0. 全景：一次「去图书馆自习」到底发生了什么

先建立整体印象，细节后面再补。玩家点下「去图书馆自习」后：

```
GameEngine.takeAction('study')
  │
  ├─ 1. const from = log.length           记下日志起点（只返回本次新增的日志）
  │
  ├─ 2. 状态守卫                           已结束？有待处理事件？→ 直接 throw
  │
  ├─ 3. 查行动表 + 校验                    不存在？行动力不够？条件不满足？→ throw
  │
  ├─ 4. actionPoints -= 1
  ├─ 5. entry = pushLog('action', '你选择了「去图书馆自习」')
  │                                       ↑ 返回刚写入的条目，后面要补挂变化量
  ├─ 6. changes = applyEffects(action.effects)    学业+4 心情-2 健康-1（自动 clamp）
  │      entry.changes = changes                  ★补挂「回执」
  │
  ├─ 7. 如果行动力归零 → endWeek()
  │        │
  │        ├─ a. pushLog('每周固定衰减') + applyEffects(weeklyEffects)  ★也带回执
  │        │      学业/技能/社交/健康-1、心情-1、金钱-100
  │        ├─ b. rollWeeklyEvent()             掷 0.7 概率 → 过滤事件池 → 按权重抽 → triggerEvent
  │        │       └─ 有选项 → pending = 事件，停下等玩家
  │        └─ c. maybeAdvance()  ★时间推进的唯一闸门
  │                ├─ pending 非空？ → 什么都不做，等玩家选完
  │                ├─ 已是第 16 周？ → settleEnding()
  │                └─ 否则 → week+1，行动力重置
  │
  └─ 8. buildResult(from) → { logs: 新增日志, pending, ended }
         ↑ 每条日志可能带 changes（这一步实际改了多少属性）
```

★ `maybeAdvance()` 是整个引擎最精巧的地方，第 7 节会重点讲。

★ `pushLog` 返回条目、`applyEffects` 返回变化量，是「结算回执」功能的需要 ——
日志必须先写（这样效果里的 `log` 才排在它后面），而变化量只有结算完才知道，
所以只能「先写日志、后补回执」。第 6 节末尾会展开讲。

★ 阶段 2 又往引擎里加了两个东西：**专业**（你是谁 —— 一层可选的内容标签，第 8 节）
和**项目**（你能造出什么 —— 第二个会改状态的入口，§8.5）。
项目那套写法刻意和 `takeAction` 保持一致，仍然是
「守卫 → 先写日志 → 补回执 → 行动力归零则 `endWeek()`」。

## 1. TypeScript 速通（只讲你用得到的部分）

### 1.1 类型是「注解」，不是类

TS 的类型**只在编译期存在，运行时全部擦除**。

```ts
export interface Stats {
  academic: number
  social: number
}
```

编译成 JS 之后：

```js
// 什么都没有！interface 完全不产生代码
```

对比 Java：Java 的 interface 会变成 class 文件；TS 的不会。
所以你可以随便写类型，运行时零开销。这也是为什么 TS 能编译成 JS 给浏览器跑。

再看这一行：

```ts
export type RNG = () => number
```

- Java 里你会写成 `@FunctionalInterface interface RNG { double next(); }`
- C++ 里是 `std::function<double()>`
- Python 里其实就是一个「调用返回 float 的可调用对象」

`(参数) => 返回类型` 是函数类型。这里没写参数，所以是「无参、返回 number」。

### 1.2 `type` 和 `interface` 的区别

- `interface`：只能描述对象形状，可以「声明合并」（同名 interface 自动合并）
- `type`：什么都能起别名 —— 联合类型、函数类型、字符串字面量、元组……

经验法则：**描述对象用 `interface`，其余用 `type`**。本项目就是这么用的。

### 1.3 ★ 联合类型与「判别联合」（本项目最重要的一个概念）

**联合类型** `A | B` 表示「要么是 A，要么是 B」：

```ts
export type FlagValue = number | boolean
```

Java 里你只能用 `Object` 加 `instanceof` 判断，或者上一堆继承。
TS 的联合是「封闭的、编译期已知的」，因此编译器能精确推断。

**判别联合**（discriminated union，也叫 tagged union / 代数数据类型）：
给每个分支一个共同的**字面量字段**当作标签，这里是 `type`。

```ts
export type Condition =
  | { type: 'stat'; key: StatKey; op: CompareOp; value: number }
  | { type: 'flag'; key: string }
  | { type: 'week'; op: CompareOp; value: number }
  | { type: 'not'; condition: Condition }
  | { type: 'all'; conditions: Condition[] }
  | { type: 'any'; conditions: Condition[] }
  | { type: 'chance'; probability: number }
```

它同时是**类型**又是**数据**。你可以把它直接写进 JSON 里：

```ts
{ type: 'stat', key: 'academic', op: '>=', value: 85 }
```

这就是「数据驱动的 DSL」的全部秘密 —— 条件不是代码，是一个普通对象。

对比一下：如果用 Java 写，你得建一个 `Condition` 抽象类 + 8 个子类 + 一个 visitor；
用 Python 写，你得靠字典加一堆 `if 'key' in d`。TS 的判别联合是这三种语言里最舒服的。

### 1.4 ★ 类型收窄 + 穷尽性检查

判别联合最爽的地方：`switch` 到 `type` 之后，TS 自动知道这个分支有哪些字段。

```ts
switch (condition.type) {
  case 'stat':
    // 这里 TS 已经知道 condition 有 key / op / value
    // 写成 condition.probability → 立刻编译报错
    return compare(ctx.state.stats[condition.key], condition.op, condition.value)
  case 'chance':
    // 这里 TS 知道只有 probability
    return ctx.rng() < condition.probability
}
```

更狠的是**穷尽性检查**：如果你往 `Condition` 联合里加了第 10 个成员，
却忘了在 `evaluate` 里处理它，因为函数声明了返回 `boolean`，
TS 会发现「函数可能走到末尾却没有 return」并直接报错：

```
error TS2366: Function lacks ending return statement and
return type does not include 'undefined'.
```

**这就是「加功能时编译器帮你找全所有要改的地方」**。这是 TS 比 Java 的 `enum + switch`、
比 Python 的字典分发都强的地方 —— 不需要写任何测试就能保证分支不漏。

### 1.5 `keyof` / `Record`：类型的「单一真相源」

```ts
export interface Stats {
  academic: number
  social: number
  health: number
  mood: number
  money: number
  skill: number
}

export type StatKey = keyof Stats
// 等价于：'academic' | 'social' | 'health' | 'mood' | 'money' | 'skill'

export type StatRange = Record<StatKey, { min: number; max: number }>
// 等价于：{ academic: {min,max}; social: {...}; ... } 每一项都必须有
```

这两行带来一个很强的性质。**我实测过**：往 `Stats` 里加一个 `stress: number` 字段，
然后跑 `pnpm typecheck`，编译器准确报出 **3 处**需要同步的地方：

```
src/data/config.ts(7,14):     error TS2741: Property 'stress' is missing
                              in type 'StatRange'        ← STAT_RANGES 属性范围表
src/data/config.ts(16,14):    error TS2741: Property 'stress' is missing
                              in type 'Stats'            ← INITIAL_STATS 初始值表
src/engine/effects.ts(88,14): error TS2741: Property 'stress' is missing
                              in type 'Record<keyof Stats, string>'  ← STAT_LABELS 中文名表
```

你只改了 `Stats` **一处**，编译器就把所有需要同步的地方全列出来了，
而且**一行测试都不用跑**。注意 `types.ts` 自己不会报错 ——
因为 `StatKey` 和 `StatRange` 都是*派生*出来的，它们自动跟着变。

这就是「单一真相源 + 用类型做重构保险」。在 Java/C++ 里，
你得靠运行时单测或者全局搜索才发现漏了哪张表；Python 就更别提了。

（实验后已把 `stress` 还原。这类「临时改一下验证编译器行为」的小实验，
是学类型系统最快的方式。）

### 1.6 `?` 可选属性、`?.` 可选链、`??` 空值合并

```ts
export interface GameEvent {
  weight?: number        // 可选：可能是 number，也可能是 undefined
  requires?: Condition
}
```

读的时候用可选链：

```ts
if (event.choices && event.choices.length > 0) { ... }
```

这里的 `&&` 顺便做了类型收窄：`event.choices` 为真之后，TS 知道它不再是 `undefined`。

`??` 是**空值合并**，只在左边是 `null` / `undefined` 时才用右边的值：

```ts
const picked = pickWeighted(pool, (event) => event.weight ?? 1, this.rng)
//                                              ↑ weight 没写就用 1

this.seed = options.seed ?? randomSeed()
```

⚠️ **`??` 和 `||` 的区别是个经典 bug 来源**：

```ts
const a = 0
a || 5   // → 5   因为 0 是 falsy！
a ?? 5   // → 0   只在 null/undefined 时才回退
```

所以「用户传了 `seed: 0`」这种合法输入，用 `||` 会被错误地当成没传。
Python 里没有这个问题（只有 `or`，行为同 `||`），所以特别容易带过来。

### 1.7 `import type`：只导入类型

```ts
import type { ActionDef, GameEvent, TurnResult } from './types'
```

为什么要专门加 `type`？因为 `tsconfig.json` 里开了 `verbatimModuleSyntax: true`，
它要求「只用于类型的导入」必须写成 `import type`。

原因是真实存在的：类型在编译后被擦除，
如果你用普通 `import { ActionDef }` 导入一个 interface，编译出的 JS 会保留这行导入，
运行时就会去找一个根本不存在的导出 → 报错。`import type` 保证这行被彻底删掉。

### 1.8 函数是一等公民 + 闭包（JS 的灵魂）

JS 里函数可以当参数传、当返回值返回、被变量接住：

```ts
export function pickWeighted<T>(
  items: readonly T[],
  weightOf: (item: T) => number,   // ← 传入一个「怎么算权重」的函数
  rng: RNG,
): T | null
```

这在 Java 里是 `Function<T, Double>`，在 C++ 里是模板 + `std::function`，
在 Python 里就是传个 lambda。JS 的版本最轻，连 lambda 语法都一样。

**闭包**就是把局部变量「包」进函数里带走。`mulberry32` 是绝佳例子：

```ts
export function mulberry32(seed: number): RNG {
  let a = seed >>> 0          // ← 这个 a 被下面的函数记住了
  return function next(): number {
    a = (a + 0x6d2b79f5) >>> 0   // ← 每次调用都改同一个 a
    let t = a
    ...
  }
}
```

`mulberry32` 返回后，局部变量 `a` 本该销毁，但返回的函数一直引用它，
所以 `a` 活了下来，而且**每次调用 `next()` 都在改同一个 `a`**。

这就是「状态藏在闭包里」的用法。在 C++ 里等价于一个带成员变量的仿函数对象，
在 Java 里等价于一个持有 field 的匿名类实例。JS 里只要几行。

顺带解释那段位运算（它是标准的 mulberry32）：
- `>>>` 是**无符号右移**，`x >>> 0` 是把 x 强行转成 32 位无符号整数（截断高位）
- `^` 是异或，`Math.imul` 是 32 位整数乘法（普通 `*` 在超过 2^53 后会丢精度）

这套「位混合」是伪随机数的经典套路：把种子搅得足够乱，
再除以 2^32 归一化到 `[0, 1)`。

### 1.9 `this` 是动态的（和 Java/C++ 完全不同）

```ts
availableActions(): ActionDef[] {
  const ctx = this.createContext()
  return this.data.actions.filter(
    (action) => action.cost <= this.state.actionPoints && evaluate(action.requires, ctx),
  )
}
```

注意 `filter` 里用的是**箭头函数** `(action) => ...`。
箭头函数不绑定自己的 `this`，它会**捕获外层的 `this`**（也就是这个 engine 实例）。

如果这里写成普通函数：

```ts
return this.data.actions.filter(function (action) {
  return action.cost <= this.state.actionPoints   // ← this 是 undefined，运行时报错！
})
```

在 JS 里，普通函数的 `this` 取决于**怎么被调用**，而不是定义在哪里。
`filter` 回调是被当作普通函数调用的，所以 `this` 是 `undefined`（严格模式下）。

**在 TS 里写回调，默认用箭头函数。** 这是从 Java/C++ 过来最容易翻车的地方。

### 1.10 `private` 只是编译期的建议

```ts
export class GameEngine {
  private readonly state: GameState
```

⚠️ TS 的 `private` **编译后完全消失**，运行时你照样能 `engine.state` 访问到它
（只是编辑器会划红线）。Java 的 `private` 是 JVM 层面强制的，TS 不是。

真要运行时也私有，得用 `#state` 这种原生私有字段语法。本项目用的是编译期 `private`
—— 够用，而且更简单。

`readonly` 同理，只是编译期不允许重新赋值。

### 1.11 `sort` 会改原数组（血的教训）

```ts
const sorted = [...this.data.endings].sort((a, b) => a.priority - b.priority)
```

`[...arr]` 是**展开运算符**，作用是复制一份数组（等价 Python 的 `arr[:]`、
Java 的 `new ArrayList<>(arr)`）。

为什么要复制？因为 **JS 的 `Array.prototype.sort` 是原地排序，会修改原数组**。

如果不复制，`this.data.endings` 的顺序就被永久改变了 ——
而 `GAME_DATA` 是全局共享的数据，第二局游戏就会受影响。这类 bug 极难查。

（`toSorted()` 是新 API，返回新数组不改原数组，更安全。
以后你写新代码可以优先用它。）

顺便注意：JS 的 `sort` **默认按字符串排序**，所以 `[10, 9, 100].sort()` 得到
`[10, 100, 9]`。必须传比较函数。Python 的 `sorted()` 是稳定且不改原数组的，别搞混。

### 1.12 解构赋值与展开

```ts
const state = { ...createInitialState(GAME_DATA.config), ...overrides }
```

`{ ...obj }` 是浅拷贝；`{ ...a, ...b }` 是合并，后面的覆盖前面的。
Python 里是 `{**a, **b}`，功能一样。

```ts
const { state, config, rng } = ctx        // 对象解构
const [first, second] = list              // 数组解构
```

Python 的 `a, b = t` 是同一回事。

### 1.13 模块与 `async/await`

```ts
// 导出
export function evaluate(...) { }
export type Condition = ...
export class GameEngine { }

// 导入
import { evaluate } from './conditions'
import type { Condition } from './types'
```

`./conditions` 对应 `src/engine/conditions.ts`。JS 的模块路径**必须带 `./` 或 `../`**
（Python 的 `from .conditions import` 带点，Java 靠 classpath 不带路径，JS 两种都不像）。

`async/await` 是 Promise 的语法糖（类似 Python 的 `async`/`await`，C++20 的协程）：

```ts
const answer = await readLine(lines, '> ')   // 等这一行读完再往下走
```

关键区别：**Python 的 asyncio 是你自己起事件循环，JS 的事件循环天生就在跑**。
浏览器 / Node 自带，不需要 `asyncio.run()`。

## 2. `types.ts` 逐段讲解

### 2.1 `RNG`

```ts
export type RNG = () => number
```

一个类型别名指向函数类型。整份代码里，**游戏逻辑用到的随机数从不由 `Math.random()` 产生**，
永远通过 `RNG` 注入（唯一的例外是没传种子时的 `randomSeed()`，它用 `Math.random()`
生成一个种子，之后就与它无关了）。这一个决定带来了可复现性（见第 3 节）。

### 2.2 `Stats` / `StatKey` / `StatRange`

```ts
export interface Stats { academic: number; social: number; ... }

export type StatKey = keyof Stats

export type StatRange = Record<StatKey, { min: number; max: number }>
```

`Stats` 是**唯一的真相源**。`StatKey`（键的联合）和 `StatRange`（必须覆盖所有键的映射）
都是从它派生出来的，所以不存在「加了属性忘了加范围」这种可能。

### 2.3 `FlagValue` / `Flags`

```ts
export type FlagValue = number | boolean
export type Flags = Record<string, FlagValue>
```

`Record<string, FlagValue>` 等价于 Java 的 `Map<String, Object>`（但键必须是字符串），
或 Python 的 `dict[str, int|bool]`。

为什么 flag 要支持 `number`？因为需要「计数型」flag，比如 `穷困周数`：

```ts
{ type: 'addFlag', key: '穷困周数', delta: 1 }   // 累加
{ type: 'flagAtLeast', key: '穷困周数', value: 4 } // 判断 >= 4
```

布尔型则表示「是否发生过」，比如 `加入集训队`。

### 2.4 `Condition`：条件 DSL

这是整个项目最核心的类型。逐条看设计意图：

| 分支 | 用途 | 为什么需要 |
|---|---|---|
| `stat` | 属性比较 | 最常见的判断 |
| `flag` | flag 为真 | 「加入社团了吗」 |
| `flagEq` | flag 等于某值 | 精确匹配 |
| `flagAtLeast` | 数值 flag ≥ 某值 | 「穷困周数 ≥ 4」 |
| `week` | 周数比较 | 「第 9 周之后才能投简历」 |
| `not` | 取反 | 组合 |
| `all` / `any` | 与 / 或 | 组合。**空 `all` 恒真，空 `any` 恒假** |
| `chance` | 概率 | 「30% 概率」 |

注意 `not` / `all` / `any` 的字段类型又是 `Condition` 本身 ——
这叫**递归类型**，让条件可以无限嵌套。TS 完全允许，因为类型定义是惰性的。

「空 `all` 恒真」这一点被用来做**兜底结局**（见 `endings.ts` 最后一条），
这是个很漂亮的技巧：与其写 `{ type: 'stat', key: 'academic', op: '>=', value: 0 }`
这种「为了恒真而硬凑」的条件，不如定义「空集合上的 `every()` 为真」——
这在数学上也是良定义的（vacuous truth）。

### 2.5 `EvalContext`：为什么要把 `config` 和 `rng` 一起传

```ts
export interface EvalContext {
  state: GameState
  config: GameConfig
  rng: RNG
}
```

求值条件时只需要 `state` 其实就够了，但 `chance` 需要随机数、属性夹取需要 `config`。
把它们打包成一个 context 对象传参，好处是：

- 以后要加东西（比如「当前回合数」「玩家存档时间」）只需改一个类型
- 函数签名不会越来越长

这叫 **Parameter Object** 模式。Java/C++ 里同样适用。

### 2.6 `Effect`：效果 DSL

和 `Condition` 同构，但表达的是「做什么」：

```ts
| { type: 'stat'; key: StatKey; delta: number }        // 属性增减
| { type: 'setFlag'; key: string; value: FlagValue }   // 设置 flag
| { type: 'addFlag'; key: string; delta: number }      // 累加
| { type: 'log'; text: string }                        // 写日志
| { type: 'if'; requires: Condition; effects: Effect[] }        // 条件效果
| { type: 'branch'; options: { weight: number; effects: Effect[] }[] } // 概率分支
| { type: 'end'; endingId: string }                    // 直接结束
```

`if` 和 `branch` 的字段里又含 `Effect[]`，同样是递归类型
—— **效果可以嵌套效果**，这就是为什么数据文件能表达「40% 概率拿到 Offer，
拿到的话心情 +15 并设置 flag」这种复杂逻辑，而引擎只有 20 行。

`branch` 的存在理由写在注释里了：`if + chance` 配 `if + not chance`
是**两次独立随机**，可能出现两个分支都不中。概率分支必须一次抽完。
这个坑我第一版就踩了。

### 2.7 内容定义三件套：`ActionDef` / `GameEvent` / `Ending`

```ts
export interface ActionDef {
  id: string
  label: string
  description: string          // 只写氛围文案，不写数值
  cost: number                 // 消耗行动点
  requires?: Condition         // 不满足则不出现在列表里
  effects: Effect[]
  majors?: MajorTags           // 阶段 2 加的：专属专业；不写 = 全专业共享
}
```

注意 `description` 里**故意不写数值**。数值由 `describeEffects(action.effects)`
自动生成（见 `effects.ts`）。这是个很实际的教训：

> 原来的 `description` 是「学业 +6，心情 -3，健康 -2」。
> 后来我调平衡把 `+6` 改成 `+4`，忘了改这行文案，
> 于是 CLI 里显示的效果和实际结算不一致。

**能推导出来的信息就不要手写第二份。** 这条原则上到 UI、下到文档都适用。

```ts
export interface GameEvent {
  id: string
  title: string
  text: string
  category: EventCategory       // 目前只有 'random'，留了扩展位
  weight?: number               // 权重，默认 1
  repeatable?: boolean          // 默认 false → 一局只触发一次
  requires?: Condition
  choices?: Choice[]            // 有选项 → 等玩家选
  effects?: Effect[]            // 没选项 → 直接结算
}
```

`repeatable` 的默认值语义要注意：**默认 `false`（只触发一次）**，
代码里靠 `!event.repeatable` 来判断。这种「默认值由代码而不是字段决定」的写法
在 TS 里很常见，因为 TS 无法给 interface 字段设默认值。

```ts
export interface Ending {
  id: string
  title: string
  text: string
  priority: number              // 小的先判
  requires: Condition
}
```

`priority` 让结局形成一条**判定链**：坏结局优先，普通结局兜底。

阶段 2 给 `ActionDef` / `GameEvent` / `Ending` 各加了一个可选字段
`majors?: MajorTags`（「专属专业；不写 = 全专业共享」），
外加稍后会讲到的 `SummaryRule.majors`。第 8 节专门讲它。

### 2.8 `GameState`：存档就是这个对象

```ts
  flags: Flags
  seenEvents: string[]
  log: LogEntry[]
  endingId: string | null

```

`log` 里的元素长这样（`changes` 是后加的，第 6 节末尾会讲它为什么存在）：

```ts
export interface LogEntry {
  week: number
  kind: 'action' | 'event' | 'system' | 'ending'
  text: string
  changes?: StatChange[]        // 这条日志造成的**实际**属性变化；没变化时字段不存在
}

export interface StatChange {

}
```

设计约束是「**纯 JSON、无循环引用、无函数**」。
这样它能被 `JSON.stringify` 直接写进 `localStorage`，
也能被 `structuredClone` 深拷贝，以后做存档功能零成本。

注意 `endingId: string | null` 而不是 `string | undefined`。
`null` 在 JSON 里是合法的，`undefined` 会被 `JSON.stringify` **直接丢掉**，
导致存档读回来少一个字段。**要进 JSON 的状态，用 `null` 不用 `undefined`。**

`majorId` 是阶段 2 加的（§8.2）：它必须进 `state`，因为存档读回来时要能还原
「你是谁」—— 专业决定了哪些内容可见。注意它是 `string` 而不是 `string | null`，
理由见 §8.2（e）。

### 2.9 `TurnResult`：UI 只需要看这个

注意 `TurnResult` **本身**没有增字段 —— 结算回执是挂在 `logs[i].changes` 上的。
这个设计选择的好处就在这里：给 `LogEntry` 加一个可选字段是非破坏性的，
而给 `TurnResult` 加字段会让所有构造它的地方都要改。

## 3. `rng.ts`：为什么不用 `Math.random()`

```ts
export function mulberry32(seed: number): RNG
export function randomSeed(): number
export function pickWeighted<T>(items, weightOf, rng): T | null
export function pickOne<T>(items, rng): T | null
```

三个理由：

1. **测试可以断言随机行为**。带种子意味着「给定输入必然给定输出」，
   于是 `expect(play(seed)).toBe(play(seed))` 这种测试才成立
   （`tests/engine.test.ts` 里用的种子是 1、2、3、100、2025）。
   用 `Math.random()` 的话，随机相关的代码根本没法测。

2. **玩家可以复现同一局**。CLI 启动时会打印种子。以后做存档回放、
   分享「我这局贼离谱你自己玩一遍」都靠它。

3. **数值平衡可以批量模拟**。`pnpm simulate -- --games 500` 一次跑 3000 局，
   全部种子确定，所以调完数值重跑，差异一定来自数值而不是随机噪声。
   （不带参数时默认每种风格 200 局，共 1200 局。）

`pickWeighted` 的算法就是**轮盘赌**：

```ts
const total = weights.reduce((sum, w) => sum + Math.max(0, w), 0)  // 权重总和
if (total <= 0) return null
let roll = rng() * total          // 在 [0, total) 里掷一个点
for (...) {
  roll -= w                        // 依次扣掉每个权重
  if (roll < 0) return items[i]    // 扣成负数说明落在这个区间里
}
```

末尾还有一段「浮点误差兜底」：因为 `rng()` 的结果是浮点数，
极端情况下循环结束 `roll` 仍可能是极小的正数，所以补一个「返回最后一个非零权重项」。

`Math.max(0, w)` 是为了防负数权重 —— **防御式编程**：
即使数据写错了，也只是这项不被抽中，而不是整个抽奖逻辑崩掉。

## 4. `conditions.ts`：递归求值

```ts
function compare(a: number, op: CompareOp, b: number): boolean {
  switch (op) {
    case '>=': return a >= b
    case '<=': return a <= b
    ...
    default: return false
  }
}
```

三层结构：`compare` 处理单次数值比较，`evaluate` 递归处理条件树。

```ts
export function evaluate(condition: Condition | undefined, ctx: EvalContext): boolean {
  if (condition === undefined) return true     // ★ 没写条件 = 恒真
  switch (condition.type) {
    case 'stat':  return compare(ctx.state.stats[condition.key], condition.op, condition.value)
    case 'flag': {
      const value = ctx.state.flags[condition.key]
      return value === true || (typeof value === 'number' && value !== 0)
    }
    ...
    case 'not':  return !evaluate(condition.condition, ctx)
    case 'all':  return condition.conditions.every((child) => evaluate(child, ctx))
    case 'any':  return condition.conditions.some((child) => evaluate(child, ctx))
    case 'chance': return ctx.rng() < condition.probability
    case 'seenEvent': return ctx.state.seenEvents.includes(condition.id)
  }
}
```

几个值得注意的点：

**（a）`condition === undefined` 返回 `true`。**
这样一个「可选条件」的语义就很自然：不写 `requires` 就等于「总是触发」。
调用方（引擎）就不用每次都判断 `requires` 是否存在。

**（b）`typeof value === 'number'` 是运行时类型检查。**
因为 flag 的静态类型是 `FlagValue = number | boolean`，
但运行时它可能是 `undefined`（键不存在）。
`typeof` 在 TS 里同时起到「运行时判断」和「类型收窄」两个作用
—— `&&` 右边 TS 就知道 `value` 是 `number` 了。

**（c）`flag` 分支把「非 0 数字」也算作真。**
所以 `穷困周数: 3` 既可以用 `flagAtLeast` 判断，也可以用 `flag` 判断「至少穷困过一次」。

**（d）`every` / `some` 就是** Python 的 `all()` / `any()`、Java 的 `stream().allMatch()`。
空数组时：`every` 返回 `true`，`some` 返回 `false`。**兜底结局正是靠这个特性。**

**（e）`compare` 里的 `default: return false`。**
这其实削弱了穷尽性检查 —— 如果我以后往 `CompareOp` 加个 `'startsWith'`，
编译器不会报错，那个算子会静默地永远返回 `false`。
严格做法是删掉 `default` 并声明返回类型，让 TS 来保证穷尽。
这是个真实的小妥协，你可以当成「练习」去改掉它，看看 TS 会不会在别处报错。

## 5. `state.ts`：可变内部 + 不可变对外

```ts
export function createInitialState(
  config: GameConfig,
  majorId: string,
  initialStats: Stats,
): GameState {
  return {
    week: 1,
    actionPoints: config.actionPointsPerWeek,
    stats: { ...initialStats },   // ★ 复制！不能直接引用调用方传进来的对象
    flags: {},
    seenEvents: [],
    log: [],
    endingId: null,
    majorId,
  }
}
```

（阶段 2 起签名多了 `majorId` 与 `initialStats` 两个参数 —— 为什么专业知识不进
这个文件，§8.6 会讲。）

`{ ...initialStats }` 那个复制**至关重要**。
`initialStats` 是调用方算好传进来的（基准属性 + 专业偏移，见 §8.3）。
如果写成 `stats: initialStats`，那么 `stats` 和调用方那份对象就是**同一个对象**：
调用方只要还留着这个引用，本局状态就可能被从背后改掉；
而谁要是图省事写成 `createInitialState(config, id, config.initialStats)`，
全局的初始配置就会被污染，第二局游戏从被改过的值开始 ——
这种 bug 在多人游戏和测试里会要命。

**原则：凡是把外部可变对象放进可变状态的地方，都要复制。**
阶段 2 只是换了参数的来源，这条原则不变 —— 它约束的是「边界」，不是某个具体变量。

```ts
export function pushLog(state: GameState, kind: LogEntry['kind'], text: string): LogEntry {
  const entry: LogEntry = { week: state.week, kind, text }
  state.log.push(entry)
  return entry                    // ★ 返回条目，而不是 void
}
```

**为什么返回条目**：结算回执需要「把实际变化量挂到刚写的那条日志上」。
但日志必须先写（效果里的 `{type:'log'}` 要排在它后面，叙事顺序才对），
而变化量只有 `applyEffects` 跑完才知道 —— 所以只能「先写、后补」。
返回条目让调用方能补挂 `entry.changes`。

注意参数类型 `LogEntry['kind']` —— **索引访问类型**，等价于
`'action' | 'event' | 'system' | 'ending'`。这样以后往 `LogEntry` 加一种 `kind`，
这个函数的调用点会自动获得更强的类型检查。

```ts
export function cloneState(state: GameState): GameState {
  return structuredClone(state)
}
```

`structuredClone` 是 JS 内置的**深拷贝**（比 `JSON.parse(JSON.stringify(x))` 好，
因为它正确处理 `Date`、`Map`、`Set` 和循环引用）。

**为什么引擎内部可变、对外却返回副本？**

引擎内部（`takeAction` / `applyEffects`）到处在直接改 `this.state`，
这样写起来最直观、性能也最好。但如果把内部对象直接暴露出去：

```ts
const s = engine.getState()
s.stats.academic = 0     // 从外部改坏了引擎！
```

所以 `getState()` 永远返回 `cloneState(this.state)`。这是
**「内部可变、边界不可变」**的模式。

代价是每次查询都深拷贝一次。本项目状态很小（几十个字段），
完全无所谓。等状态变大再考虑优化（比如改用不可变数据结构 + 结构共享）。
先正确，再快。

## 6. `effects.ts`：递归应用 + 自动夹取 + 结算回执

```ts
export function applyEffects(ctx: EvalContext, effects: readonly Effect[]): StatChange[] {
  const changes = new Map<StatKey, StatChange>()
  applyEffectsInto(ctx, effects, changes)

  // 净变化为 0 且没触顶的不显示（避免「+0」噪声）；
  // 但触顶的 0 变化必须保留 —— 「这次白费了」本身就是最重要的反馈
  return [...changes.values()].filter(
    (change) => change.delta !== 0 || change.capped !== undefined,
  )
}

/** 内部递归用：把变化累加进调用方传进来的同一张表 */
function applyEffectsInto(ctx, effects, changes: Map<StatKey, StatChange>): void {
  for (const effect of effects) {
    applyEffect(ctx, effect, changes)
  }
}

function applyEffect(ctx: EvalContext, effect: Effect, changes: Map<StatKey, StatChange>): void {
  const { state, config } = ctx
  switch (effect.type) {
    case 'stat': {
      const range = config.statRanges[effect.key]
      const current: number = state.stats[effect.key]
      const desired = current + effect.delta
      const next = clamp(desired, range.min, range.max)
      state.stats[effect.key] = next

      // 被截断说明撞到了上限或下限，记下来让 UI 能解释「为什么只加了这么点」
      let capped: 'min' | 'max' | null = null
      if (next !== desired) capped = desired > next ? 'max' : 'min'

      recordChange(changes, effect.key, next - current, capped)
      break
    }
    ...
    case 'if':
      if (evaluate(effect.requires, ctx)) {
        applyEffectsInto(ctx, effect.effects, changes)      // ★ 递归
      }
      break
    case 'branch': {
      const picked = pickWeighted(effect.options, (option) => option.weight, ctx.rng)
      if (picked) applyEffectsInto(ctx, picked.effects, changes)   // ★ 递归
      break
    }
    case 'end':
      state.endingId = effect.endingId
      break
  }
}
```

设计要点：

**（a）`clamp` 是唯一改属性的入口。**
所以「属性永远在合法范围内」是**结构性保证**，不靠开发者自觉。
`statRanges` 从 `config` 来，所以「学业上限是 100」这种规则只写一次。

**（b）递归让数据可以无限嵌套。**
`if` 里有 `effects`，`effects` 里还能有 `if`，还能有 `branch`，还能再嵌……
引擎代码量不变，表达力无限。这就是「组合优于继承」。
Java 里你得用组合模式 + 一堆类；Python 里靠字典递归；TS 靠判别联合 + 递归。

**（c）`readonly Effect[]`。**
`readonly T[]` 表示「这个数组我不会改」。编译器会阻止你写 `effects.push(...)`。
这是**给调用方的契约**，比 Java 的 `final` 参数强（Java 的 `final` 只锁引用，
不锁内容）。传进来的 `effects` 是全局共享的数据，万一被改了就是灾难。

**（d）★ 返回的是「实际」变化量，不是「声明」的。**
这是本文件最值得琢磨的一处：

```ts
const desired = current + effect.delta      // 声明要加多少
const next = clamp(desired, ...)            // 实际只能加到这里
recordChange(changes, effect.key, next - current, capped)   // 记实际值
```

`next - current` 而不是 `effect.delta` —— 学业 98 时 `delta` 是 4，但实际只加了 2。
**回执必须报 2。** 如果报 4 让玩家高兴，他会一直做无效投入，
永远学不会「该换方向了」。

`changes` 用 `Map<StatKey, StatChange>` 而不是数组，是为了让同一次结算里
对同一属性的多次变化（比如每周衰减 −1 加上穷困 −8）**自动汇总成净值 −9**。
递归时把同一张表往下传，所以 `if` / `branch` 里的变化也会累加进这次的总额。

**（d）`case 'stat'` 显式标注了 `const current: number`。**
其实 TS 能推断，标出来是为了可读性 —— 提醒读者这里有类型。

最后是 `describeEffects`：

```ts
export function describeEffects(effects: readonly Effect[]): string {
  const parts: string[] = []
  const walk = (list: readonly Effect[]): void => {
    for (const effect of list) {
      if (effect.type === 'stat') {
        const sign = effect.delta >= 0 ? '+' : ''
        parts.push(`${STAT_LABELS[effect.key]} ${sign}${effect.delta}`)
      } else if (effect.type === 'if') {
        walk(effect.effects)      // 递归进 if
      } else if (effect.type === 'branch') {
        for (const option of effect.options) walk(option.effects)   // 递归进 branch
      }
    }
  }
  walk(effects)
  return parts.join(' / ')
}
```

这就是把 `ActionDef.description` 里的数值删掉的底气 —— UI 直接
`describeEffects(action.effects)` 就能得到「学业 +4 / 心情 -2 / 健康 -1」，
数据改了显示自动跟着变。

注意它把 `if` 和 `branch` 里**所有分支**的属性都列了出来，
所以「50% 结果A，50% 结果B」会显示成两组的并集。
对行动来说够用了（行动一般没有 branch），但对事件选项就不太合适 ——
**这是个以后可以改进的点**（比如只显示 `if` 里的非概率部分）。

### 6.1 ★ 预告 vs 回执：为什么它们必须用两套逻辑

到这里你已经见过两个都跟「属性变化」有关的东西，别把它们搞混：

| | `describeEffects(effects)` | `applyEffects(ctx, effects)` 的返回值 |
|---|---|---|
| 类型 | `string`（给人看的文本） | `StatChange[]`（给程序用的数据） |
| 回答 | 「这个效果**说**它会做什么」 | 「**实际**发生了什么」 |
| 学业 98 时 | `学业 +4` | `{key:'academic', delta:2, capped:'max'}` |
| 有 `branch` 时 | 所有分支的并集 | 只算真正命中的那个分支 |
| 消耗随机数吗 | 否（纯读数据） | 是（`chance` / `branch` 会抽） |
| 用在哪 | 行动菜单的**灰色**预告 | 结算的**彩色**回执 |

**为什么不能图省事只留一个？**

因为两者在简单情形下确实能凑合统一，但**一旦出现属性上限、`if` 条件、`branch` 概率分支，
它们必然分叉**。这时候「只留一个」就等于让其中一个必然出错：

- 只留 `describeEffects` → 回执会撒谎（显示 `+4` 而实际 `+2`），
  玩家基于假信息做决策，**比没有信息更糟**
- 只留 `applyEffects` → 菜单得先跑一遍效果才能显示预告，那会**消耗随机数**并真的改状态

**一个可以带走的经验**：两个东西「看起来描述同一件事」，不代表它们可以共用实现 ——
先问「它们对什么**数据源**负责」。预告对声明负责，回执对结果负责，
这是两个不同的真相，所以必须两套。

这条原则的完整版在 [设计文档 §4.5](./设计文档.md#45-反馈设计回执--预告)，
包括它是被一次真实的玩家反馈逼出来的（839 个项次核对后发现数值全对，
真正的问题是文案有歧义）。

## 7. `engine.ts`：核心是「相位控制」

### 7.1 构造：依赖注入

```ts
constructor(data: GameData, options: NewGameOptions = {}) {
  this.data = data
  this.seed = options.seed ?? randomSeed()
  this.rng = mulberry32(this.seed)
  this.major = resolveMajor(data, options.majorId)

  this.state = createInitialState(
    data.config,
    this.major.id,
    // 基准属性 + 专业偏移，并且夹进合法区间（开局这一帧同样受 I1 约束）
    applyStatBonus(data.config.initialStats, this.major.statBonus, data.config.statRanges),
  )
  ...
}
```

三处注入（第三处是阶段 2 加的）：
- `data` 从外部传 → 换一套内容不用改引擎
- `options.seed` 从外部传 → 测试完全可复现
- `options.majorId` 从外部传 → 换一个专业不用改引擎

（`resolveMajor` / `applyStatBonus` 这两行是阶段 2 加的，展开在 §8.4（a）。）

`options: NewGameOptions = {}` 是**默认参数**：不传时用空对象，
所以 `new GameEngine(DATA)` 和 `new GameEngine(DATA, { seed: 1 })` 都能用。
（等价 Python 的 `options=None` + `if options is None: options = {}`，
但 JS 的默认参数更简洁。注意这里不存在 Python「可变默认参数」的坑。）

`this.seed = options.seed ?? randomSeed()` 必须**先算 seed 再建 rng**，
因为同一个 seed 既要给 rng 又要留着打印给玩家。

### 7.2 只读查询：给 UI 用的窄接口

```ts
getState(): GameState            { return cloneState(this.state) }
getPending(): GameEvent | null   { return this.pending }
isEnded(): boolean               { return this.state.endingId !== null }
getMajor(): MajorDef             { return this.major }            // 阶段 2
getProjects(): ProjectView[]     { ... }                          // 阶段 2
availableActions(): ActionDef[]  { ... }
getPendingChoices(): ChoiceView[] { ... }
```

（`getMajor()` / `getProjects()` 是阶段 2 加的窄接口，
前者见 §8.4（b），后者见 §8.5（a）。）

`getPendingChoices()` 特别值得看：

```ts
getPendingChoices(): ChoiceView[] {
  if (!this.pending) return []
  const ctx = this.createContext()
  return (this.pending.choices ?? []).map((choice) => ({
    choice,
    enabled: evaluate(choice.requires, ctx),
  }))
}
```

它把「选项」和「选项可不可用」**一起算好**给 UI。
UI 不需要自己调 `evaluate`，也不需要知道条件 DSL 长什么样。

这就是为什么 CLI 能把不可用选项灰掉、`simulate.ts` 能自动过滤掉不可选项，
而它们俩都不用写一行条件判断逻辑。**把判断留给引擎，UI 只负责显示。**

### 7.3 ★ `maybeAdvance()`：唯一的「时间推进闸门」

这是全篇最重要的一段：

```ts
private maybeAdvance(): void {
  if (this.pending !== null) return          // ① 有事件没处理 → 冻结时间
  if (this.state.endingId !== null) return   // ② 已结束 → 冻结时间
  if (this.state.week >= this.data.config.totalWeeks) {
    this.settleEnding()                      // ③ 学期结束 → 结算结局
    return
  }
  this.state.week += 1                       // ④ 正常推进
  this.state.actionPoints = this.data.config.actionPointsPerWeek
  pushLog(this.state, 'system', `—— 第 ${this.state.week} 周开始 ——`)
}
```

它只被两个地方调用：

```ts
private endWeek(): void {          // 行动力耗尽时
  const settlement = pushLog(this.state, 'system', '每周固定衰减')
  const changes = applyEffects(...weeklyEffects)
  if (changes.length > 0) settlement.changes = changes
  this.rollWeeklyEvent()
  this.maybeAdvance()              // ← 调用点 1
}

choose(choiceIndex: number): TurnResult {
  ...
  this.pending = null
  const entry = pushLog(this.state, 'action', `你的选择：${choice.label}`)
  const changes = applyEffects(...choice.effects)
  if (changes.length > 0) entry.changes = changes
  this.maybeAdvance()              // ← 调用点 2
  ...
}
```

> ⚠️ 注意 `endWeek` 里那句 `'每周固定衰减'` 的文案。它之前叫「第 N 周结算」，
> 结果被玩家读成「本周总结」—— 但这条只报告固定衰减，本周的行动效果在自己的行上。
> 玩家拿它去对属性条的实际变化，就会以为数字错了。
> **文案歧义会被当成数值 bug 来报**，所以措辞要刻意避免这种误读。

**为什么这样设计？**

考虑这个场景：第 5 周行动力用完了，触发了一个「室友通宵打游戏」事件，
事件有三个选项要玩家选。

- `endWeek()` 结算完本周、抽到事件、把 `pending` 设好，然后调 `maybeAdvance()`
- `maybeAdvance()` 看到 `pending !== null`，**什么都不做就返回了**
- 于是 `week` 还是 5，玩家必须先处理事件
- 玩家 `choose(1)` → `pending = null` → 再次 `maybeAdvance()` → 这次才 `week = 6`

**时间推进的逻辑只写了一遍，而且它自己知道什么时候不该推进。**
UI 完全不需要判断「现在能不能点下一周」——引擎已经挡住了。

对比一下常见的烂写法：把「推进周数」放在 UI 里，或者散落在三四个方法里，
每次都加一句 `if (hasPendingEvent) return`。那种代码一旦漏加一处，
就会出现「事件还没选完就跳到下一周」的 bug，而且极难复现。

这里还有一个**隐藏的正确性**：`maybeAdvance()` 的第 ③ 分支
（结算结局）放在「推进周数」之前。所以第 16 周用完行动力时，
先结算本周事件，再判结局，不会出现「第 17 周」这种越界。

### 7.4 `takeAction` 的守卫顺序

```ts
if (this.state.endingId !== null) throw new Error('游戏已经结束了')
if (this.pending !== null) throw new Error('还有未处理的事件，请先做出选择')

const action = this.data.actions.find((item) => item.id === actionId)
if (!action) throw new Error(`未知行动: ${actionId}`)
// 专业可见性也要在这里挡一道：availableActions() 过滤过，但 takeAction 是公开 API，
// 不能假设调用方一定先过滤（fail fast 的一致性）
if (!matchesMajor(action.majors, this.major.id)) {
  throw new Error(`行动不属于本专业(${this.major.id}): ${actionId}`)
}
if (action.cost > this.state.actionPoints) throw new Error('行动力不足')
if (!evaluate(action.requires, this.createContext())) throw new Error(`行动条件不满足: ${actionId}`)
```

**先检查能不能做，再做。** 一旦开始改状态就不再回滚 ——
所以所有校验必须前置。这是「fail fast + 事务性」的思路。

（`matchesMajor` 那一行是阶段 2 加的。它守的是「公开 API 不假设调用方」这条一致性：
`availableActions()` 已经把别的专业的行动过滤掉了，但 `takeAction()` 是公开方法，
不能假设调用方一定先过滤过。同一行守卫在 `investProject()` 里也出现了一次，见 §8.5（b）。）

用 `throw` 而不是返回错误码，是 JS/TS 的惯例（Python 用异常，Java 用异常，
C++ 常常用错误码）。**抛异常意味着「调用方写错了」**，
而调用方（UI）本来就应该先用 `getPending()` / `availableActions()` 过滤掉非法操作。

我在写测试时正因为这个约定被教育了一次：
测试里图省事写 `engine.choose(0)`，结果 0 号选项是「换主板（需要 1200 元）」，
条件不满足 → 直接抛错。**这个抛错是好事**，它暴露了我测试写得不对，
而不是引擎有问题。修法是测试里先按 `enabled` 过滤。

### 7.5 `rollWeeklyEvent`：事件池的过滤与抽取

```ts
private rollWeeklyEvent(): void {
  if (this.rng() >= this.data.config.weeklyEventChance) return   // 先掷「本周有没有事件」

  const ctx = this.createContext()
  const pool = this.data.events.filter((event) => {
    if (!matchesMajor(event.majors, this.major.id)) return false
    if (event.category !== 'random') return false
    if (!event.repeatable && this.state.seenEvents.includes(event.id)) return false
    return evaluate(event.requires, ctx)
  })

  const picked = pickWeighted(pool, (event) => event.weight ?? 1, this.rng)
  if (picked) this.triggerEvent(picked)
}
```

四层过滤（第 1 层是阶段 2 加的）：
1. 是不是本专业可见的（`matchesMajor`）
2. 类别对不对
3. 是不是已经触发过（非重复事件查 `seenEvents`）
4. 触发条件满不满足

专业过滤必须放在最前面：`evaluate` 可能消耗随机数（`chance` 分支），
别的专业的事件一旦被求值，就会从本局的随机流里偷走一个随机数 ——
同种子的对局立刻变形。放在前面，它们连条件都不会被碰到。

然后按 `weight`（默认 1）加权随机抽一个。

⚠️ **注意这里 `rng()` 被调用了两次**：「本周有没有事件」一次，
「抽中哪个事件」一次（如果每个事件还带 `chance` 条件，会再多几次）。
因为 `rng` 是同一个闭包里的状态流，所以**调用次数和顺序会影响结果**。

这意味着：以后你在中间插一次 `rng()` 调用，同一 seed 的整局游戏结果就全变了。
这是种子确定性系统的固有特性（不算 bug，但要心里有数）。
所以「用 seed 复现某一局」的前提是**代码没改过**。

### 7.6 `triggerEvent`：分流到「等玩家」或「直接结算」

```ts
private triggerEvent(event: GameEvent): void {
  this.state.seenEvents.push(event.id)
  const entry = pushLog(this.state, 'event', `【${event.title}】${event.text}`)

  if (event.choices && event.choices.length > 0) {
    this.pending = event       // 有选项 → 挂起，等 choose()
    return
  }

  // 没选项 → 立即结算，并把回执挂在事件这一条日志上
  const changes = applyEffects(this.createContext(), event.effects ?? [])
  if (changes.length > 0) entry.changes = changes
}
```

事件被触发就立刻记进 `seenEvents` —— **不管玩家选了什么**。
所以「触发过」和「选过某个选项」是两件事。如果你以后要做
「A 选项选过才解锁某个事件」，需要再加一个 `chosenOption` 之类的 flag。

顺带注意：这条「立即结算」路径**只在事件没有 choices 时**走。
有选项的事件要等 `choose()`，回执挂在「你的选择：X」那条日志上 ——
所以四个挂载点加起来才覆盖全部路径（行动 / 选项 / 无选项事件 / 每周衰减）。

### 7.7 `settleEnding`：按优先级取第一个命中

```ts
private settleEnding(): void {
  const ctx = this.createContext()
  const sorted = this.data.endings
    // filter 已经产出了新数组，所以后面的 sort 不会动到 data 里的原顺序
    .filter((ending) => matchesMajor(ending.majors, this.major.id))
    .sort((a, b) => a.priority - b.priority)
  const hit = sorted.find((ending) => evaluate(ending.requires, ctx)) ?? null

  this.state.endingId = hit ? hit.id : null
  if (hit) {
    pushLog(this.state, 'ending', `【结局：${hit.title}】${hit.text}`)
  } else {
    pushLog(this.state, 'ending', '【结局】学期结束了，但你没有触发任何结局。')
  }
}
```

两个细节：

- 现在是 `.filter(...).sort(...)`：**`filter` 顺带承担了复制的职责**，
  所以原来那个 `[...this.data.endings]` 可以省掉 —— `sort` 改的是过滤出来的新数组
  （第 1.11 节讲过「sort 会改原数组」以及为什么那是个灾难级 bug）。
  代价是这行现在同时依赖两件事：专业过滤 + 防原地排序。哪天有人为了「省一次遍历」
  把 `filter` 删掉，`sort` 就会原地改掉全局的 `GAME_DATA.endings`。
  所以代码里那句注释是必要的 —— 它解释的是这行**为什么不能简化**。
- `?? null` 把 `find` 可能返回的 `undefined` 归一化成 `null`
  —— 保持 `endingId` 的类型是 `string | null`，可以安全进 JSON

那段 `else` 分支理论上永远不会执行（兜底结局恒真），但**还是要写**。
这叫**防御式编程**：如果哪天有人删了兜底结局，你会在日志里看到明确提示，
而不是让 `endingId` 静默地保持 `null`、游戏在最后一周卡死。

### 7.8 `buildResult`：用「日志起点」过滤增量

```ts
private buildResult(fromLogIndex: number): TurnResult {
  const logs: LogEntry[] = this.state.log.slice(fromLogIndex)
  return { logs, pending: this.pending, ended: this.isEnded() }
}
```

`takeAction` / `choose` 开头都记了 `const from = this.state.log.length`，
结尾 `buildResult(from)` 用 `slice` 切出**本次新增的日志**。

为什么不直接返回整个 `log`？因为 UI 只想显示「刚刚发生了什么」，
每次都重印整份历史会很吵。而让 UI 自己去 diff 上一份 `log` 又很别扭。

`slice(from)` 的意思是「从下标 `from` 开始到结尾」。
（Python 的 `log[from:]` 完全一样。）

### 7.9 `getSummary`：把「做过什么」翻译成人话

学期结束时，光给一个结局标题玩家记不住什么。所以引擎还产出一份**结算回顾**：

```ts
getSummary(): RunSummary {
  const ctx = this.createContext()
  const lines = this.data.summary.rules
    .map((rule, index) => ({ rule, index }))
    // 先按专业过滤，再求值条件 —— 顺序不影响结果，但让「这条规则本局根本不存在」
    // 和「它存在但条件不满足」两件事在代码上一眼可分
    .filter(({ rule }) => matchesMajor(rule.majors, this.major.id))
    .filter(({ rule }) => evaluate(rule.requires, ctx))      // 条件满足 → 这条要出现
    .map(({ rule, index }) => ({
      kind: rule.kind,
      text: rule.countFrom
        ? rule.text.replace(/\{n\}/g, String(this.flagNumber(rule.countFrom)))
        : rule.text,
      order: rule.order ?? 0,
      index,
    }))
    .sort((a, b) => a.order - b.order || a.index - b.index)  // 稳定排序
    .map(({ kind, text }) => ({ kind, text }))
  ...
  return {
    identity: this.major.identity,                           // ← 身份来自专业，不来自数据
    ...
  }
}
```

值得注意三点：

1. **规则表是纯数据**（`src/data/summary.ts`），引擎只做求值 + 替换 + 排序 ——
   和事件系统完全同构。所以「写一句回顾」不需要碰引擎。
2. **它复用了 `evaluate`**。回顾规则里能写 `flag` / `seenEvent` / `stat` /
   `all` / `any` / `not`，因为那本来就是同一套条件语义。
3. **排序要「order 优先、书写顺序兜底」**。只按 `order` 排的话，
   同 order 的几条顺序不确定，同一局结算两次可能显示不同的顺序。
   加 `index` 兜底之后结果唯一 —— 这是「同种子同结果」的延伸。

阶段 2 在这里加了两处（§8.4（c）（d））：一行专业过滤，
以及 `identity` 改成读 `this.major.identity` ——
「你是谁」只有 `MajorDef` 一处真相源，数据和引擎都不留第二份。

`dominantStat()` 里那个归一化也值得看一眼：比较的是 `stats[key] / ranges[key].max`
而不是裸值。因为金钱上限 999999、其余 100，直接比大小的话「一句话总评」永远是同一句。

## 8. 阶段 2：专业维度与项目系统（引擎的增量）

前 7 节讲的是阶段 1 的引擎：那时候「专业」这个概念还不存在，计算机是唯一的隐式专业。
阶段 2 往引擎里加了两样东西：**专业**（你是谁）和**项目**（你能造出什么）。

这一节按改动发生的位置走一遍，但先记住整节的判据 ——

### 8.1 ★ 一句话判据

> **专业不是引擎里的分支，而是内容上的一个可选标签。**
> 引擎只学会一句话：「打了 `majors` 标签的内容，只有对应专业看得见；
> 没打标签的，全专业共享。」

于是「加第 3 个专业」的代价是**新增一个内容文件 + 在 3 处各注册一行**
（`majors.ts` 注册专业、`index.ts` spread 进去、`cli/simulate.ts` 给风格加权重），
而 **`src/engine/` 一行都不用改** —— 这是这条设计的重点，也是它值钱的地方。
（原文写的是「全部代价是新增一个数据文件，引擎、CLI、Web 一行都不用改」：
引擎确实不用改，但只写一个文件是接不上的 —— `index.ts` 是手写 spread，没有自动发现。
完整清单见技术文档配方 9。）

这句话不是口号：它由两层测试守着（8.8）；「加专业没扰动任何一个老对局」当年由金标指纹
逐位证明 —— 注意那份夹具在阶段 2.6 因为**有意改共享内容**重新抓取过，
所以现在跑测试时它证明的是「自那次抓取以来没漂移」，原委见 8.7 末尾的说明。

另外两个「没有增加」同样重要，后面会逐条兑现：

- **没有新增任何 `Condition` / `Effect` DSL 分支** —— 项目系统用现成的 `flag` 条件表达（8.5）
- **没有给 `GameState` 加字段** —— 项目进度存在现成的 `flags` 里（8.5）

### 8.2 types.ts 的增量

#### （a）`MajorTags`：给「可选标签」起个名字

```ts
export type MajorTags = string[] | undefined
```

`undefined` = 全专业共享。为什么默认值选它、而不是「空数组表示共享」，8.3（a）会解释。

从类型上看，它和 `string[] | undefined` 是同一个东西；它的价值是**命名** ——
接口里看到 `majors?: MajorTags` 而不是 `majors?: string[]`，
一眼就知道这是「内容归属标签」，不是别的一串字符串。

（`majors?: MajorTags` 里的 `?` 和 `MajorTags` 自带的 `undefined` 叠在一起，
TS 会合并成同一件事：字段可能不存在，也可能显式写成 `undefined`。两种写法语义相同。）

#### （b）`MajorDef`：专业定义

```ts
export interface MajorDef {
  id: string
  /** 显示名，如「计算机」 */
  name: string
  /** 一句话身份，如「计算机专业大三学生」。开局日志与结算回顾共用这一处 */
  identity: string
  /** 开局选择界面上的介绍文案 */
  description: string
  /** 相对 `config.initialStats` 的属性偏移 */
  statBonus?: Partial<Stats>
}
```

`Partial<Stats>` 是个新的 TS 概念 —— **映射类型（mapped type）**。
它的定义就一行：

```ts
type Partial<T> = { [K in keyof T]?: T[K] }
```

它把 `Stats` 的每个字段都变成可选的，于是 `statBonus` 可以只写想调的那几项
（`{ academic: 2, skill: -12, health: -2 }`），其余自动保持基准值。
Java 里你得为此单独声明一个类、字段全用包装类型（`Integer` 而不是 `int`）；
C++ 里得逐字段 `std::optional<int>`。TS 内置一行就能表达。

**为什么是「偏移」而不是每个专业重抄一份完整属性**：基准数值（`config.initialStats`）
只留一处，调平衡时改基准就能同时作用于所有专业；「文科比计算机差在哪」也压缩成
一张一眼能看完的小表。这是 §2.2「单一真相源」原则在专业维度上的又一次应用。

`data/majors.ts` 里的一条长这样（节选）：

```ts
{
  id: 'literature',
  name: '汉语言文学',
  identity: '汉语言文学专业大三学生',
  description: '读、写、想。你的作品就是你的简历，但稿费和绩点都不等人。',
  statBonus: { academic: 2, skill: -12, health: -2 },
}
```

注意 `computer` 那一条**故意不写** `statBonus`：基准属性本来就是按计算机定的，
不写就等于不加偏移。这一点直接保证了「引入专业维度之后，老种子的开局属性逐位不变」。

#### （c）四处 `majors?: MajorTags`

`ActionDef` / `GameEvent` / `Ending` / `SummaryRule` 各加了同一个字段 ——
注释都是同一句「专属专业；不写 = 全专业共享」：

```ts
export interface ActionDef {
  ...
  /** 专属专业；不写 = 全专业共享 */
  majors?: MajorTags
}
```

这就是「专业系统」在内容层接口上的全部痕迹：**四个可选字段**。
没有新类型分支、没有新行为。

`Ending` 那一条的注释要多读一句：

```ts
/** 专属专业；不写 = 全专业共享。兜底结局必须共享，否则会有专业没有结局 */
majors?: MajorTags
```

兜底结局（`requires` 是空 `all`、恒真的那一条，见 §2.4）一旦被打上专业标签，
另一个专业在最后一周就会「一个结局都命中不了」（I6「一局必定走到某个结局」被打破）。
这条纪律由测试守着。

#### （d）`ProjectDef` / `ProjectView`

```ts
export interface ProjectDef {
  id: string
  name: string
  description: string
  /** 专属专业；不写 = 全专业共享（当前数据里项目都是各专业专属） */
  majors?: MajorTags
  /** 解锁条件（不满足则显示为「未解锁」） */
  requires?: Condition
  /** 每次投入消耗的行动力，默认 1 */
  cost?: number
  /** 需要投入几次才算完成 */
  requiredInvestments: number
  /** 每次投入的效果（通常是小幅属性收益） */
  perInvest: Effect[]
  /** 完成时的一次性效果（奖励 + 产出 flag） */
  onComplete: Effect[]
  /** 进度存放的数值 flag key（由引擎写入，每次投入 +1） */
  progressFlag: string
  /** 完成标志 flag key（由引擎写入），供结局 / 回顾消费 */
  completionFlag: string
}
```

```ts
export interface ProjectView {
  project: ProjectDef
  progress: number      // 已投入次数
  required: number      // 需要投入几次
  completed: boolean
  unlocked: boolean     // 解锁条件是否满足（false → UI 应该置灰）
}
```

`ProjectDef` 大量复用了已有的 `Condition` / `Effect`（`requires` / `perInvest` / `onComplete`）
—— 这是「组合优于继承」的又一次体现：项目不是一种新效果，而是
**一组已有效果 + 两个记账用的 flag key**。

`progressFlag` / `completionFlag` 由**数据**声明、由**引擎**写入，
所以引擎不需要任何命名约定（不需要约定「进度 flag 一律叫 `X_进度`」）。

`ProjectView` 的角色和 `ChoiceView`（§7.2）完全一样：**引擎把「这个项目现在是什么样」算好给 UI**，
UI 只负责显示和置灰，不需要知道条件 DSL 长什么样。

⚠️ `ProjectDef.requires` 里**不要写 `chance`**：引擎每次渲染项目列表都会求值它
（`getProjects()` 里那句 `evaluate(project.requires, ctx)`），
而 `chance` 会消耗随机数 —— 「打开一次面板」不该改变这一局的随机流。
`types.ts` 的 `SummaryRule` 注释里写着同一条纪律（回顾必须确定）。

#### （e）状态与数据集的两个字段

```ts

  /** 本局所选专业 id */
```

**存档读回来时要能还原「你是谁」**。专业决定哪些行动 / 事件 / 结局 / 回顾可见，
丢了它这局就还原不了。而它只是一个 string —— I8（状态必须是纯 JSON）零成本满足。

### 8.3 ★ 新文件 `majors.ts`：引擎里关于专业的全部代码

整个文件 70 行，其中一半是注释；三个函数加起来不到 30 行。
文件开头的注释就是它的承诺：

```ts
/**
 * 专业维度的**通用**处理。
 *
 * 这个文件刻意做得很小，因为它承担的是「引擎里的专业相关逻辑总共只有这么多」
 * 这个承诺。引擎不认识「计算机」或「文科」，只认识两条规则：
 *
 *   1. 内容没打 `majors` 标签 → 全专业共享
 *   2. 内容打了标签 → 只有列出的专业看得见
 */
```

#### （a）`matchesMajor`：一行完成过滤

```ts
export function matchesMajor(tags: string[] | undefined, majorId: string): boolean {
  return tags === undefined || tags.includes(majorId)
}
```

`||` 在这里同时干了两件事：短路求值，以及**类型收窄** ——
左边为假之后 TS 知道 `tags` 不再是 `undefined`，所以右边的 `tags.includes(...)`
不会报「可能为 undefined」。（§1.6 的 `&&` 收窄是同一个机制。）

**为什么默认值是「共享」，而不是「专属」？**

这是本文件最重要的一个决定。内容库里绝大多数条目 —— 下雨、生病、宿舍矛盾、
体测、食堂涨价 —— 跟专业毫无关系。让它们**默认可见**，才有：

> 「加专业」的改动量 ∝ **新增内容**，而不是 ∝ **全库内容**。

如果反过来（默认专属，必须显式打标签才算共享），那么每加一个专业，
都得回头把库里那几十条无关条目全部追加一次新专业的 id。
改动的规模一下就从「写你想要的东西」变成「维护你不关心的东西」。

而真正专业相关的内容（文科的「写稿 / 读原著」、计算机的开源库项目）只要写一行
`majors: ['literature']`。忘了写标签的后果是「所有专业都能看见它」，
这在测试里会被立刻发现（8.8）。

#### （b）`resolveMajor`：默认取第一个，未知专业直接抛错

```ts
export function resolveMajor(data: GameData, majorId?: string): MajorDef {
  const first = data.majors[0]
  if (!first) {
    throw new Error('GameData.majors 不能为空：至少要有第一个专业作为默认值')
  }
  if (majorId === undefined) return first

  const found = data.majors.find((major) => major.id === majorId)
  if (!found) {
    const available = data.majors.map((major) => major.id).join(' / ')
    throw new Error(`未知专业: ${majorId}（可选：${available}）`)
  }
  return found
}
```

四个值得说的点：

**① `majorId?: string` 是可选参数。** 不传就是 `undefined`。这里用
`majorId === undefined` 判断「没传」，而不是 `if (!majorId)` ——
因为后者会把空字符串 `''` 也当成没传。这和 §1.6 讲的 `??` vs `||` 是同一个坑。

**② 不传就用第一个专业。** 这让老调用方（`new GameEngine(DATA, { seed })`）
和只想快速开一局的测试不用被迫指定专业。兼容性不靠「到处补参数」实现，
而是靠数据里**第一个专业就是默认专业**这个约定 —— 所以 `data/majors.ts`
的注释专门写了「计算机必须留在第一位」。

**③ `data.majors[0]` 后面为什么还要判空？**
因为 **TS 不检查数组长度**：`data.majors[0]` 的静态类型就是 `MajorDef`，
哪怕 `majors` 是空数组，编译器也不会拦。这时候写 `data.majors[0]!`
（**非空断言**）只是让编译器闭嘴，运行时照样拿到 `undefined`，
然后在后面某处 `this.major.id` 时炸掉 —— 而且报错离真正的错误很远。
所以这里选择**真的判空并抛出一条人话错误**。
**类型注解不能替代运行时校验**，这就是例子。

**④ 传了未知专业 → 抛错，不回退。** 这条纪律值得单独记住：
如果查不到时静默用默认专业，那么「玩家选了文科、进的却是计算机」这种 bug
会**一路静默地跑完一整局** —— 内容池错了、身份文案错了、结局错了，
没有任何一处会报错，玩家看到的只是「怪怪的」。而 fail fast 的效果是：
构造 `GameEngine` 这一行就炸，错误信息还把可选专业列了出来。

（`map(...).join(' / ')` 就是 Python 的 `' / '.join(...)`，只是方法挂在数组上。
错误信息是给凌晨三点的你看的，不是给编译器看的。）

#### （c）`applyStatBonus`：基准 + 偏移，并夹进合法区间

```ts
export function applyStatBonus(
  base: Stats,
  bonus: Partial<Stats> | undefined,
  ranges: StatRange,
): Stats {
  const result = { ...base }
  if (!bonus) return result

  for (const key of Object.keys(bonus) as StatKey[]) {
    const delta = bonus[key]
    if (delta === undefined) continue
    const range = ranges[key]
    result[key] = Math.min(range.max, Math.max(range.min, result[key] + delta))
  }
  return result
}
```

**① `const result = { ...base }` —— 先复制**（§5 的原则）。这个函数是纯函数，
它不该改自己的入参。等会儿 `createInitialState` 还会再复制一次（§8.6），
两层复制看着冗余，其实是**两个函数各自独立的契约**：谁都不假设对方给了新对象。

**② `Object.keys(bonus) as StatKey[]` —— 类型断言。**
`Object.keys` 的返回类型是 `string[]`（它不知道你传进去的是什么形状），
所以要手动断言成 `StatKey[]`，下一行才能用 `bonus[key]` / `ranges[key]`。
`as` 和 `private` 一样是**纯编译期的**（§1.10）：它不产生任何运行时检查。
所以如果数据里手滑写了 `{ stress: 3 }`，`as` 不会拦你，
`ranges[key]` 会是 `undefined`，下一行读 `range.max` 当场 TypeError。
—— 这是 `as` 的代价：**它把「编译器帮你查」换成了「祈祷自己写对了」**。
能用类型推导解决的地方就不要用它。

**③ `if (delta === undefined) continue`。** `Object.keys` 只返回实际存在的键，
所以严格说这里不会是 `undefined`；但 `Partial<Stats>` 的类型允许它是，
用一个显式的 `continue` 比写 `delta!` 更诚实（也顺手挡住了
`{ skill: undefined }` 这种显式写法）。**能收窄就别断言。**

**④ ★ 为什么要 clamp？** 这是这个函数里唯一一个「看起来多余」的操作，
所以特别值得讲。

`applyEffects` 里的 clamp 是游戏**进行中**改属性的唯一入口（§6 的（a）），
它保证不变量 I1：「每项属性都在 `statRanges` 的 `[min, max]` 内」。
但**开局那一帧**同样受 I1 约束，而它不走 `applyEffects` ——
它是 `createInitialState` 直接写进状态的。如果这里不夹，
一个写大的偏移（比如文科 `social: +40`）就会让玩家**第一眼看到的就是一条越界的属性条**：
UI 上那根条可能画出容器，或者显示成 140/100。
这类「第一帧就违约」的 bug 最容易被忽略，因为它不经过任何已有的检查点。

```ts
result[key] = Math.min(range.max, Math.max(range.min, result[key] + delta))
```

读法是「先保证不小于 `min`，再保证不大于 `max`」—— 和 `effects.ts` 里的 `clamp`
是同一个意思。区别只有一个：`effects.ts` 会产出 `capped` 回执（告诉玩家
「你这次白费了」），这里不产出 —— 开局的偏移是**设定**，不是**结算**，
不需要解释「为什么只加了一点」。

对应测试的名字很直白：**「每个专业的开局属性都落在 statRanges 内（I1 从第一帧就成立）」**。

⚠️ 但 clamp 只能防「越界」，防不住「平衡被起始值悄悄改掉」。
`data/majors.ts` 里记着一次真实事故：文科第一版给了 `academic +5, social +6`，
结果三条「死内容」不变量（死结局 / 死事件 / 死规则）一起报警 ——
**起始值偏高会把共享内容里那些「低阈值」路线整片挡在门外**：
`academic < 25` 的学业崩塌、`social <= 30` 的「一个人过完一学期」，
在文科身上永远达不到。所以现在只留最小必要偏移（`skill -12` 这种核心差异），
专业之间的真正差异交给**行动 / 事件 / 项目**去承担。

### 8.4 engine.ts 的五处改动

#### （a）构造函数：一个可选参数、一个私有字段、两次调用

```ts
export interface NewGameOptions {
  /** 指定随机种子即可复现同一局游戏；不传则随机 */
  seed?: number
  /** 专业 id；不传则用 `data.majors` 里的第一个 */
  majorId?: string
}
```

```ts
export class GameEngine {
  ...
  /** 本局专业（数据里的一条定义，引擎不对它做任何特判） */
  private readonly major: MajorDef

  constructor(data: GameData, options: NewGameOptions = {}) {
    this.data = data
    this.seed = options.seed ?? randomSeed()
    this.rng = mulberry32(this.seed)
    this.major = resolveMajor(data, options.majorId)

    this.state = createInitialState(
      data.config,
      this.major.id,
      // 基准属性 + 专业偏移，并且夹进合法区间（开局这一帧同样受 I1 约束）
      applyStatBonus(data.config.initialStats, this.major.statBonus, data.config.statRanges),
    )
    ...
  }

```

注意 `this.major` 存的是**解析后的专业定义**（`MajorDef`），不是 id。
只存 id 的话，后面每处过滤都得再查一次表；而且 `resolveMajor` 已经保证了
「一定有一个专业」，所以 `this.major` 的类型是 `MajorDef` 而不是 `MajorDef | undefined`
—— §8.3（b）把判空和抛错的成本一次付清了，后面所有代码都不用再判。

`private readonly`：一旦开局定了就不能换专业（换专业等于存档失效）。

开场白也从写死的字符串改成了读专业数据：

```ts
// 开场白里的「你是谁」来自专业数据。引擎里刻意不留任何一个具体专业名：
// 一旦写死「计算机专业大三学生」，「加第 3 个专业只写数据」这句话就假了。
pushLog(
  this.state,
  'system',
  `开学了。你是${this.major.identity}，本学期共 ${data.config.totalWeeks} 周，每周 ${data.config.actionPointsPerWeek} 点行动力。`,
)
```

`` `${...}` `` 是模板字符串（Python 的 f-string / Java 的字符串拼接）。
以前这句是 `'开学了。你是计算机专业大三学生，……'` ——
一句话就把「引擎不认识专业」的承诺打破了。现在身份只从 `this.major.identity` 来。

#### （b）`getMajor()`：透传本局专业

```ts
/** 本局专业定义（含显示名与身份文案），供界面显示 */
getMajor(): MajorDef {
  return this.major
}
```

注意它**不深拷贝**，和 `getState()`（§5）不一样。为什么可以这样：
`this.major` 是**注入进来的只读配置**（`getConfig()` 直接返回 `this.data.config`
也是同样的做法），不是「本局会被改的状态」。
规则可以记成一句话：**引擎内部会变的东西才需要拷贝；外部数据本来就不该被改。**

#### （c）四处专业过滤：一行 `matchesMajor`，四处复用

四个和「内容可见性」有关的位置各加了一行过滤，全都调用同一个 `matchesMajor`。

**① `availableActions()`**

```ts
availableActions(): ActionDef[] {
  const ctx = this.createContext()
  return this.data.actions.filter(
    (action) =>
      matchesMajor(action.majors, this.major.id) &&
      action.cost <= this.state.actionPoints &&
      evaluate(action.requires, ctx),
  )
}
```

**② `rollWeeklyEvent()` 的事件池**（§7.5 那段现在多了一层）

```ts
const pool = this.data.events.filter((event) => {
  if (!matchesMajor(event.majors, this.major.id)) return false
  if (event.category !== 'random') return false
  if (!event.repeatable && this.state.seenEvents.includes(event.id)) return false
  return evaluate(event.requires, ctx)
})
```

**③ `settleEnding()` 的结局表**（§7.7，顺带替掉了 `[...]` 复制）

```ts
const sorted = this.data.endings
  // filter 已经产出了新数组，所以后面的 sort 不会动到 data 里的原顺序
  .filter((ending) => matchesMajor(ending.majors, this.major.id))
  .sort((a, b) => a.priority - b.priority)
```

**④ `getSummary()` 的回顾规则**（§7.9）

```ts
.filter(({ rule }) => matchesMajor(rule.majors, this.major.id))
.filter(({ rule }) => evaluate(rule.requires, ctx))
```

「先过滤专业、再求值条件」是这四处的共同写法，但理由不完全相同：

- 对**事件池**来说这个顺序是**必须**的。`evaluate` 可能消耗随机数（`chance` 分支），
  如果先求值了别的专业的事件条件，就会从本局的随机流里**偷走一个随机数** ——
  同种子的对局立刻变形。把 `matchesMajor` 放在 `&&` / `if` 的最前面，
  别的专业的内容连条件都不会被碰到。
- 对**回顾规则**来说顺序不影响结果（而且回顾里本来就禁止 `chance`），
  这个写法是**可读性优先**：代码里那句注释的意思是，
  「规则本局根本不存在」和「规则存在但条件不满足」是两件事，分开写一眼能看出来。

#### （d）`getSummary()` 的身份：从专业来，不从数据来

```ts
return {
  identity: this.major.identity,
  lines,
  ...
}
```

`SummaryContent`（回顾的内容表）里**故意没有** `identity` 字段，
类型定义处写着理由：「一旦身份留在这里，就会出现『专业改了、结算页还写着旧专业』
的二源问题」。于是「你是谁」只写在 `MajorDef.identity` 一处 ——
开局日志（§8.4（a））和结算回顾（这里）读的是同一个字段。

### 8.5 ★ 项目系统：一个新机制，零个新 DSL 分支

#### （a）`getProjects()`：把状态投影成 UI 能直接用的形状

```ts
/**
 * 本专业可见的全部项目（含未解锁与已完成的），带进度。
 *
 * 这里**不过滤**未解锁/已完成的：界面需要显示「还没解锁」和
 * 「进度 2/3」这类信息，直接过滤掉它们反而啥都展示不了。
 * 能不能投入由 `investProject` 负责挡（fail fast）。
 */
getProjects(): ProjectView[] {
  const ctx = this.createContext()
  return this.data.projects
    .filter((project) => matchesMajor(project.majors, this.major.id))
    .map((project) => {
      const progress = this.projectProgress(project)
      return {
        project,
        progress,
        required: project.requiredInvestments,
        completed: progress >= project.requiredInvestments,
        unlocked: evaluate(project.requires, ctx),
      }
    })
}
```

这个方法和 `getPendingChoices()`（§7.2）是同一种东西：
**引擎把「现在是什么情况」算完，UI 只管画。**
注意它返回的 `ProjectView` 是 `map` 里现造的**新对象**，
所以 UI 改不动 `this.data.projects` 里的定义。

`projectProgress` 是第二个「读数值 flag」的工具函数（第一个是 §7.9 的 `flagNumber`）：

```ts
private projectProgress(project: ProjectDef): number {
  const value = this.state.flags[project.progressFlag]
  return typeof value === 'number' ? value : 0
}
```

`flags` 的值类型是 `FlagValue = number | boolean`，运行时还可能是 `undefined`，
`typeof value === 'number'` 一次搞定「运行时判断 + 类型收窄」（§4 的（b））。

#### （b）`investProject()`：第二个「会改状态的入口」

方法头那段注释把设计意图说完了：

```ts
/**
 * 向一个项目投入一次：消耗行动力、进度 +1，攒满则完成并结算奖励。
 *
 * 语义刻意对齐 `takeAction` —— 同样的守卫顺序、同样的「先写日志、后补变化量」、
 * 同样在行动力归零时结算本周。这样「做项目」和「做行动」在引擎里是同一种东西，
 * UI 也能把它们并排放在「这周做点什么」里。
 */
```

守卫部分完整照抄（注意顺序）：

```ts
investProject(projectId: string): TurnResult {
  const from = this.state.log.length

  if (this.state.endingId !== null) {
    throw new Error('游戏已经结束了')
  }
  if (this.pending !== null) {
    throw new Error('还有未处理的事件，请先做出选择')
  }

  const project = this.data.projects.find((item) => item.id === projectId)
  if (!project) throw new Error(`未知项目: ${projectId}`)
  if (!matchesMajor(project.majors, this.major.id)) {
    throw new Error(`项目不属于本专业(${this.major.id}): ${projectId}`)
  }

  const cost = project.cost ?? 1
  if (cost > this.state.actionPoints) throw new Error('行动力不足')

  const progress = this.projectProgress(project)
  if (progress >= project.requiredInvestments) {
    throw new Error(`项目已经完成了: ${projectId}`)
  }
  if (!evaluate(project.requires, this.createContext())) {
    throw new Error(`项目条件不满足: ${projectId}`)
  }
```

和 `takeAction`（§7.4）逐条对照，能看到它是**故意同构**的：

| | `takeAction` | `investProject` |
|---|---|---|
| 已结束 | `endingId !== null` → throw | 同 |
| 待处理事件 | `pending !== null` → throw | 同 |
| 查表 | `actions.find(...)` → 「未知行动」 | `projects.find(...)` → 「未知项目」 |
| 专业 | `matchesMajor(action.majors, ...)` | `matchesMajor(project.majors, ...)` |
| 资源 | `cost > actionPoints` → 「行动力不足」 | 同（`cost` 默认 1） |
| 内容条件 | `evaluate(action.requires, ...)` | `evaluate(project.requires, ...)` |

多出来的只有一条：`progress >= requiredInvestments` → 「已经完成了」。
它也在**扣行动力之前**，所以「对着做完了的项目再点一次」不会白扣一点行动力。

然后是「改状态 → 写日志 → 补回执」这三步，和 `takeAction` 一字不差：

```ts
  // 校验全部前置之后才开始改状态（一旦开始就不再回滚）
  this.state.actionPoints -= cost
  const next = progress + 1
  this.state.flags[project.progressFlag] = next

  // 进度写进日志文案：玩家不用回头翻面板也知道自己攒到哪了
  const entry = pushLog(
    this.state,
    'action',
    `〔第${this.state.week}周〕你投入到「${project.name}」（进度 ${next}/${project.requiredInvestments}）`,
  )
  const changes = applyEffects(this.createContext(), project.perInvest)
  if (changes.length > 0) entry.changes = changes
```

`entry.changes` 这个「先写日志、后补回执」的写法，理由和 §0 / §6 讲的完全一样：
效果里的 `{ type: 'log' }` 要排在行动那条日志后面（叙事顺序），
而变化量只有结算完才知道。**新入口没有发明新写法，这本身就是设计目标。**

完成时的分支：

```ts
  if (next >= project.requiredInvestments) {
    // 先置完成 flag，再结算 onComplete —— 这样 onComplete 里的 if 条件
    // 能读到「已完成」，数据作者不必去猜执行顺序
    this.state.flags[project.completionFlag] = true
    const doneEntry = pushLog(this.state, 'system', `「${project.name}」完成了。`)
    const doneChanges = applyEffects(this.createContext(), project.onComplete)
    if (doneChanges.length > 0) doneEntry.changes = doneChanges
  }

  if (this.state.actionPoints <= 0) {
    this.endWeek()
  }

  return this.buildResult(from)
}
```

三个细节：

- **先写 `completionFlag`、再结算 `onComplete`。** 这是一个**顺序契约**：
  数据作者可以在 `onComplete` 的效果里写
  `{ type: 'if', requires: { type: 'flag', key: '项目_诗集_完成' }, ... }`
  并且确信它一定读得到 `true`。契约写进代码，数据就不用靠猜。
- **`endWeek()` 照旧。** 做项目也消耗行动力，归零同样走 `endWeek()` ——
  所以「相位控制」那条唯一的闸门（§7.3）对两个入口都成立。
- **完成日志用 `'system'` 而不是 `'action'`。** 它是系统的通报，不是玩家的选择。

#### （c）进度为什么放在 `flags` 里（而不是给 `GameState` 加字段）

`this.state.flags[project.progressFlag] = next` —— 就这一行，项目进度就存下来了。
好处有三层：

1. **`GameState` 一个字段都没加。** 于是 I8（「状态必须是纯 JSON、
   可被 `structuredClone`」）零成本继续成立。如果新加一个
   `projects: Record<string, number>` 字段，存档格式就得跟着改，
   所有构造 `GameState` 的地方都要同步。
2. **进度和完成是可被条件读取的普通数据。** 没有新增 `Effect` 分支、
   没有新增 `Condition` 分支 —— 完成判定用的是现成的 `flag` / `flagAtLeast`。
   比如 `data/literature.ts` 里的那条长篇小说回顾：

   ```ts
   {
     requires: { type: 'flag', key: '项目_长篇_完成' },
     kind: 'skill',
     order: 26,
     countFrom: '项目_长篇_进度',
     text: '一部长篇前后投入了 {n} 次，结尾改了七遍',
     majors: ['literature'],
   }
   ```

   结局那边也一样，用现成的 `any` 把「事件线」和「项目线」并列：

   ```ts
   {
     type: 'any',
     conditions: [
       { type: 'flag', key: '连载邀约' },
       { type: 'flag', key: '项目_长篇_完成' },
     ],
   }
   ```

   于是「你这学期造出了什么」真的能决定你成为谁 ——
   而引擎里连「项目」对应的 DSL 分支都不存在。
3. **`progressFlag` 是「引擎写」、`countFrom` 是「数据读」。**
   这两个 flag 由数据声明、由引擎写入，而静态审计（`src/cli/audit.ts`）
   扫的是**数据**，看不到引擎里的写入点 —— 所以它有一个 `consumedByEngine`
   参数专门豁免这两个 key：

   ```ts
   // 项目进度 / 完成 flag 是**引擎**写的（investProject 每次 +1 / 置 true），
   // 静态扫描看不到写入点，所以必须豁免，否则会误报「读了却没人写」。
   const engineWritten = content.projects.flatMap((project) => [
     project.progressFlag,
     project.completionFlag,
   ])
   ```

   同一个审计器还必须**按专业**跑：`auditFlags(majorId)` 用的是 `contentFor(majorId)`
   切出来的那份内容。因为「共享结局读了 flag，而写它的只有文科专属事件」
   这种跨专业泄漏，从全局看「有写有读」完全正常，但对计算机来说那个条件永远不成立。

到这里可以下一个结论：**项目系统在引擎里只增加了「两个公开方法 + 一个私有读进度函数」，
没有增加任何 DSL 分支。** 这正是「专业差异由内容承担」这条设计的执行方式。

### 8.6 state.ts：为什么「专业」这个概念不进 state.ts

签名变了（§5 引的就是新版）：

```ts
export function createInitialState(
  config: GameConfig,
  majorId: string,
  initialStats: Stats,
): GameState {
```

两个新参数：`majorId` 只是**存进状态**（存档要用，见 §8.2（e）），
`initialStats` 是**已经算好的开局属性**（基准 + 偏移 + 夹取，由 `applyStatBonus` 完成）。

为什么不在 `createInitialState` 里读专业、在这里算偏移？文件头的注释写得很清楚：

```ts
/**
 * `initialStats` 由调用方算好传进来（基准属性 + 专业偏移，见 `majors.ts`），
 * 而不是在这里读 config：这样 state.ts 完全不需要知道「专业」这个概念，
 * 它只管把一份已经确定的数值装进状态里。
 */
```

这是**职责单一**的一次具体应用：`state.ts` 是「状态的构造与维护」，
专业解析和数值叠加是 `majors.ts` 的事。如果 `createInitialState` 开始认识
`MajorDef`，「引擎里的专业相关逻辑总共只有这么多」这句话就被稀释了。

### 8.7 ★ 为什么加完这一整套，旧对局一个比特都没动

这是阶段 2 最值得学的一手：**新机制必须能「默认不参与」。**

证据是**金标指纹**（`tests/golden-fingerprint.ts`）：在做那两步之前，先抓下
「6 个经典风格 × 10 个种子」的对局结果（结局 / 六项终局属性 / 遇到事件数 / 回顾条数），
冻成文件；加完专业、加完项目之后逐位重跑，**全部一致**。三件事共同保证了它：

**（a）`pickWeighted` 里的 0 权重是惰性的。**

```ts
const weights = items.map(weightOf)
const total = weights.reduce((sum, w) => sum + Math.max(0, w), 0)
if (total <= 0) return null

let roll = rng() * total
for (let i = 0; i < items.length; i++) {
  const w = Math.max(0, weights[i] ?? 0)
  if (w === 0) continue
  roll -= w
  if (roll < 0) return items[i] ?? null
}
```

盯住 `if (w === 0) continue` 那几行，会发现：

- 权重 0 的项**不参与 `total` 累加**，总权重不变 → `roll` 的取值区间不变
- 循环里遇到它直接 `continue`，**不扣减 `roll`** → 落点判定不变
- `rng()` 仍然**只被调用一次**（就在 `let roll = rng() * total` 那一行）

三条加起来：**往候选列表里塞进一个权重为 0 的项，抽签结果逐位不变，
连随机数的消耗次数都不变。** 这就是「惰性」的含义 ——
它存在，但对既有的概率分布没有任何影响。

项目系统就是靠这条性质做成 **opt-in** 的：模拟器里每个风格的 `__project` 权重
默认是 `0`（`weights['__project'] ?? 0`，没写这个 key 的风格一律不投项目），
所以六个经典风格的候选列表里**连项目都不会出现**。新机制加进来了，
老玩法的随机流一动没动。

> 注意这三条都不是自动成立的：只要写成「先累加所有项（包括 0 项）、再乘系数」，
> 或者在循环里每项都消耗一次随机数，新候选就会挪动随机流 —— 金标指纹会红，
> 而且失败原因极难看出来（「某个种子第 7 周抽到了另一个事件」）。
> **一个机制能不能被「无声地」加进来，取决于它脚下的工具是否有这种惰性。**

**（b）内容的拼接顺序：共享在前，专业内容追加在后。**

`data/index.ts` 里：

```ts
actions: [...ACTIONS, ...LITERATURE_ACTIONS],
events: [...EVENTS, ...LITERATURE_EVENTS],
endings: [...ENDINGS, ...LITERATURE_ENDINGS],
projects: [...COMPUTER_PROJECTS, ...LITERATURE_PROJECTS],
```

`pickWeighted` 是按数组顺序累加权重抽签的，所以顺序一变结果就变。
把专属内容**一律追加在末尾**，计算机过滤出来的池子顺序就和加专业之前逐位相同。
（文件里的注释把这条写明了：「这条性质由 tests/golden-fingerprint.ts 守着，不是靠自觉。」）

**（c）过滤在求值之前**（§8.4（c））。别的专业的内容不仅不进池子，
连条件都不会被求值 —— 所以它连一个随机数都偷不走。

三件事合起来，「新增一个专业」才真正是**纯增加**：
不改老数据的顺序、不消耗新的随机数、不改任何概率分布。

> **后来它被重新抓取过一次（阶段 2.6），这里要说清楚为什么。**
> 那次是**有意**改共享内容：新增了一个行动（「约同学联机打游戏」）、
> 三个限周事件（花钱换健康/技能/社交），还调了一条共享回顾规则的阈值。
> 往共享池子里加东西，整局随机流必然变 —— 70 局**全部**变了，这是种子确定性系统的
> 固有特性（§5.4），不是 bug。
>
> 所以指纹的定位要精确：**它是一份「快照」，不是永久契约。**
> 它擅长抓「你没打算改、但它却变了」（比如重构引擎时手滑；
> 或者给专属内容忘了写 `majors` 标签，让它渗进了别的专业）。
> 而「改了共享内容 → 指纹必然红」是**预期**的，这时正确的动作是：
> 先生成到临时文件、**diff 一遍**确认变化形状符合预期，再重新抓取。
> 真正永不过期的是「差分不变量」（§8.8）—— 它每次现算，不依赖任何冻结数据。

### 8.8 两层测试：怎么保证「加专业只写数据」

§8.1 那句承诺（「加第 3 个专业只需要写数据」）如果只写在注释里，
三个月后一定会被某次「顺手优化」推翻。所以它被两层测试守着。
（两个测试文件共 **75** 个测试。）

**第一层：源码扫描 —— 禁止引擎里出现任何专业痕迹。**

```ts
/**
 * 去掉注释再检查。注释是写给人看的说明（「引擎不认识计算机」这种话
 * 本身就该写在注释里），不构成行为；而**代码**里出现专业名/id 才是硬编码。
 */
const stripComments = (source: string) =>
  source.replace(/\/\*[\s\S]*?\*\//g, '').replace(/\/\/[^\n]*/g, '')
```

它先把 `src/engine/**.ts` 的注释全部剥掉（注释里写「引擎不认识计算机」是应该的，
不构成行为），然后断言：

- 代码里**不出现任何专业 id 字面量** —— 杜绝 `if (majorId === 'computer')` 这类分支
- 代码里**不出现任何专业的身份 / 名称文案** —— 杜绝写死的开场白

这一层抓的是「引擎里长出了专业特判」。它的好处是**不需要跑游戏**，
改一行代码就能知道；局限是它只看得见字面量，看不见「过滤漏了一处」这类逻辑错误。

**第二层：差分不变量 —— 一个专业的对局不受其他专业内容影响。**

```ts
const mismatches: string[] = []

for (const major of GAME_DATA.majors) {
  const isolated = isolateMajor(major.id)
  for (const [strategy, weights] of Object.entries(STRATEGIES)) {
    for (const seed of [1, 2, 3, 7, 42]) {
      const full = playOne(seed, weights, major.id)
      const alone = playOne(seed, weights, major.id, isolated)
      if (JSON.stringify(full) !== JSON.stringify(alone)) {
        mismatches.push(`  ${major.id} / ${strategy} / seed=${seed}`)
      }
    }
  }
}
```

它的思路比金标指纹更本质：**不依赖任何冻结的夹具，所以永远不会过期。**
把 A 专业的内容单独拎出来跑一局，和它在完整数据集（含 B 专业的全部内容）里跑，
结果必须逐位相同 —— 如果引擎里漏了一处过滤，B 专业的内容就会渗进 A 的池子，
这条测试会直接指出「哪个专业 / 哪个风格 / 哪个种子」。

再加上 §8.7 讲的金标指纹，以及三条按专业成立的「死内容」不变量
（死结局 / 死事件 / 死规则：专属内容必须在它自己的专业里可达），
「加专业只写数据」这句话才算被钉住了。

最后用一句话收束阶段 2 的设计：

> 引擎里新增的全部「专业知识」，就是 `majors.ts` 里的三个纯函数；
> 其余部分只是**在已有流程的四个位置各插一行过滤**，
> 加**一个复用现有 DSL 的项目循环**。

## 9. 这个项目用到的设计模式清单

| 模式 | 用在哪 | 一句话说明 |
|---|---|---|
| **依赖注入** | `new GameEngine(GAME_DATA, {seed})` | 引擎不 new 数据，从外面拿 |
| **分层架构** | `cli → data → engine` | 依赖单向，引擎最底层最纯净 |
| **数据驱动 / 解释器模式** | `Condition` / `Effect` DSL | 逻辑写成数据，引擎负责解释 |
| **组合模式** | `Effect` 里嵌 `Effect[]` | 递归结构表达无限嵌套 |
| **策略模式** | `RNG` 参数、`weightOf` 回调 | 算法从外部传入 |
| **参数对象** | `EvalContext` | 一堆相关参数打包传 |
| **值对象 / 快照** | `getState()` 返回深拷贝 | 跨边界时复制，内部可变 |
| **兜底分支** | 空 `all` 恒真的结局 | 保证总有出路，不卡死 |
| **单一真相源** | `Stats` → `keyof` → `Record` | 派生类型，改一处全联动 |
| **可选标签 / 过滤器** | `majors?: MajorTags` + `matchesMajor` | 不写标签 = 共享，写了 = 专属；加专业只写数据 |
| **开关式扩展（opt-in）** | `pickWeighted` 的 0 权重、`__project` 风格权重 | 新机制默认不参与，老对局逐位不变 |
| **纯函数模块 / 无状态策略** | `majors.ts` 三个函数 | 过滤 / 解析 / 叠加都不认识具体专业 |

### 答案

**A1.** 实测是 **3 处**，全部在数据/展示层，`types.ts` 自己不报错：

```
config.ts(7)     STAT_RANGES  缺 stress（StatRange 是 Record<StatKey,...>，要求覆盖所有键）
config.ts(16)    INITIAL_STATS 缺 stress（类型是 Stats，要求字段齐全）
effects.ts(88)   STAT_LABELS  缺 stress（类型是 Record<StatKey, string>）
```

（如果你以后在哪写了对 `StatKey` 的穷尽 `switch`，那里也会报错。）
注意 `StatKey` / `StatRange` 是**派生**出来的，所以它们自动跟着 `Stats` 变，
改一处、编译器列出全部同步点 —— 这就是「单一真相源」的收益。

**A2.** 返回 `true`。好处是「可选条件」的语义自然：
不写 `requires` 就等于「总是触发」，引擎不需要到处写
`if (requires && !evaluate(requires))` 这种判空。

**A3.** `week` 还是 5。因为 `endWeek()` 最后调 `maybeAdvance()`，
而它第一行 `if (this.pending !== null) return` 就直接返回了。
要等玩家 `choose()` 处理完事件，`pending` 变回 `null`，
再次调用 `maybeAdvance()` 才会 `week = 6`。

**A4.** 会破坏封装。外部拿到内部对象引用后可以直接改
（`state.stats.academic = 0`），引擎的状态就被污染了；
而且如果外部把引用存起来，之后引擎内部再改，外部看到的是「活」的变化，
这在 React 那种「靠引用变没变来判断要不要重渲染」的场景下会彻底失效。
深拷贝让每次查询都是一份独立的快照。

**A5.** `stats` 会和调用方传进来的那份对象**共享引用**。
阶段 2 之后 `initialStats` 是调用方算好的（`applyStatBonus` 已经返回了一个新对象），
所以通常不会再直接污染 `GAME_DATA.config.initialStats` —— 但原则没有变：
只要哪个调用点图省事写成 `createInitialState(config, id, config.initialStats)`，
第一局改属性就会把全局初始配置一起改掉，第二局从被改过的值开始。
在测试里表现为「单独测通过、连着测失败」——非常难查。
**结论：边界上的复制不能省；省掉它只是把这个 bug 挪到一个更不起眼的调用点上。**

**A6.** 因为 `chance` 求值会**消耗一次随机数**。
`if (chance 50%)` 和 `if (not chance 50%)` 是**两次独立的 50% 抽取**，
可能出现「都没中」（10% 概率漏掉分支）或「都中了」（两个分支都执行）。
`branch` 用一次加权抽取决定落在哪个区间，必定且只命中一个。

**A7.** `Array.prototype.find` 找不到时返回 `undefined`。
而 `GameState.endingId` 的类型是 `string | null`。
如果不管它，`endingId` 就可能是 `undefined`，
而 `JSON.stringify` 会把 `undefined` 字段整个丢掉，存档读回来就少字段了。
`?? null` 把 `undefined` 归一化成 `null`。

**A8.** 为了让 UI 完全不依赖条件 DSL。
如果让 UI 自己判断，那 UI 就得 import `evaluate`、拿到 `EvalContext`、
知道怎么构造 context —— 条件系统一改，所有 UI 都要跟着改。
现在引擎算好 `enabled` 交给 UI，CLI 和以后的 React 界面都只负责
「把 `enabled === false` 的按钮灰掉」这一件事。

**A9.** 后果是**改动量正比于全库内容**。内容库里绝大多数条目（下雨、生病、
宿舍矛盾）跟专业无关，如果默认专属，那每加一个专业都要回头给这几十条全部追加
新专业的 id —— 维护成本落在「你不关心的东西」上，而且漏一条就意味着
新专业少了一批共享内容。
现在的写法（`undefined` = 共享）让改动量正比于**新增内容**：
加专业只需写新的数据文件，老内容一行都不动。代价只有一条：
内容作者**忘了**打标签时，内容是给所有专业看的 ——
这在测试里会立刻暴露（专业隔离的差分不变量），而不是静默出错。

**A10.** 因为「静默回退」会制造一类**极难发现的 bug**：
玩家在界面上选了文科，引擎却按默认专业（计算机）建了这一局 ——
行动池、事件池、结局池、身份文案、结算回顾全部是计算机的，
但**没有任何一处会报错**。玩家只能感觉「怪怪的」，开发者拿到复现也看不出问题在哪。
fail fast 把这行错误提前到 `new GameEngine(...)` 那一行，
错误信息里还列出了可选的 id（`未知专业: nope（可选：computer / literature）`）——
凌晨三点调试时，这条信息本身就是答案。

**A11.** 因为 `clamp`（`effects.ts`）管的是**游戏进行中**的属性变化，
而不变量 I1 说的是「**每项**属性都在 `statRanges` 内」——
它约束的是**状态**，不是「某条代码路径」。
开局那一帧不走 `applyEffects`，是 `createInitialState` 直接写进去的，
如果那里不夹，一个写大的偏移（比如 `social: +40`）就会让玩家第一眼看到
越界的属性条。这是「**不变量要对所有写入点成立，而不是对常用的那个写入点成立**」。
顺带一提：夹取只防越界，防不了「起始值悄悄改掉平衡」——
文科第一版 `academic +5 / social +6` 就把共享的低阈值内容挡在门外了（§8.3（c））。

**A12.** 一个都没加。`Condition` / `Effect` 的判别联合在阶段 2 完全没动
（所以 §1.4 讲的穷尽性检查也一行都不用改）。
项目系统用的是现成的材料：`progressFlag` 是一个数值 flag（引擎每次投入 `+1`），
`completionFlag` 是一个布尔 flag（攒满时置 `true`）；
「完成了没有」用 `{ type: 'flag', key: '项目_长篇_完成' }`，
「投入了几次」用 `{ type: 'flagAtLeast', ... }` 或 `countFrom` 渲染 `{n}`。
换句话说，**新机制是「已有 DSL 的一种用法」，不是「DSL 的一个新分支」** ——
这正是它能在不碰引擎解释器的前提下加进来的原因。

**A13.** 靠三件事，缺一不可：
（1）`pickWeighted` 里 **0 权重是惰性的** —— 不参与权重累加、循环里直接跳过、
`rng()` 仍然只调一次，所以往候选列表里塞一个权重 0 的项，抽签结果与随机数消耗都不变；
（2）**内容的拼接顺序**是「共享在前、专属追加在后」（`data/index.ts`），
所以老专业过滤出来的池子顺序和加专业之前逐位相同；
（3）**过滤在求值之前**，别的专业的内容连条件都不被求值，
也就不会偷走任何一个随机数。
于是新加的项目对六个经典风格是 opt-in（`__project: 0`）——
新机制存在，但对老玩法完全不可见。金标指纹就是这一点的回归证明。
