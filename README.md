# 🎓 大学生活模拟器 (campus-life)

一个**数据驱动**的文字养成游戏。你是一名大三学生，开局先决定自己是
**计算机**还是**汉语言文学**专业；一个学期 16 周，每周 3 点行动力，
在「学业 / 社交 / 健康 / 心情 / 金钱 / 技能」之间做取舍，
还可以花好几周**做出点东西来**（开源库、算法题单、诗集、长篇），
最后走向某个结局。

## 快速开始

```bash
pnpm install              # 装依赖
pnpm dev:web              # ★ Web 界面（开发服务器，带热更新）→ http://localhost:5173
pnpm build:web            # 构建 Web 产物到 dist/
pnpm preview:web          # 预览构建产物
pnpm play                 # 命令行试玩（开局会让你选专业）
pnpm play -- --major literature            # 直接指定专业（computer / literature）
pnpm play -- --seed 2025  # 复现某一局（开局会打印随机种子）
pnpm test                 # 跑单元测试（75 个，含界面渲染）
pnpm typecheck            # 类型检查
pnpm simulate             # 数值平衡模拟：每个专业 × 7 种决策风格 × 200 局
pnpm simulate -- --games 1000   # 加大样本量
pnpm measure:layout       # 布局回归检查（需先跑 dev:web；加 -- --shots 出截图）
pnpm measure:layout -- --ending        # 玩到结局再测「结算页」的布局
pnpm measure:layout -- --start         # 测「开局选专业」那一屏
pnpm measure:layout -- --major literature   # 测指定专业的界面（文科有 7 个行动，更挤）
pnpm measure:layout -- --projects      # 展开作品面板后再测
pnpm preflight            # 推送前自检：代码健康 + 架构边界 + GitHub 连通性
```

> **Web 界面**：`pnpm dev:web` 后打开 http://localhost:5173 。
> 手机连同一个 WiFi 也能访问（开发服务器监听局域网，终端会打印地址）。
> 支持 `?seed=2025` 复现某一局、`?major=literature` 直接进某个专业，
> 链接可以直接分享。
>
> 界面是**移动优先的单栏，宽屏（≥1000px）自动变双栏**：
> 左栏是状态与日志，右栏是操作面板（固定 400px），顶栏横跨整宽。
> 手机端那套是逐像素调过的，双栏只在宽屏生效 —— 移动端几何一行没动，
> 而且是用 `pnpm measure:layout` 的移动端数字逐项比对证出来的。

> **颜色说明**：结算回执默认只在确认支持 ANSI 的终端里上色（Windows Terminal / VS Code 终端 / ConEmu），
> 因为 PowerShell 5.1 的旧版控制台会把转义序列显示成乱码。想强制开启：`$env:FORCE_COLOR=1; pnpm play`。

## 架构：为什么这样分层

```
src/
  engine/          ← 引擎层：纯 TypeScript，零浏览器依赖
    types.ts         所有核心类型（状态 / 条件 / 效果 / 内容定义）
    rng.ts           可复现的伪随机数发生器
    conditions.ts    条件 DSL 的求值
    effects.ts       效果的应用
    state.ts         状态创建 / 日志 / 深拷贝
    majors.ts        专业维度的通用处理（内容按标签过滤，引擎不认识具体专业）
    engine.ts        流程编排（GameEngine 类）
  data/            ← 内容层：全是数据，不含逻辑
    config.ts        数值配置（含每周衰减）——「基准属性」也在这里
    majors.ts        专业表（身份文案 + 相对基准的属性偏移）
    actions.ts       每周可选行动（共享 + 计算机专属）
    events.ts        事件库（共享 + 计算机专属）  ← 加内容只需要改这个文件
    literature.ts    汉语言文学专业的完整内容包（行动 / 事件 / 回顾 / 结局 / 项目）
    projects.ts      计算机专业的项目 / 作品
    endings.ts       结局表
    summary.ts       结算回顾规则（把这一局做过的事翻译成叙述）
  cli/             ← 界面层 A：命令行
    play.ts          交互式试玩
    simulate.ts      数值平衡模拟器（按专业分区输出）
    audit.ts         静态内容审计（死 flag：写了没人读 / 读了没人写）
    text.ts          终端排版（CJK 宽度 / 颜色能力检测）
  web/             ← 界面层 B：浏览器（React）
    useEngine.ts     引擎适配层（唯一认识引擎的地方）
    App.tsx          页面骨架
    styles.css       样式
    components/      开局选专业 / 属性面板 / 日志流 / 行动面板 / 作品清单 / 事件卡 / 结算回执 / 结算页
tests/
  engine.test.ts    引擎与内容（59 个）
  web.test.tsx      界面渲染冒烟（16 个）
  golden-fingerprint.ts  冻结的对局指纹（守护「加专业不影响已有专业」）
```

界面是**两个平行的层**，都只依赖 `data/` 和 `engine/`：

```
   cli/ ──┐
          ├──依赖──▶  data/  ──依赖──▶  engine/
   web/ ──┘                              ▲
                                         │
                        tests/ ──────────┘
```

**`engine/` 完全不认识这两个界面**。这不是一句口号：加 Web 界面时，
`src/engine/` 的改动是 **0 行逻辑**（只加了一个展示顺序常量，见下）。

`engine/` **不认识** `data/` 和 `cli/`；`data/` 也不认识 `cli/`。
内容通过构造函数注入给引擎（依赖注入），所以：

- 换一套内容（比如改成「职场生活模拟器」）不用改引擎一行代码
- 引擎可以脱离界面单独测试，80 个测试跑完只要几秒
- 同一个引擎，命令行能驱动，以后 React 也能驱动

## 六个关键技术点

### 1. 用数据描述逻辑：条件 DSL + 效果 DSL

不写 `if (academic > 80 && week > 10)`，而是写成数据：

```ts
requires: {
  type: 'all',
  conditions: [
    { type: 'week', op: '>=', value: 10 },
    { type: 'stat', key: 'skill', op: '>=', value: 60 },
  ],
}
```

效果同理：

```ts
effects: [
  { type: 'stat', key: 'skill', delta: 6 },
  { type: 'setFlag', key: '拿到实习Offer', value: true },
  { type: 'if', requires: { type: 'chance', probability: 0.3 }, effects: [...] },
  { type: 'branch', options: [{ weight: 6, effects: [...] }, { weight: 4, effects: [...] }] },
]
```

好处：**策划改数值不用碰代码**，TS 的类型还能在编译期抓住写错的字段名。

### 2. 注入随机数种子 → 整局游戏可复现

```ts
const engine = new GameEngine(GAME_DATA, { seed: 42 })
```

同一 seed + 同一串决策 = 同一结局。这让单元测试可以断言随机行为，
也让「存档回放」和「数值平衡模拟」成为可能。

### 3. 兜底分支：游戏永远不会卡死

结局表最后一条的 `requires` 是 `{ type: 'all', conditions: [] }`，
空 `all` 恒为真 → 任何情况下都能匹配到结局，并且有测试专门守着这条不变量。

### 4. 结算回执：玩家看到的数字必须是真的

每次行动、每个选择、每周结束都会显示**实际**的属性变化：

```
▸ 〔第1周〕你选择了「去图书馆自习」
    学业 +4       心情 −2       健康 −1
· 每周固定衰减
    学业 −1       技能 −1       社交 −1
    健康 −1       心情 −1       金钱 −¥100
```

关键在「实际」两个字 —— 学业 98 时选自习，菜单预告说 `+4`，但回执显示 `+2（已满）`。
如果回执照抄预告让玩家高兴，他会一直做无效投入，**永远学不会该换方向了**。

预告和回执**故意用两套逻辑**（声明值 vs 实际值），因为一旦有属性上限、`if` 条件、
`branch` 概率分支，两者必然分叉。有一条不变量守着它：

> **报告的变化量之和，必须等于属性的真实变化。**

它不关心引擎内部怎么算，只要求「你说变了多少」和「实际变了多少」永远一致 ——
这让我们能立刻区分「引擎算错了」和「显示/文案有歧义」，不会去乱改本来正确的代码。

### 5. 结算回顾：把数字变成故事

一局 48 次行动、70 多个事件（每个专业看到其中 60+ 条），如果最后只丢一个结局标题，玩家记不住这局发生过什么。
所以学期结束时给一份**回顾**：

```
════ 计算机专业大三学生 · 本学期结算 ════
 这学期，你——
   · 加入了 ACM 集训队，把自己泡在算法题里
   · 在社团里从新人做到了骨干
   · 给开源项目提的补丁被合并了
   · 投出去了 3 份简历
   · 有 4 周钱包见了底，食堂只敢点最便宜的窗口
   · 身体被透支得厉害
 [ 这一学期，你手上多了些真本事。 ]
 🏁 技术宅的胜利
```

**规则是纯数据**，形态就是「条件满足 → 产出一句话」，复用的还是那套条件 DSL：

```ts
{ requires: { type: 'flagEq', key: '社团贡献', value: 2 },
  kind: 'club', order: 14, text: '在社团里从新人做到了骨干' }
```

好处和内容层一样：**改文案不用碰代码**，而且可以自动检查质量 ——
`pnpm simulate` 会报告有多少条回顾规则从未被触发过（「死规则」，和死结局同一个思路）。
目前计算机 33 条、文科 36 条规则全部可达（**按专业分别检查**：
一条「只有文科会说的话」不该因为计算机没触发它就被误判成死规则）。

顺带说一个只有实测才会发现的细节：**一句话总评是按「归一化后」的属性选的**。
金钱上限是 999999、其余是 100，直接比大小的话总评永远是「跟钱打交道」，
必须比 `值 / 该项上限`。

### 6. 多专业 + 项目：机制放在引擎里，差异全部由数据承担

「不同专业」如果只做**起始数值不同**，那点差异三周就抹平了 —— 因为大家共用同一批
事件和行动。真正拉开专业差距的是**「你能造出什么」**，所以「多专业」和
「项目/作品系统」是一起做的（设计文档 §9 的判断，实现之后也确实如此）。

做法是把两者都做成**数据上的一层标签**：

```ts
// 专业不是引擎里的分支，而是内容的一个可选标签
{ id: 'ev_oss', title: '开源 PR 被合并了', category: 'random', majors: ['computer'] }
// 不写 majors = 全专业共享（绝大多数内容都是这样：宿舍矛盾、下雨、生病……）
```

引擎只学会一句话：「打了标签的内容，只有对应专业看得见」。所以加第 3 个专业 =
新增一个数据文件，`src/engine/` 一行都不用改 —— 而这句话有**两条独立**的测试守着：

1. **源码扫描**：引擎代码里不许出现任何专业 id 或专业名（注释除外），
   杜绝 `if (majorId === 'computer')` 这类暗礁
2. **差分不变量**：把某个专业的内容**单独拎出来**跑一局，结果必须与它在
   完整数据集（含另一个专业的全部内容）里逐位相同

第 2 条不依赖任何冻结数据，所以永远不会过期 —— 它是「加专业只写数据」的真正判据。

项目则是引擎里唯一为「多周投入 → 攒进度 → 完成 → 产出 flag」写的机制
（`getProjects()` / `investProject()`），而且**没有新增任何 DSL 分支**：
进度就存在 `flags` 里，完成判定用现成的 `flagAtLeast` / `if` 表达。
每专业两个项目，性格刻意不同（文科：3 次的诗集 vs 4 次的长篇），
完成产出的 flag 会通向该专业的结局 ——「你成了什么」真的由「你造了什么」决定。

## 数值平衡：模拟器发现了什么

这是这个项目里最有价值的经验。**光靠人肉试玩，你永远发现不了下面这些问题。**

`pnpm simulate` 会用 7 种决策风格各跑几百局，**并按专业分别输出**结局 × 风格的命中率矩阵。
迭代过程中它抓出了三类问题（阶段 2 又抓出了第四类）：

### 问题一：数值全面溢出

第一版每个行动给 +6~+8。48 次行动对 0–100 的刻度来说是碾压，
结果平均学业 95、社交 99、技能 94，保研率 36%。

**修法**：引入**每周衰减**（学业/技能/社交/健康各 −1，心情 −2）。
不持续投入就会退步，行动力立刻变成稀缺资源。同时把所有正向收益压到 +4 左右。

### 问题二：结局互相「饿死」

`学业崩塌` 的触发条件是 `academic < 25 || mood < 10`，
而 `情绪崩溃` 是 `mood < 25 && social < 35`。

结局是**按优先级取第一个满足的**，所以 `学业崩塌` 把 mood 那条线抢走了，
`情绪崩溃` 在 3000 局里一次都没触发过 —— 一段死代码。

**修法**：**一个坏结局只对应一个核心失败维度**。学业归学业（`academic < 25`），
身体归身体（`health < 15`），心情归心情（`mood < 15`），三条线互不重叠。

### 问题三：坏结局把好结局堵死

心情每周 −2，加上学习/写代码/兼职每次 −2，导致「学霸」风格 47% 情绪崩溃、
「技术宅」63% 情绪崩溃。而坏结局优先级更高，意味着**一旦心情崩了，
所有好结局都不可能达成**，`技术宅的胜利` 常年 0%。

**修法**：心情衰减减半到 −1，崩溃阈值下调到真正的灾难级别（< 15）。
另外发现 `投简历` 白送社交 +2，让「孤僻的技术宅」这个设定根本走不通，也去掉了。

### 问题四（阶段 2）：起始属性会偷走共享内容的可达性

新增文科时，第一版给了 `academic +5, social +6` —— 看起来很合理（文科生阅读量大、
表达强）。结果**三条不变量一起报警**：

```
死结局  : 文科 · 学业崩塌（academic < 25）
死事件  : 文科 · 学业预警通知（< 45）、补考通知（靠「被预警」flag）
死规则  : 文科 · 「大部分时间都是一个人过的」（social ≤ 30）
```

原因不是数据写错，而是**共享内容里的「低阈值」路线是按计算机的基准值设计的**：
你把起点抬高 5 点，那些「掉到 25 以下」的失败路线就整片够不着了。
一个专业免疫了某种失败，本身就是数值设计的问题。

**修法**：起始属性只留最小偏移（文科现在只有 `skill −12` 与 `health −2`），
差异交给**行动 / 事件 / 项目**去承担 —— 这正是设计文档 §9 一开始的判断
（「C 是 B 的深度来源」），只是当时没料到它还能这样被自动验证出来。
同类问题还有 mood `+2`：它让「心情 < 40 → 辅导员谈心 → 心理咨询预约」这条链
几乎接不上（心理咨询预约一度成了死事件），也一并去掉。

技术宅 34% 靠作品走通（极端路线的代价是 30% 崩溃）；
社交达人 49% 社交成功但 25% 为钱所困；躺平 16% 学业崩塌；均衡派低风险、全面发展率最高。

文科的签名完全不同：学业线更强（保研 38%）、作品线是它独有的出口
（作品发表 10–12.5%、签约作者 5–9.5%），而代价是健康（学霸 33% 住院休学）。
「作品派」在文科身上 89% 走成签约作者 —— 这是**有意的**：这个风格的全部行动力
都投在写作上，作品线就是它的归宿。

### 问题五（阶段 2.6）：一个「免费」的选项，会悄悄改写整局平衡

试玩反馈说得很准：**钱的用处太窄**。当时钱的去向只有三类 ——
每周固定生活费（强制，玩家无法决策）、「少损失」（修电脑、看病、买教材）、
以及聚餐约会那种小额情绪消费。也就是说钱只能**被动抵挡衰减**，
攒下来没有任何出口，`兼职` 这条线因此缺乏意义。
另一个独木桥是：全项目只有 `socialize` 一个行动能给社交，而它要 ¥40 ——
**钱包见底的那几周，社交这条路是直接封死的**。

于是加了「花钱换属性」（限周事件：健身房 / 培训课 / 班级聚会）和一个
不花钱的社交行动「约同学联机打游戏」。但第一版**把平衡打崩了**：

| 指标（计算机 · 均衡派） | 改之前 | 第一版 | 最终版 |
|---|---|---|---|
| 社交达人 结局 | 4.0% | **42.0%** | 5.5% |
| 保研上岸 | 14.5% | **3.0%** | 16.0% |
| 为钱所困（社交达人风格） | 18.5% | **41.0%** | 24.5% |

两个独立的原因，都很反直觉：

1. **健康是最紧的属性**（§数值设计）。第一版白送健康 +3，等于把最稀缺的资源送人。
2. 更根本的：**模拟器是按权重随机选的，它表达不了「我只在没钱时才这么干」。**
   一个**永远可用**的免费社交行动，会被「有钱的时候」也大量选中 ——
   既顶掉了 `兼职`（于是更容易穷到「为钱所困」），又给所有人涨了社交。

修法是把「只在需要时出现」这件事**写进数据**而不是写进愿望：
新行动的门槛是 `钱 < 40`，与 `聚餐（钱 ≥ 40）` 恰好互斥 ——
**任何时刻都有且只有一条社交路**，钱够就聚餐（社交 +4/心情 +4），钱不够才一块儿打球。
这样既修好了独木桥，又不会给所有对局免费加社交。

> 顺带一提，这次改动还**逼出两个新的自动检查**（见技术文档 §6.5）：
> 「死选项」和「死行动」。因为花钱的门槛很容易写成一个玩家**永远付不起**的数 ——
> 而钱在这个游戏里是紧的（16 周固定 −1600，起始只有 800）。

**「每个专业的每个结局都能被玩出来」已经被写成了单元测试**（2800 局），
以后加专业或调数值时如果某条路线变得不可达，测试会立刻报警。
同构的不变量还有**死事件 / 死规则 / 死项目 / 死 flag**（见技术文档 §6.1）。

## 已知的坑（踩过并已修）

1. **`not chance` 不是 `chance` 的反面** —— 那是两次独立随机，可能两个分支都不中。
   概率分支必须用 `branch`（按权重必定命中一个）。
2. **readline 在没有监听 `line` 事件时会丢掉已缓冲的行** ——
   重定向输入时只有当前 `question()` 挂着的那一行能被接住。
   改用 `rl[Symbol.asyncIterator]()`（内部有行队列）。
3. **`question()` 在输入流 EOF 时 promise 永不 settle** ——
   进程会卡在 top-level await（退出码 13）。异步迭代器会给出 `done`。
4. **行动文案不要手写数值** —— 改了 `effects` 却忘了改描述就会不同步。
   改用 `describeEffects(action.effects)` 自动生成。
5. **npm script 名会被包管理器内置命令遮蔽** —— 我最初把自检脚本命名为
   `pnpm doctor`，结果跑的是 **pnpm 自己的 `doctor`**，不是我的脚本。
   必须 `pnpm run doctor` 才能跑到脚本，所以改名叫 `preflight`。
6. **`.ps1` 脚本里有中文就必须存成带 BOM 的 UTF-8** ——
   Windows PowerShell 5.1 读取无 BOM 的 UTF-8 脚本会按 GBK 解码，
   所有中文变乱码。而 `.npmrc` / `.gitignore` 这类**配置文件反过来要保持纯 ASCII**，
   因为它们的读取方不一定按 UTF-8 解码。规则是：**脚本可以带 BOM，配置必须纯 ASCII。**
7. **临时文件要在 `git add` 之前就忽略掉** —— 我用 `.tmp-commit-msg.txt` 写长提交信息，
   先 `git add -A` 才删除它，结果它被提交并推到了公网仓库，只能再补一个清理 commit。
   现在 `.gitignore` 里有 `.tmp-*` 和 `*.tmp`。
8. **⚠️ Windows PowerShell 5.1 下不要用 `Get-Content` / `Set-Content` 往返处理 UTF-8 文件**
   —— 这是本项目踩过最严重的一个坑，会造成**静默数据损坏**：

   ```powershell
   # 危险！这两行合起来会毁掉文件
   (Get-Content package.json -Raw) -replace 'a','b' | Set-Content package.json -Encoding UTF8
   ```

   - `Get-Content` 在 PS 5.1 里**默认按系统 ANSI 码页读取**（简中 Windows 上是 GBK），
     所以 UTF-8 的中文被误解码成乱码字符
   - `Set-Content -Encoding UTF8` 又把这些乱码字符以 UTF-8 写回，**损坏不可逆**
   - 而且 `-Encoding UTF8` 会**额外写入 BOM**，导致 `JSON.parse` 直接抛
     `Unexpected token ''`，`pnpm` 也读不了 `package.json`

   这个坑当时真的把 `package.json` 推到了 GitHub 上，只能从上一个完好提交恢复。

   **正确做法（二选一）**：
   ```powershell
   # A. 需要精确控制字节/BOM 时，用 .NET（$false = 不写 BOM）
   $t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
   [System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding $false))

   # B. 只改文本内容时，直接用编辑器（本项目里就是 edit 工具），别让 shell 参与
   ```

   **BOM 规则一句话总结**：`.ps1` 脚本里有中文就**必须带 BOM**（否则 PS 5.1 按 GBK 读成乱码）；
   `.json` / `.npmrc` / `.gitignore` 这类**配置文件必须无 BOM 且纯 ASCII**。
   本仓库可以随时用这条命令自检：
   ```powershell
   Get-ChildItem -Recurse -File | Where-Object { $_.FullName -notmatch 'node_modules|\\\.git\\' } | ForEach-Object {
     $b = [System.IO.File]::ReadAllBytes($_.FullName)
     if ($b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF) { $_.Name }
   }
   ```
   正常输出应该**只有 `preflight.ps1`**。

9. **静态审计漏掉一个「写入点」就会报出很像真的假警报** ——
   写「死 flag」检查时，我只扫了行动 / 事件 / 结局 / 回顾规则，忘了
   `config.weeklyEffects`（每周固定结算里也有 `addFlag`：`穷困周数` 就是在那儿 +1 的）。
   于是检查立刻把 `穷困周数` 报成「读了却没人写」。
   **结论：审计的扫描范围必须覆盖所有能写 flag 的入口**，否则你会得到一个
   看起来很严重、其实是自己漏扫的假警报（这类假警报这个项目已经踩过 5 次以上）。

10. **`pickWeighted` 对 0 权重项是惰性的 —— 这一点可以被利用** ——
    项目的投入做成了「opt-in」：6 个经典风格的 `__project` 权重填 0，
    于是它们抽签时即使候选列表里多了一项，结果也逐位不变
    （0 权重不参与累加、总权重不变、`rng()` 仍然只调一次）。
    靠这个性质，「加了整套项目系统」之后旧的对局指纹依然完全一致 ——
    这是「新机制没有扰动原有平衡」的直接**证据**，而不是一句自我评价。

11. **内容的专业标签要跟着「它写/读了什么」走** ——
    新加的两条计算机项目回顾规则忘了标 `majors: ['computer']`，
    它们就变成全专业共享，于是文科会去「读一个自己永远写不出来的 flag」。
    静态死 flag 审计（读了却没人写）和死规则检查（文科不可达）**同时**报警，
    两处互相印证，直接指出是「漏标」而不是「数值不对」。
    这就是为什么两个方向的检查都值得写。

12. **模拟器是「按权重随机」的，它表达不了「我只在需要时才这么做」** ——
    阶段 2.6 加了一个「不花钱的社交」行动（约同学联机打游戏），本意是给钱包见底的人一条路。
    结果 社交达人 结局在计算机均衡派身上从 4% 涨到 **42%**、保研从 14.5% 掉到 3%。
    原因是它**永远可用**，于是「有钱的时候」也会被大量选中：既顶掉了 `兼职`
    （更容易穷到「为钱所困」），又给所有人涨社交。
    **修法不是调权重，而是把「只在需要时出现」写进数据**：
    它的门槛是 `钱 < 40`，与「聚餐（钱 ≥ 40）」恰好互斥。
    教训是通用的：**当一个行为在现实中是「有条件的」，那个条件就该写进 `requires`，
    而不是指望平衡时的权重去模拟它。**

13. **重活不给足超时，就会得到「时间造成的假警报」** ——
    七条「死 XX」不变量共用一份 1680 局模拟（`beforeAll` 里只跑一次），它要 4–5 秒，
    而 vitest 默认超时正好是 **5 秒**。于是它长期坐在悬崖边上，偶尔红掉。
    坑在于**它红的样子和「某结局不可达」几乎一样**，排查会先翻内容，
    而真凶只是它跑得慢 —— 中途我就被它骗过一次（还以为是自己改文案改坏了）。
    修法是**局数不降、超时给足**：样本量本身就是「稀有内容算不算可达」的判据
    （有些内容 2800 局才出现 4 次），不能为了跑得快把判据削弱。

14. **布局改动必须有自己的断言，光看「没溢出」是看不出「其实是单栏」的** ——
    做桌面双栏时意识到：一个 620px 的柱子同样不会溢出，照样全绿。
    所以给 `measure:layout` 加了一条**两栏几何**断言（宽屏必须并排、窄屏必须堆叠），
    并在视口表里补上 **1024×768 这个临界宽度**（断点在 1000px，最窄的双栏才是最容易出事的）。
